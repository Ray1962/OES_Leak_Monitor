# The documents in `docs/`

What each document is for, who reads it, whether it ships, and how it is regenerated. The rules that apply to all of them are in `CLAUDE.md` → Documentation.

`docs/` holds the human-facing docs (the design notes there are the authority on the maths, not these dev notes):

- `user-manual-zh-TW.md` — the operator manual (Traditional Chinese): the actinometry model, every tab control by control, file layout and CSV formats, day-to-day SOPs, troubleshooting, default-value tables. **This is the source of truth — edit the Markdown, never the HTML.**
- `user-manual-zh-TW.html` — a generated, self-contained rendering of the manual (inlined CSS, sticky section list, dark-mode and print stylesheets, no external requests) for operators who won't open the repo. Regenerate it after **every** edit to the Markdown, or the two drift apart:

  ```
  python3 tools/md2html.py docs/user-manual-zh-TW.md docs/user-manual-zh-TW.html "OES Leak Monitor 操作手冊"
  ```

  `python3 tools/check-docs.py` checks every generated doc against its Markdown and the two publish lists against each other (CI runs it on every push and PR); `--fix` regenerates the stale ones with each document's own title, which a hand-typed `md2html.py` command does not keep.

  The manual's screenshots are `docs/images/manual-*.png`, referenced as `![caption](images/…)` on a line of their own; `md2html.py` embeds each one as a data URI (so the HTML is ~4 MB and stays one file) and adds the figure CSS only to a document that has a figure, so every other generated doc is unchanged. They were taken by replaying the 2026-08-14 recording; `run-app` has the procedure ("Retaking a user-manual screenshot") — retake one when its tab's layout changes.

  `tools/md2html.py` is a deliberately small converter covering only the Markdown subset the manual uses — there is no pandoc or python-markdown in this environment. It is deterministic (same input → byte-identical output), so a regeneration that produces no diff means the HTML was already current. Anchor ids follow GitHub's slug rules so the manual's hand-written table of contents works in both renderings; note that `\w` in Python is already Unicode-aware, and naming extra CJK ranges in the slug regex breaks it by preserving fullwidth punctuation.
- `daily-inspection-plan-zh-TW.md` / `.html` — the fab-side inspection plan (Traditional Chinese): two-tier routine (L1 per-shift spectrum/trend check by an Operator who changes nothing; L2 weekly strategy review by an Engineer), the spectrum × trend diagnostic matrix, per-process line-selection and interference guidance, escalation matrix, printable checklists. Same Markdown-is-the-source rule and same generator as the manual — regenerate after every edit:

  ```
  python3 tools/md2html.py docs/daily-inspection-plan-zh-TW.md docs/daily-inspection-plan-zh-TW.html "OES Plasma Monitor 日常巡檢計畫"
  ```

  Both HTML files ship in the publish folder (`CopyOperatorDocs`), so a stale HTML is what the fab actually reads.
- `leak-rate-calibration.md` — full design + maths for the leak-rate calibration (P0–P4).
- `ratio-csv-sigma-score-zh-TW.md` — how to read the two numeric columns the ratio CSV writes per ratio (Traditional Chinese): the raw per-frame value against the EMA-derived second column, why a `RawMean` numerator switches that column from `_pctBaseline` to `_sigmaScore`, and the full derivation of the σ-score — the dt-aware EMA, the EWMA variance, `EffectiveSigma = max(baseσ, liveσ)` and the `20/SigmaWarn` scaling that puts the Warn threshold exactly on 120. Two worked examples: a hand-computable one, and a frame-by-frame reconciliation against `P_Ratio_0819175504.csv` (reproduced to 0.008 points), including how to recover a baseline that is no longer in `settings.json`. The point operators get wrong is in there, worked out frame by frame (§4.1): a jump inflates `liveσ` faster than it moves the mean, so the score *falls* on the frame the raw value spikes and then climbs for `2τ·ln(liveσ/baseσ)` seconds afterwards while the noise estimate decays — 32 s in the sample file, over which the score triples (109 → 310) while the raw value is *falling* 8 %. Decomposed, 82 % of that climb is the shrinking denominator and 18 % the EMA still catching up; the counterfactual column shows the answer was complete on the first frame. The warning timing cross-checks it (crossed 120 at 55:26, `ConfirmSeconds` 15 s, `OverallState` Warning at 55:42). No HTML rendering — this is a maintainer/engineer note, not a shipped operator doc.
- `golden-run-baseline-troubleshooting-zh-TW.md` / `.html` — why a Golden Run baseline was refused, and whether that refusal is a fault at all (Traditional Chinese). Its premise is the one the engine does not encode: **what this tool detects is absent when the chamber is healthy**, so a leak-free N/O line reads at the noise floor and a baseline defined as a *divisor* cannot exist for it. It separates the two regimes (no reactant gas / N₂-O₂ admitted deliberately), maps every sentence `ReportDroppedRatio` can emit to an action and a way to check that action worked, and gives equal weight to the opposite failure: a `RawMean` reading whose continuum pedestal sails through every gate and produces a healthy-looking baseline that measures the background rather than the species — which nothing in the app warns about. Same Markdown-is-the-source rule and same generator as the manual — regenerate after every edit:

  ```
  python3 tools/md2html.py docs/golden-run-baseline-troubleshooting-zh-TW.md docs/golden-run-baseline-troubleshooting-zh-TW.html "OES Leak Monitor Golden Run baseline troubleshooting"
  ```

- `baseline-builder-sop-zh-TW.md` / `.html` — the field SOP for building a Golden Run from recordings already on disk (Traditional Chinese). It is written as the site's **standard** way to build a baseline, not as the recovery path for a failed live capture, because on a tool whose process ramps or is shorter than a capture window the live capture was never the right one. Two parallel flows, single-recording and pooled-across-recordings, because their acceptance criteria genuinely differ: the first is judged on in-window steadiness and the back-check, the second on between-recording spread — which is also where the one finding that overrules a decision lives (an absolute-intensity entry pooled across runs takes the brightness gap into its σ, measured as `mean/σ` 125 → 10.7). Three hazards the app does not guard get their own steps rather than a note: a Build result stays saveable after you change the ticks or windows (so Build and Save must be one person's continuous action), a scan is silently invalidated by a later Ratio Setup / wavelength-correction / trigger-threshold edit (so those are frozen up front), and the result panel's own numbers — `mean/σ`, spread, steadiness, back-check — exist nowhere but that text box, so copying them into the day folder as `_baseline_*.txt` is a required step, not housekeeping. `§16` holds the current implementation limits (`MinFrames` 60 and the 5 σ outlier bound are not operator-adjustable, one window per recording, no class override) as one section, so an extension to the tab changes one place rather than several. The multi-process appendix reuses the pooled flow and adds only the per-class accounting the `State` column makes possible. Same Markdown-is-the-source rule and same generator as the manual — regenerate after every edit:

  ```
  python3 tools/md2html.py docs/baseline-builder-sop-zh-TW.md docs/baseline-builder-sop-zh-TW.html "OES Leak Monitor Baseline Builder 操作 SOP"
  ```

- `leak-test-20260819-analysis.md` — analysis of the 2026-08-19 leak-valve tests (Traditional Chinese), and the closest thing this repo has to a worked example of reading its own output. - `leak-test-20260920-analysis-zh-TW.md` / `.html` — the first run of the plan's P1 gate **on the production tool** (Traditional Chinese), and a null. **Its headline verdict — "the dosing valve delivered nothing" — is withdrawn (erratum at the top, 2026-10-01):** every expectation in it assumed 500 sccm total flow, the real recipes run ~30 000–36 000 sccm, so the leak was diluted ~61× and the measured +1.9 % sits inside the corrected +1.4…+3.3 % expectation. Read what follows with that in mind; the scatter, throughput and configuration findings stand. As first written: the dosing valve delivered nothing. `R_N2CO_C` moved +1.9 % at a nominal 1.0×10⁻² mbar·L/s — larger than the spec target — against a 9.3 % criterion and an extrapolated +77…+178 %. What makes that a statement about the valve rather than the indicator is a whole-spectrum regression: **twelve nitrogen features across 236–428 nm all sit within ±1 %**, and the decisive one is **CN violet 388**, because the plan's only unquantified risk (§15.4: TEOS carbon eats the leaked N₂) carries its own corollary — if N₂ were being consumed, CN would brighten. Both read −0.1 %. So the GO margin is neither verified nor refuted. Three things the day still bought: the plan's σ figures reproduced on the real tool (cross-recording 2.97 % → mean/σ 33.7 against 3.1 % → 32.2, so the extraction geometry and the +0.30 nm axis offset transfer, and this day can supply a valid Golden Run); a controlled 3.06× viewport-transmission swing that turns the 7.5 nm rule from inference into measurement — and in the same stroke **kills the `R_N2Ar_C` veto**, whose 337-over-750 pair measures the fouling; and process B's cross-recording spread falling from 15.5 % to 7.01 % — what Batch Trend reads — while its pooled-frame mean/σ, the quantity `MinBaselineMeanToSigma` is actually applied to, is 5.0, so B still gets no baseline and `TrendOnly` stands (the first draft compared the cross-recording 12.3 against that threshold, and §6.2.1 records that the plan's own §4.1 table made the same mismatch). Two configuration findings need fixing before a re-run: the classifier's Hα threshold headroom has fallen to 1.06× on the B side, and **the site configuration of plan §17 was never installed on the tool** — that day ran the old ratio set against the mis-captured 09-03 `Recipe 1` and sat in a latched Alarm from before the first dose. Scripts in `tools/analysis/20260920/`; not shipped, like the other analyses.
- `leak-test-20260928-analysis-zh-TW.md` / `.html` — the second production-tool re-run (Traditional Chinese), on two new recipes (A = LDR400 1.8 torr, 63 s; B = HDR1730 3.8 torr, 97 s, now with argon) up to DV 200 (four notes originally read `DV=250` and were corrected to 200 by the operator), and **a second null**. The notes carry only `DV=`, so the process is read off the spectrum (`Ar750/O777 > 0.5`). B settles it directly — dose order not monotonic, throughput flat, nothing nitrogen-bearing moves (|t| ≤ 1.5); A cannot, because its dose rises strictly with the clock while the chamber warms (Ar 750 ×2.4 in 30 min, drift inside one valve setting as large as between settings), so the argument there is spectral shape: an air leak *adds* emission at the band heads, and the N₂ 337 head never outruns its own sides by more than the brightness nonlinearity explains — seven DV 200 steps with the valve untouched span a 56 % Ar 750 rise, and the excess just follows the brightness. The day's real finding is **light level: an order of magnitude below 09-20** on the same spectrometer and exposure (UV ~1/10, NIR 1/25–1/100), which puts N₂ 337 at 7 % of its window in A and below detection in B, per-frame SNR 4.7–6.6 — why every N₂ ratio failed the Golden Run SNR gate that day — and leaves B's plasma gate 6–10 % above threshold. At that level the detector's fixed pattern (hot pixels at 236.9 and 337.1 nm, visible with the plasma off and identical on 09-20) is as large as the signal, so a PeakHeight maximum mostly picks a pixel; the app's own `NO 237` reading re-centres to 237.6 nm and reads the flank of an unidentified 238 nm feature, not NO. §4.3 takes on the plot that looks like a dose response — A's band-averaged 337 head rising 28 → 40 → 49 with DV — and shows it is not nitrogen: its ratio to CO 349 holds at 0.399 (CV 2.8 %) across twelve steps while the head itself moves 22 %, its shape runs to the red (N₂ second-positive shades to the violet; the same feature is thirty times brighter in a 09-20 O₂ clean, inferred CO₂⁺), and a fitted N₂-shaped component is zero throughout. §4.4 is the finding that reaches the plan: **these recipes flow 31–36 slm, not the 500 sccm plan §16.1 assumed**, so DV 200 is ~19 ppm of air and the expected rise is +1…+3 % — the day could not have seen the leak whether or not the valve delivered. The operator confirmed the unit and that 09-20 ran the same order of flow, which **withdraws the 09-20 "valve delivered nothing" verdict and turns plan §16's GO (8.3× margin) into NO-GO**: detectable leak 2.8–6.5×10⁻² mbar·L/s, 3.2–7.3× the 1 mTorr/min spec. The same section then settles whether 09-20's "N₂ 337" was air arriving by another path (a TEOS line): it was not nitrogen at all — the feature peaks at 338.2–338.6 nm, travels with the CO₂⁺ 288.3/289.6 doublet across a 44× range and four plasma types, and the N₂ (0,1) head at 357.69, which shares its upper level and must be ~0.67 of (0,0), reads −32 where +1041 was required. So `R_N2CO`'s leak-free numerator is CO₂⁺ (its 3 % CV is carbon oxide over carbon oxide, plan §3.1's trap again), and **the UV axis offset is +0.10 nm, not the +0.30 measured beyond 690 nm**. Also records a Golden Run captured at DV 200 and overwritten across processes under one name. Scripts in `tools/analysis/20260928/`; not shipped.
