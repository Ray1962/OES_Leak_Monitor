# Build, publish and the native DLLs

Read before touching `publish.cmd`, the publish profile, or any of the csproj targets that copy files into the output folder.

## Standalone publish (no .NET install required on the target PC)

`Properties/PublishProfiles/SelfContained-win-x64.pubxml` produces a single self-contained `.exe` (the .NET 8 runtime is bundled in). Three ways to run it: double-click `publish.cmd` in the repo root; `dotnet publish src/OES_Leak_Monitor/OES_Leak_Monitor.csproj -p:PublishProfile=SelfContained-win-x64`; or in Visual Studio right-click the project → Publish → that profile. The `/publish` Claude slash command does the same. Output: `src/OES_Leak_Monitor/bin/Publish/win-x64/`.

The `.exe` bundles all managed code plus the .NET 8 runtime, but native DLLs are not embedded — the output folder also holds the WPF native DLLs (`wpfgfx_cor3.dll`, `PresentationNative_cor3.dll`, `D3DCompiler_47_cor3.dll`, `PenImc_cor3.dll`, `vcruntime140_cor3.dll`), the OES native DLLs (`UserApplication.dll`, `SiUSBXp.dll`, `libsodium.dll`) and the Visual C++ runtime (`vcruntime140.dll`, `vcruntime140_1.dll`, `msvcp140.dll` — see `CopyVcRuntime` below). Ship the whole folder together — those DLLs are loose next to the `.exe` on purpose (the `DllResolver` only searches the app base directory; see the native-DLL note below). Do not enable `IncludeNativeLibrariesForSelfExtract` — it would bundle the OES DLLs into the exe and break hardware connect.

The `CopyOperatorDocs` target also drops the operator-facing HTML docs — `docs/user-manual-zh-TW.html`, `docs/daily-inspection-plan-zh-TW.html`, `docs/secs-operation-sop-zh-TW.html`, `docs/secs-acceptance-sheet-zh-TW.html`, `docs/CONTEXT-zh-TW.html`, `docs/golden-run-baseline-troubleshooting-zh-TW.html`, `docs/baseline-builder-sop-zh-TW.html`, `docs/secs-ratio-svid-example-zh-TW.html`, `docs/fdc-integration-spec-zh-TW.html` and `docs/eap-tool-event-secs-spec-zh-TW.html` — into the publish folder (publish only, not build), so a delivery folder carries its own manual, inspection plan, SECS SOP, acceptance sheet, glossary, Golden Run troubleshooting guide, Baseline Builder SOP, per-ratio SVID examples and the FDC and EAP interface specs. The two specs ship because the tool's site has no outside network: the copies on the OES PC are the ones the FDC and EAP people actually read. Both the `Warning` and the `Copy` batch over the `_OperatorDoc` item, so a missing file warns on its own and the rest still ship; regenerate it first (see `CLAUDE.md` → Documentation). Adding another shipped doc means adding one `_OperatorDoc` line here **and** one filename to `publish.cmd`'s completeness check.

Two guards exist because a publish can "succeed" and still produce an unshippable folder. Left alone, an incremental `dotnet publish` (nothing changed since the last one) keeps the `.exe` but strips every loose native DLL — a folder that launches fine and then falls back to test mode on the production PC, the hardest failure mode this app has:

- `EmptyPublishDirBeforePublish` (csproj) empties `$(PublishDir)` first, so every publish is a full copy. It hooks **`PrepareForPublish`, not `Publish`** — the pipeline copies its files inside targets that `Publish` depends on, so `BeforeTargets="Publish"` runs *after* the copy and would delete exactly what it was meant to protect. It only ever cleans a folder under the project's own `bin\`; a `-o` path outside it is warned about, not deleted.
- `publish.cmd` re-checks all 24 expected files afterwards and refuses with a non-zero exit if any are missing.

> ⚠️ **Never `set` an MSBuild property name as an environment variable in `publish.cmd`.** Environment variables become global MSBuild properties, so a helper called `OUTDIR` silently becomes `OutDir`, redirects the *build* output into the publish folder, and single-file bundling then dies with `Unable to access file during bundling` / a missing `runtimeconfig.json`. The folder-path helper is deliberately named `PUBFOLDER`. The same trap applies to `CONFIGURATION`, `PLATFORM`, `OUTPUTPATH`, `TARGETFRAMEWORK`.
## Native DLL flattening (do not remove)

`Aqst.OesSpectrometer` ships `UserApplication.dll`, `SiUSBXp.dll` and `libsodium.dll` under `runtimes\win-x64\native\`, but the package's `DllResolver` only searches the app base directory. The `FlattenOesNativeDlls` MSBuild target in `OES_Leak_Monitor.csproj` copies those three DLLs into `$(OutDir)` (and `$(PublishDir)`) after Build/Publish. If hardware connect silently falls back to test mode, check that those files reached the output root.

## The Visual C++ runtime ships app-local (do not remove)

`UserApplication.dll` statically imports `libsodium.dll`, which imports `VCRUNTIME140.dll`. On a PC that has never had the **Visual C++ 2015–2022 x64 redistributable** installed, `LoadLibrary` fails with Win32 126 (`ERROR_MOD_NOT_FOUND`) before a single device is enumerated — and `OesDevice.CheckHardwareDllAvailability` catches that into `SetupTestMode()`, so the app reports "Connected", streams synthetic spectra into the real data folder under the ordinary `P_` prefix, and writes **nothing at all** about why. It is indistinguishable in the audit log from a healthy connect except for `Serial=TEST_MODE_SIMULATOR`. Measured on a fab PC on 2026-08-17: complete delivery folder, correct bitness, working driver, vendor software connecting fine, and this was the difference.

The `CopyVcRuntime` target therefore copies `vcruntime140.dll`, `vcruntime140_1.dll` and `msvcp140.dll` into `$(OutDir)` and `$(PublishDir)`, which removes the prerequisite: Windows resolves a dependency from the executable's own folder before the system directories. Notes:

- `vcruntime140_cor3.dll` (already in the publish folder) is WPF's **renamed private copy** and does not satisfy an import of `VCRUNTIME140.dll`. It is not a substitute, and its presence is why the folder looks like it already carries the runtime.
- All three travel together — `msvcp140.dll` imports `VCRUNTIME140_1.dll`. Only `vcruntime140.dll` is strictly required by today's import graph; the other two guard against a dynamically loaded C++ component in a future SDK build.
- Source order: `-p:VcRuntimeSourceDir=<folder>` if the build sets one, then the VS C++ redist folder (`$(VCToolsRedistDir)`, only defined in a developer prompt), then `%SystemRoot%\System32` — the same binaries the redistributable installs. A build machine with no redistributable at all warns per file and `publish.cmd` then refuses the folder.
- `tools/check-oes-connect.ps1` (+ `.cmd` wrapper) is the field diagnostic for this whole class of failure: run it **in the app folder, as the operator's own user**, and it reproduces `DllResolver.Resolve` → `CheckHardwareDllAvailability` → USB enumeration and prints the Win32 error the app swallows, plus the device list and an open test. It is the only way to tell "DLL will not load" from "no device found", because the app logs neither.
