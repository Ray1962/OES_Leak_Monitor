# App shell: framework surface, MainViewModel, settings

What comes from the `Aqst.OesApp.*` packages, how `MainViewModel` wires the app, how `settings.json` is loaded and defaulted, and the Monitor tab's live trend.

## What comes from `Aqst.OesApp.Core` / `Aqst.OesApp.Wpf` (referenced, not defined here)

- `DeviceViewModel`, `LoggerViewModel`, `LogViewerViewModel`, `SystemLogger`, `DualIntensityLogger`, `IntensityCsvWriter`
- `AccessControlService`, `UserRole` (Guest < Operator < Engineer < Admin), `LoginDialog`, `UserManagementDialog`, `AccessControlConfig`
- `OesAppPaths` — resolves per-user AppData subfolders (`Config`, `Log`, `Data`) under the app folder name
- `RelayCommand`, `DeviceSettings`, `LoggerSettings`, `LogSeverity`
  - `DeviceSettings.AcquireMode` (`HWAvg` / `Oneshot` / `Standard`; `HWAvg` was `HardwareAverage` before SDK 0.5.0) and `DeviceSettings.AverageMode` (`Hardware` / `Software`) are exposed as combo boxes in the Configuration tab and hot-applied by Apply (`UpdateParametersAsync`). `Oneshot` is the fix for segmented / torn frames on Z5 / Ethernet modules; `Software` averaging trades N× wall-clock for avoiding the peak shift / broadening some hardware averagers introduce. Both round-trip through `settings.json` as strings (`SettingsService` registers `JsonStringEnumConverter`), so pre-existing files without the keys just keep the defaults.
- WPF user controls bound in `MainWindow.xaml`: `DevicePanel`, `ConfigurationPanel`, `LoggerPanel`, `LogViewerPanel`
- Global `using Aqst.OesApp.Core;` and `using Aqst.OesApp.Wpf;` are injected via the csproj, so these types appear unqualified throughout.

Treat that NuGet surface as the framework. When something looks "missing," it is almost certainly defined in those packages, not here.

## `MainViewModel`

wires a single `DeviceViewModel` (the `DeviceProfiles` array has one entry tagged `"OES1"`), the `DualIntensityLogger`, the `RecordingsViewModel`, and the toolbar role badge. Per-device Connect/Disconnect/Start/Stop live in the embedded `DevicePanel` header (Monitor tab); the LoggerPanel exposes Start Save / Stop Save. The top toolbar holds only the title, status message, and the user/role controls — there is no longer a "Both" command that bundles device + logger.

- **Constructor ordering (load-bearing).** `settings.json` is loaded and `Logger.LoadFrom` runs *before* `RecordingsViewModel` / `RatioReviewViewModel` are constructed, because both read the logger in their own constructors — they scan `EffectiveBaseDirectory` once, and Recordings also snapshots `Logger.TriggerWavelength` into `_wavelengthNm`. Built against an un-hydrated `LoggerViewModel` they silently take the factory defaults (the AppData fallback folder instead of the configured data directory — both tabs then show "0 files" until the user presses Refresh — and 337 nm instead of the configured trigger). Don't move the review tabs back above the settings load. The runtime counterpart is in `ApplyAll`: a changed base directory (tracked in `_lastDataDirectory`) re-`Refresh`es both tabs and logs `DataDirectoryChanged`, since neither watches the logger for path changes.
- **Trigger modes (Core 0.1.6).** `LoggerSettings.TriggerMode` decides what the save threshold is compared against: `Wavelength` (unchanged default), `SpectrumPercentile` (the frame's `TriggerPercentile`-th percentile — tracks the discharge rather than the gas mix, for a recipe that admits the watched gas after ignition or only in some steps), or `AnyMonitoredWavelength` (brightest of `MonitoredWavelengths`). `MainViewModel.TrendThresholdFor` passes 0 for the Monitor trend's dashed threshold line in the whole-frame modes — that line marks the threshold against the trigger *wavelength's* trace, which stops being the trigger, and a line drawn at a meaningless height is worse than no line. The recorder strip's text names the active mode.
- **Recorder strip (Monitor tab).** `RecorderStateText` / `RecorderBrush` / `RecorderDetailText` / `RecorderWarningText` / `RecorderTooltip` are a read-only projection of the logger, recomputed by `UpdateRecorderStatus()` from `Logger.PropertyChanged`. It exists because the `LoggerPanel` — the only place that shows whether anything is being recorded — lives in the Engineer-gated Configuration tab, so an Operator doing the daily check previously had no way to see it. Status only, by design: seeing the state is an Operator concern, arming stays an Engineer one. `RecorderWarningText` compares the live `Logger.Enabled` against `_persistedLoggerEnabled` (the value in `settings.json`, refreshed at load and in `SaveSettings`) and warns while they differ — Start Save without Save silently reverts to disarmed on the next launch, which is otherwise invisible until the data is missing. Documented for operators in the manual §6.1.2.

## `AppSettings` + `SettingsService`

`settings.json` in `OesAppPaths.ConfigDirectory`. Two framework `LoggerSettings` defaults are overridden for a fresh file: `DefaultTriggerWavelengthNm` (337.1, the N₂ band head, not the framework's 387) and **`DefaultLoggerEnabled` = true** — the framework ships a general-purpose recorder disarmed, but a leak monitor that isn't recording has nothing to show when someone asks what the tool was doing an hour ago, and the arming switch is on the Engineer-gated Configuration tab an Operator never opens. Only the *factory* value changes: a stored `"enabled": false` is a saved decision and is honoured. A third override, `DeviceSettings.ForceTestMode`, works the same way: **`DefaultForceTestMode` = false**, because the framework ships it *true* and a fresh settings.json therefore ran the whole leak monitor on the synthetic generator — nothing on screen says so but `Test Mode: True` in the `DevicePanel` footer, and the CSVs carry the ordinary prefix. `AppSettings.NewDevice()` is the one place that value is applied, so the default list and `OnDeserialized`'s padding cannot disagree; `AppSettingsDefaultsTests` pins all three plus the stored-decision half of the contract. `MainViewModel.LoadDefaultsAll` re-applies all three after `LoadDefaults()`, so the button and a fresh install land in the same place — left alone the framework's device defaults silently re-arm test mode and the next Save persists it. `AppSettings.OnDeserialized` migrates the legacy `device1`/`device2` keys into the `devices` list, and pads the list to at least 2 entries (legacy schema lock — do not shrink to 1).

## `WavelengthTrendViewModel` + `WavelengthTrendPanel`

the live intensity time-trend chart below the `DevicePanel` on the Monitor tab. It does **not** subscribe to the device itself; `MainViewModel.FanOutSpectrum` feeds it each frame via `OnSpectrum(...)` (see the fan-out note in `replay.md`), and it plots one line per tracked wavelength: the trigger ("threshold") wavelength configured in the `LoggerPanel` (the "selected" wavelength — not a separate setting), plus the first `MaxMonitoredWavelengths` (5) entries of that panel's monitored-wavelength list (the wavelengths logged into the intensity CSV). Each line is the peak intensity within ±0.5 nm of its wavelength (a peak *locator* that absorbs wavelength drift — **not** noise filtering; by default the chart plots the raw per-frame counts, deliberately unfiltered, so it reads like a live scope). A dashed reference line marks the save-start threshold intensity. `MainViewModel` seeds it from `LoggerViewModel.ToSettings()` and re-points it (`Configure`) on every `ApplyAll`; any change to the tracked-wavelength set rebuilds and clears the trends. Two display toggles, both re-projecting from each `Track`'s retained raw points so the toggle also transforms the history already on screen: a **Smooth** checkbox (default off) applies the same `α = 1 − exp(−dt/τ)` EMA the Leak Monitor uses (τ = `SmoothTauSeconds`, 3 s) to damp per-frame noise — the running EMA is advanced every frame in `UpdateEma` and replayed across raw on toggle; a **Normalize** checkbox divides every line by its value at the moment the box is ticked (baseline captured in the *display* domain, so a smoothed line also snaps to 1.0), the threshold line hidden while normalized. Follow-while-zoomed, Zoom All — same chart conventions as the Leak Monitor trend. Retention is `AppSettings.TrendRetentionMinutes` (default 30, clamped 1–480), a **single setting shared with the Leak Monitor trend** — they are read together, and every point is held in memory, so the ceiling is a real limit. Applied via `SetRetention` at construction and on every `ApplyAll`; shortening it trims the plotted points immediately, measured against the newest point rather than the wall clock (the chart's clock is the spectrum stream — with acquisition stopped, "now" would empty it).
