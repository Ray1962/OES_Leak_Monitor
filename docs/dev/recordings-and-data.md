# Recordings and the data folder

The CSV files on disk and everything that reads, archives, snapshots or bundles them.

## `Recording` / `RecordingGroup`

parse CSVs produced by `IntensityCsvWriter` under `{baseDir}\YYYYMM\DD\{prefix}_{tag}_{MMddHHmmss}[_N].csv`. The group key is `{prefix}|{sessionStart}|{rotation}` (dual-OES file layout preserved) but only the `"OES1"`-tagged file populates the group; any historical `"OES2"` siblings on disk are ignored at scan time. Year is recovered from the parent folder.

## `Recording.FromArchive` / `Recording.OpenText`

the review tabs read archived CSVs **straight out of `DD.zip`**, so compressing a day folder (see `DataRetentionService`) doesn't hide it from Recordings / Ratio Review. Scanning a month folder lists loose `*.csv` and then each `*.zip`'s central directory; an archived `Recording` carries `ArchivePath` + `EntryName`, and `OpenText()` returns a `StreamReader` over the entry whose `Dispose` also closes the owning `ZipArchive`. Parsing streams the decompression — a 30 MB full-spectrum entry parses in ~0.35 s with no temporary extraction, which matters because a single file can be several hundred MB. `RecordingCsvParser.ReadFull(TextReader, …)` (Core 0.1.5) and `RatioCsvReader.Read(TextReader, …)` are the overloads that make this possible; both are forward-only, so a non-seekable stream is fine. The lists show a `zip` marker column and Ratio Review's status names the source archive.

## `RecordingsViewModel` + `RecordingsPanel`

Recordings tab: scans the data folder, builds OxyPlot line / heatmap / frame-spectrum views, supports two-row compare mode (two sessions overlaid — orthogonal to device count), PNG export, clipboard copy, notes, search. **The line view plots up to `MaxTrendWavelengths` (6) wavelengths**, added from the emission-line catalog picker or typed free-hand (a stretch of continuum with no line on it is the control you need when judging whether a line responded, and the catalog cannot offer it). **Colour encodes the wavelength, dash pattern the session** — "which line moved" and "how does this run differ from that one" are separate questions, so they get separate channels instead of being made mutually exclusive; colours are positional and re-dealt on removal so the swatch list can't disagree with the legend. `NormalizeTrend` divides each trace by **its own mean over the whole recording** (not the first frame — a recording usually starts before the plasma is lit, and dividing by ~0 explodes the trace); it is *not* the Leak Monitor's % -of-baseline, whose divisor is a Golden Run, so the axis says `× own mean` and a trace whose mean is ≤ 0 is left in raw counts and labelled. `UsePeakWindow` (±0.5 nm max, matching the Monitor tab's live trend) is **off by default**: taking a window maximum biases a weak line upward and inflates its scatter, which is exactly the σ-based judgement §1.1 asks the operator to make here — drift belongs to the Wavelength Calibration overlay instead. The set persists to `AppSettings.RecordingsWavelengths` on every change (a review preference, not a measurement setting), written with the same read-modify-write idiom as the replay selection since whoever is comparing recordings never visits the Configuration tab's Save.

## `RatioReviewViewModel` + `RatioReviewPanel` + `RatioCsvReader`

Ratio Review tab: scans the data folder for the `{prefix}_Ratio_*.csv` files `RatioCsvLogger` writes, and plots the selected file's per-ratio trend in one of three modes — % of baseline (with the 100/120/150 % threshold lines), raw ratio, or **leak rate** (the calibrated `Q̂` in mbar·L/s with a translucent ±1σ band) — with the composite leak state drawn as translucent Warning/Alarm bands behind the series. The ratio CSV carries trailing `LeakRate,LeakRateSigma` columns (P3); `RatioCsvReader` locates columns by header name so pre-calibration files (without those columns) still parse, exposing `RatioTrendData.HasLeakRate`. The per-ratio percent column is named for what it holds — `_pctBaseline` or `_sigmaScore` (see `ValueHasPedestal` in `ratio-setup-and-lines.md`) — and `RatioTrendData.PctIsSigmaScore` carries that through so the legend can mark a σ-score series; both share the 100/120/150 scale by construction, but they are not the same number and a file that doesn't say which is unreadable a year later. Reuses `Recording.TryParse` for the shared filename scheme, filtering on the `"Ratio"` tag. PNG export, clipboard copy, search.

## `ConfigSnapshot` + `SystemLogMirror`

**what makes a day folder readable on its own.** The data lives wherever the operator pointed the logger (a fab machine's `C:\DualOES`); everything needed to interpret it lives under `%AppData%` — the save threshold and trigger mode that decide which frames are evaluated at all, the ratio definitions, the wavelength corrections, the active Golden Run, and the system log saying what the tool actually did. Copying a day folder off the machine takes the first and leaves the second, which is not a mistake anyone makes once: it is what the folder layout invites. On 2026-08-19 it cost a day's leak testing — the save threshold had to be bounded by arithmetic on the frame that opened the plasma gate, and the acquisition mode inferred from the frame interval, both of them sitting in a file nobody thought to copy (`docs/leak-test-20260819-analysis.md` §9). `ConfigSnapshot` writes `_config_{HHmmss}.json` beside the recordings when one opens, **skipping when the newest one there is identical** — so a settings change mid-session (that day: integration 200 → 100) leaves a second file whose name says when. It is `settings.json` **with holes cut in it, not a list of fields to remember**: the whole `accessControl` section goes, and any property named `passwordHash` anywhere in the tree, and everything else is copied wholesale — a hand-picked list would have omitted the logger trigger settings, which are exactly what was missing. `SystemLogMirror` copies the day's `yyMMddHH.csv` log files in as `_log_*.csv`, re-copying whichever has grown (the live hour is still being appended to, so every copy but the last is partial; the last is taken in `MainViewModel.Dispose`) and opening with `FileShare.ReadWrite` because `SystemLogger` holds its own handle. Both are best-effort and log their own failure; both are named with a leading underscore and are rejected by `Recording.TryParse`, so the review tabs walk past them. `MainViewModel.CurrentSettings()` is the single definition of "the settings right now", shared by Save and the snapshot — the snapshot exists to be trusted months later, so it has to be the same object the Save button would write.

## `DiagnosticBundle` + `DiagnosticManifest` + `OesLoadProbe` + `DiagnosticsViewModel` + `DiagnosticsPanel`

**the one-click diagnostic bundle**, on the Logs tab and **deliberately ungated**: the person who can press it is the Operator on the phone, and a diagnostic an Operator cannot produce does not exist. Same split as the SECS tab and the recorder strip — it reads and copies, it changes nothing. It serves exactly two questions, the two that cannot be settled over a phone call: *it silently stopped measuring* and *the host says it never got that alarm*. Both are answered from four places nobody copies together — the data folder the operator chose, the logs and configuration under `%AppData%`, the SECS profile and traffic log, and one fact that lives nowhere at all until something probes for it. `ConfigSnapshot` / `SystemLogMirror` fixed the narrow version of this for a day folder; this is the same argument for a whole machine. Contents: 7 days of system + SECS log (the whole `Logs\` tree is ~800 KB for three months, so the window is free, and a test-mode session is routinely noticed the next day), today's ratio CSVs and `_config_*.json`, the SECS profiles, a redacted `settings.json` **and its `.bak-*` files** — which is why `ConfigSnapshot.RedactJsonText` exists: a backup written by an older build need not deserialise into `AppSettings` any more, and a redactor that throws on the file it was aimed at fails open. `OesLoadProbe` is `tools/check-oes-connect.ps1`'s sections 1–4 run **in-process** (files, VC++ runtime, PE bitness, `LoadLibraryEx` + the Win32 error `CheckHardwareDllAvailability` swallows) — the button's process is already in the app folder, under the operator's account, at the right bitness, which are that script's three preconditions. It deliberately skips the script's section 5: re-entering the native SDK to enumerate USB while the tool may be acquiring makes a diagnostic nobody dares press, so the device's live state answers that half instead. **The `.ps1` stays** — when the app will not start, it is the only one of the two that can run. **Two omissions are the whole design.** A recording over the cap is dropped *whole*, never shortened: the EMA, the EWMA variance and the σ/min slope are dt-bound, so a trimmed full-spectrum CSV re-baselines happily and answers wrongly with nothing in the file to say so. And the newest recording is usually the one the logger holds open — copied anyway (`FileShare.ReadWrite`, as `SystemLogMirror` does, because it is the file covering the problem) but marked `Truncated` via the same exclusive-open probe `DataRetentionService` uses. Both land in the manifest's **"NOT in this bundle"** section, which is why the manifest exists at all: one listing only what is present reads as complete whatever is missing. `README.txt` and `manifest.json` are rendered from one object, never assembled twice. The filename leads with the **machine name, not the serial** — a serial reads `TEST_MODE_SIMULATOR` in precisely the failure this is for, so it is evidence inside and never a label outside; the chamber code is appended only when set, so its absence says "no MES here". Runs on a worker thread with no cancel (a half-written bundle is rubbish; the question during the wait is "is it done", which progress answers), keeps the newest 5 bundles, and logs the path as `DiagnosticBundleCreated` because the Explorer window gets closed and "where is it" is always the next sentence. `DiagnosticBundleTests` pins the three negative facts plus the button itself; operator-facing docs are manual §6.12.1 and the rewritten postmortem §5.

## `DataRetentionSettings` + `DataRetentionService`

data-folder housekeeping, in this project (no NuGet change). **It compresses, it never deletes**: a day folder that ages past `ArchiveAfterDays` (30) becomes a sibling `{baseDir}\YYYYMM\DD.zip`, so every row stays recoverable with any unzip tool and the actual retention decision stays with whoever owns the data. Two rules, in order: age first (what an audit asks about), then `MaxTotalSizeGB` (20) as a safety net that keeps compressing into newer folders, oldest first, until the tree fits. Neither ever touches the newest `MinKeepDays` (2) days or a folder holding a file the logger has open (`MainViewModel.IsFileInUseByLogger`, plus an exclusive-open probe that also catches a CSV someone left open in Excel). **The removal order is the safety property**: probe locks → write `.zip.tmp` → verify the archive's entry list equals the folder's file list → rename into place → only then delete the originals; any failure leaves the folder exactly as it was. `MainViewModel` runs a pass 20 s after start-up and every 6 h on a worker thread (`_retentionRunning` suppresses overlap), logs every action, and exposes the Configuration-tab row (enable, days, cap, Compress now, status). `MainWindow.ShowDataFolderWarning` shows free-space / over-cap warnings when the app opens and closes — and only then, since a dialog that appears every time stops being read.

- **`Enabled` defaults to false, deliberately.** It shipped as true for exactly one development session, and launching the app once compressed three months of real data on the dev machine — an upgrade would do the same on a production tool, with months of days vanishing from the Recordings / Ratio Review lists (into archives, but still) that nobody asked to create. Warnings are issued whatever the switch says; only the compressing is opt-in. Restoring is `Expand-Archive` back into `DD\`, but don't rely on that being anyone's expectation.

## `RatioCsvLogger`

**independent of the intensity logger.** It used to open/close in lockstep with the threshold logger's save sessions, which tied the leak record to the raw-spectrum recorder; disarming that recorder — or simply running below its trigger threshold — silently threw away the leak history and left Ratio Review with nothing to replay. The two are not the same kind of data: a full-spectrum intensity row is ~22 KB (~400 MB/hour at 5 Hz), a ratio row ~200 B (~4 MB/hour), so the ratio CSV is cheap enough to always write. It now subscribes only to `LeakMonitorEngine.SampleProcessed`, opens lazily on the first frame after idle, and closes on `Stop()` — called from `MainViewModel` when acquisition stops and on Reset Run. A session crossing local midnight rolls into a new file so each day's rows land in that day's folder (which also bounds a continuously-acquiring file to one day). `Configure(LoggerSettings)` mirrors the intensity logger's base directory + file prefix (startup and every `ApplyAll`) so both recorders share one folder tree; that is now their only coupling. `UniquePath` appends `_N` if a same-second file exists, since the writer opens with `append:false` and two sessions can share a start second (a quick double Reset Run). A failed open sets `_openFailed` so a broken path is not retried once per frame. **Consequence:** the ratio file no longer shares a session timestamp with an intensity CSV, so `RecordingsViewModel` skips every non-`"OES1"` file at scan time — without that, each ratio file would create an empty `RecordingGroup` of its own in the Recordings list.
