# Leak engine

Line extraction, ratios, the Golden Run, thresholds and alarms, the plasma gate, process classes, ratio roles and the leak-rate calibration.

## Leak Monitor

an actinometry-based air-leak detector on its own tab. `LineIntensityExtractor` + `LineRegion` pull line intensities out of each `SpectrumSample` in one of three `LineExtractMode`s (`LineRegion.PeakSearchHalfWidthNm` re-centers the window on the actual peak each frame, so wavelength-calibration drift or a shifted band head doesn't corrupt the reading). `PeakHeight` and `Integral` subtract a linear continuum interpolated between two side windows; `Integral` is in **counts·nm** with fractional-pixel window edges, so it neither steps by a whole pixel when the peak search shifts the window nor depends on how finely the axis samples. **`RawMean` subtracts nothing and searches for nothing** — for a wavelength with no peak, where the two subtracting modes measure mostly their own baseline error: a convex continuum puts the interpolated line above the middle (systematically negative — measured −11.7 with 63 % of frames negative at 440.7 nm where the raw value is a stable 3745 ± 19), and the peak search on a monotonic slope pins the window to the edge of its search range every frame. `RatioDefinition.ValueHasPedestal` (a `RawMean` numerator, in either monitor mode — dividing by a reference scales the pedestal, it does not remove it) is the single predicate for everything that consequently changes: the Warn/Alarm **factors** are dropped in favour of the σ terms (1.2 × a pedestal is tens of σ — an alarm that looks armed and can never fire), the % -of-baseline display becomes a σ-score, the trend slope reads in σ/min, the leak-rate calibration fits the absolute rise Δ instead of the fractional one, and the ratio CSV names that column `_sigmaScore` rather than `_pctBaseline`. Raw readings carry no noise estimate at all (SNR **unknown**, not high — dividing a pedestal by the continuum σ reports 200 for a wavelength with no line on it), so the SNR gate stands down for them; in ratio mode it still gates the reference line, which does have one. `LeakMonitorEngine` divides signal lines by a reference line into ratios — the reference defaults to Ar 750.4 nm but is switchable per ratio from `ReferenceLineCatalog` (N₂ 337.1, N₂ 662.4, Hα 656.3, Ar 750.4, Ar 811.5). **The factory ratio set is what one machine's known-leak measurement selected, not the textbook assumption**: `R_N2Ar` (N₂ 337.1 `RawMean` / Ar 750.4, 33.8 σ), `R_NOAr` (NO 237, 18.3 σ — a second species, so an independent opinion), `R_N2357Ar` (N₂ 357.7 `PeakHeight`, 16.2 σ, so one ratio dropping to LowSignal can't make `RequireTwoForAlarm` unreachable), and `R_N2357Abs` — the same 357.7 line undivided, **shipped disabled**, whose only job is to be read beside `R_N2357Ar` to separate a chemistry change from the whole spectrum brightening. Absolute intensity doesn't return to baseline once a leak is closed (+7.6 % measured, with the Ar-normalized ratio back at +1 %), so armed by default it would park an untuned tool in Warning after every event. It replaced `R_O`/`R_OH`/`R_NO`/`R_Ar` (all over N₂ 337.1), where three of the four numerators measured 0.1–0.7 σ against the same leak that moved the *denominator* 33.8 σ. Factory Warn/Alarm factors are 1.05/1.12 (that machine's 2 % scatter); `RatioDefinition`'s class defaults stay 1.2/1.5 for hand-added ratios. Existing installs are not migrated — `CreateDefault()` only runs for a fresh `settings.json`; a Golden Run baseline only applies while everything that defines the monitored quantity still matches: the reference line it was divided by (`GoldenRunRatioBaseline.ReferenceLabel`, ratio mode only — an absolute baseline stores `""` so swapping an unused line can't invalidate it), the monitor mode (`.Mode`; a ratio and a line intensity are not the same quantity), and the extraction revision (`.ExtractionRevision`, checked only for ratios whose reading involves an `Integral`, whose unit changed to counts·nm — peak-height and raw baselines survive the upgrade). Each mismatch logs its own `LeakMonitorBaselineMismatch` reason. A capture is also rejected outright unless its mean clears `MinBaselineMeanToSigma` (10) σ and zero (`GoldenRunRatioUnstableBaseline`): thresholds, the % display and the leak-rate fit all divide by that mean, and a `−25 ± 95` baseline turns every one of them into the sign of the noise. `GoldenRun.Acquisition` records the integration time / averaging / correction switches / axis the capture ran under (`AcquisitionFingerprint`, fed in by `MainViewModel` via `ConfigureAcquisition` at start-up and on every Apply); a live mismatch surfaces on `LeakMonitorSnapshot.AcquisitionWarning`, in the Leak Monitor banner, and once in the log (`LeakMonitorAcquisitionMismatch`) — absolute-intensity readings scale with those settings, so changing the exposure silently re-scales every ratio against a baseline that no longer applies. The engine runs a per-ratio `RatioMonitor` (EMA + two-level threshold state machine + sustained-confirmation + latched alarm), and computes a composite `LeakAlarmLevel`. **`Acknowledge(user)` logs `LeakMonitorAcknowledged`** (who, which latched ratios were cleared, composite before → after) — without that entry the audit CSV showed an alarm ending by itself, which is what a real run produced: an `Alarm → Normal` at 21:10:37 with nothing to attribute it to. The one other place a latch clears is `ResetRuntimeState(clearAlarms: true, reason)`, which logs `LeakMonitorAlarmLatchCleared` naming the reason and the ratios; the invariant is not "only Acknowledge clears a latch" but "nothing clears one without an entry of its own". A call that finds nothing latched logs nothing, so the entry always means a human ended a confirmed alarm. `LeakMonitorViewModel.SetRole` carries the username for it. **Signal-quality gate:** `LineIntensityExtractor.Extract` returns a `LineMeasurement` (value + a local continuum-noise σ estimated from the baseline windows → SNR); when the signal or reference line falls below `RatioDefinition.MinSnr` (default 5) the ratio enters `RatioState.LowSignal` and is held out of the composite alarm (absolute mode judges **only** the monitored line — the reference takes no part in the reading, so letting its SNR veto would leave a strong line reading "low signal" for ever) — at low plasma intensity the ratio of two near-noise lines is meaningless however well it is smoothed. The Warn/Alarm thresholds also widen by the *larger* of the Golden-Run σ and the live EWMA σ, so a noisier-than-baseline ratio doesn't trip on its own jitter. The Leak Monitor panel shows each ratio's SNR and a "LOW SIGNAL" banner when any enabled ratio is below its floor. The **same SNR floor gates Golden Run capture**: a frame only feeds a ratio's baseline if its lines clear `MinSnr` (mirrors the runtime gate), and `FinalizeCapture` *rejects* a ratio's baseline outright when fewer than `MinBaselineAcceptFraction` (0.5) of its SNR-evaluable frames cleared the floor — so a near-noise line can't seed a baseline from a biased sliver of upward noise excursions (logged `GoldenRunRatioLowSnr` / explained in `ReportDroppedRatio`). **A capture that clears none of those gates is discarded outright** — `FinalizeCapture` returns before it stores the run, so an empty capture neither becomes the active baseline nor replaces a same-named run that is already working. Storing it (the old behaviour) took every ratio's baseline away at once and unpaired the bound calibration with it, on the strength of a window that measured nothing — usually just a trigger threshold set above the plasma, with the gate shut for the whole minute. The engine reports every capture on `GoldenRunCaptureFinished` (a `GoldenRunCaptureResult`: the run, `Accepted`, and the per-ratio rejection reasons — the same sentences the log carries); `GoldenRunCaptured` now fires **only for an accepted capture**, since a discarded one leaves nothing for `MainViewModel` to persist. `LeakMonitorViewModel` turns the result into a modal: Error for a discarded capture (naming the baseline left untouched), Warning listing the ratios that got no baseline when some did — a capture is a deliberate action the operator waited a minute for, and a silently partial one leaves ratios out of the composite alarm with no sign on screen. **A capture that would destroy baselines a same-named stored run still has is held unstored** (`NeedsConfirmation` + `Lost`): the VM merges that into one Yes/No dialog (what this capture missed *and* what replacing would cost — two halves of one sentence, and a second window saying it again is one that gets clicked away), then `ConfirmCapturedRun(run, keep)` either stores it or logs `GoldenRunCaptureDiscarded`. Only same-name overwrites are compared, because only they are irreversible; capturing under a new name leaves the old run selectable. A capture that loses nothing — the weekly re-baseline — is stored without asking, since a confirmation seen every time is one nobody reads. The dialog also names the run it would replace *before* the minute is spent, since it offers the current name by default. **Alarms don't escalate or latch during a capture** (`RatioMonitor.SuppressLatch`, `wasCapturing`): the window is judged against the baseline being replaced, so after a recipe change a deviation is certain and means nothing — an acknowledge-me alarm from a routine re-baseline is how operators learn to acknowledge without reading. `GoldenRunCaptureDeviation` logs where each ratio actually sat relative to that outgoing baseline (σ for pedestal values, % otherwise) — stated, not judged, because the same number is noise after a recipe change and the whole story when re-capturing the same recipe. A "Golden Run" captures the leak-free baseline (mean/σ per ratio) and is persisted to `settings.json` the moment it completes. `LeakMonitorViewModel` / `LeakMonitorPanel` show the per-ratio rows, the % -of-baseline trend chart, and the capture / acknowledge commands. `SpectralLineCatalog` is the static reference line table. Engine alarm transitions and Golden Run captures bridge into `SystemLogger`. `RatioCsvLogger` writes the ratio trend (raw ratio + % of baseline / σ-score per ratio) — each column headed `{DisplayName} [{key}]`, since the key is a random GUID stub (`RatioEditViewModel.GenerateKey`) that deliberately never changes so baselines and calibrations survive a rename, which also makes it meaningless to anyone opening the CSV without the `settings.json` that produced it; `RatioCsvReader.SplitColumn` recovers both, bare-key files (everything written before this) still parse and just have no label — to `{prefix}_Ratio_{MMddHHmmss}[_N].csv` under the same `DataDirectory\YYYYMM\DD` folder — **its own recorder, deliberately independent of the threshold logger** (see `RatioCsvLogger` in `recordings-and-data.md`). All of this lives in this project, not the NuGets.

## `PlasmaGate`

the plasma-present gate for **absolute-intensity** ratios, mirroring `DualIntensityLogger.SampleTriggerMetric` exactly (nearest bin within `WavelengthToleranceNm` / frame percentile / brightest monitored wavelength, per `TriggerMode`) against `SaveStartThresholdIntensity`, so the gate and the recorder judge brightness by one measurement — a third way to measure it would guarantee the two eventually disagree. **They share the metric and the threshold, not the state machine**: the gate is a bare per-frame `metric > Threshold`, while the recorder confirms for `StartConfirmSeconds`, holds through `StopConfirmSeconds`, and (Core 0.1.8) back-fills. So a recording carries gate-closed rows at both ends — the `PreTriggerSeconds` head and the stop-confirm tail — and "the gate is open" is not the same claim as "this row is in a file". `MainViewModel` feeds it in via `LeakMonitorEngine.ConfigureTrigger(LoggerSettings)` at construction and on every `ApplyAll` — **hot-applied**, unlike a Ratio Setup edit, because it is a logger setting and a staged one would leave the two disagreeing for the rest of the run. **Both modes gate on it.** Ratio-mode entries additionally require their own reference line (`den > 0 && den > floor`) because they divide by it — **the floor is per reference line**, keyed by `LineRegion.MeasurementKey` (the string form of the `MeasuresSameAs` fingerprint) and stored in `GoldenRun.PlasmaFloors`. It was one pooled number per run, which only holds while every ratio shares a reference: mix an Ar 811.5 reference with an N₂ 662.4 one and the pooled 20 % lands *above* the faint line's normal level, so that ratio reads "plasma off" every frame and goes silently dark while the bright one is left effectively ungated. Keying on the full fingerprint rather than the label is deliberate — two ratios can read `Ar 750.4` as `PeakHeight` counts and as an `Integral` in counts·nm, and pooling those is the same mixing one scale down; too-fine a key merely stops the pooling, too-coarse is a wrong number. `GoldenRun.PlasmaPresentFloor` survives as the fallback for runs captured before this and is no longer written, so an upgrade changes nothing until the next capture. `_floorByRatio` is resolved in `ApplyGoldenRun` (the only place either `_defs` or the active run changes), not per frame — but that check is not a plasma test: a frame the spectrometer returns *blank* still carries ~75 counts at the reference wavelength, clearing `> 0` and clearing a floor derived from a capture those same blank frames contaminated. A real run produced 20 such frames in 13 minutes; **one** of them inside a Golden Run capture pushed that ratio's baseline to `0.02512 ± 0.05914` (σ 2.4× the mean) so `MinBaselineMeanToSigma` rejected it — with the gate the same window gives `0.02064 ± 0.00073`. `TrackGateDropouts` counts brief closures sandwiched between good frames and logs `SpectrumFrameDropout` (first immediately, then a running total at most every 5 min): the gate discards them silently, and an instrument fault you can't measure is one you can't fix — this is the number that says whether `AcquireMode = Oneshot` helped. A closure longer than `MaxDropoutSeconds` (1 s) is the plasma genuinely going off, not a dropout, and isn't counted. Absolute mode never had the reference to fall back on: it doesn't divide by it, so the reference needn't exist — and a line that isn't there extracts to continuum noise about zero, making `den > 0` a coin flip that decided whether the frame was evaluated (32 % of rows blank in a real run), while a reference on a *convex* continuum extracts systematically negative (a linear baseline drawn between the two side windows lies above it) and the ratio never evaluated a single frame. An unusable / unmeasurable gate leaves absolute ratios **ungated** and logs `LeakMonitorPlasmaGateUnavailable` once — "we can't tell" is not "plasma off", and a silently dead ratio is the failure this replaced.

## `ProcessClassifier` (+ `RatioDefinition.ProcessClass`, `RatioState.NotApplicable`)

**names the process a plasma step is running, from the spectrum alone**, so a chamber that interleaves recipes can scope each ratio to the one it measures. Disabled by default (`LeakMonitorSettings.ProcessClassifier.Enabled`), and an empty `ProcessClass` applies to every step, so an unconfigured install is unchanged down to the ratio CSV's columns. It exists because the measured tool cycles `B(156 s) → (A → C) × N` against a single `ActiveGoldenRun`: judging every step against one baseline compares three different plasmas, and the argon reference the factory ratio set divides by exists in only one of the three. The rules are an ordered decision list of line *ratios* (absolute levels move ten-fold between these processes and 30 % within one batch as the viewport fouls; a ratio of two lines in one frame does not). **The state machine is per step, in the engine**: a step runs between transitions of a *boundary* threshold — the lowest level any class runs at, not the class's own, because the class is not known until several frames in and a boundary tuned to the brightest class would never see a dim class's step begin, so it could never be classified and would stay dark for ever (the 2026-08-19 failure from the other direction). The verdict is taken once at `DecideAfterFrames` (3, ≈ 6 s — a step's first 10 s scatter by 8.7 %, its 10–30 s by 1.6 %) and then **locked**: a plasma step does not change process half way through. A step no rule matched is `Unknown` and nothing is judged during it. Out of its class an entry reads `NotApplicable` — a third quiet state beside `Disabled` (someone decided) and `NoPlasma` (idle or a fault), because those call for three different reactions — its smoothing is dropped so the next step of its own class cannot inherit a reading of a different plasma, and **its latch survives**, since a confirmed leak does not end when the tool moves on. `PlasmaGate.TriggerMetric` is public so the one brightness measurement can be compared to a per-class threshold (`ProcessClassDefinition.PlasmaThreshold`) rather than a second gate measuring brightness its own way. Every rule's measured value is recorded — snapshot, system log, and trailing `ProcessClass,ProcessStep,disc:*` columns in the ratio CSV — because a step landing near a threshold is only diagnosable from the number. `RatioEditViewModel.ToDefinition()` must carry `ProcessClass`: without it the first Save on the Ratio Setup tab un-scopes every ratio at once with nothing on screen to say so (`ProcessClassTests` pins that, plus the latch and the boundary threshold). Design, site configuration and the measured numbers: `docs/leak-monitor-plan-zh-TW.md`.

## `RatioDefinition.Role` (`RatioRole.Alarm` / `TrendOnly` / `Guard`, + `RatioState.Observing`)

**what an entry is for**, orthogonal to `MonitorMode`, which is what it measures. Defaults to `Alarm`, so an existing configuration is unchanged. `TrendOnly` is for an indicator whose cross-batch reproducibility cannot carry a threshold — on the measured tool two of the three processes reach mean/σ of 7.3 and 6.5 against the engine's own baseline-acceptance floor of 10, and a full-spectrum sweep found nothing better, so an alarm there is one operators learn to ignore, which costs more than the alarm is worth; the value still reaches the ratio CSV and the batch record, where the trend is read off it. `Guard` is the same machinery for the opposite reason: a control quantity (`CO 607.9 / Ar 811.5` on that tool) whose job is to be read *beside* an alarm, separating "the process gas moved" from "there is a leak". Both stop in `RatioMonitor.Update` **after the smoothing and before the thresholds**, so changing a role changes what is judged and not what is recorded; both are excluded from `ComputeOverall` and from the leak-rate fusion, and neither latches. They read `Observing` — deliberately not `Normal` (which claims a judgement nobody made) and not `NoBaseline` (for these, not having one is the expected condition, not a fault), which is also why `ResetRuntime` idles them at `NoPlasma`. `LeakAlarmEventArgs.Guards` carries the guard rows **as they read on the frame that caused the transition** — the question "leak, or did the gas move?" is asked about that moment and is recoverable only if written down then — and `MainViewModel.FormatGuards` puts value and deviation-from-baseline into the `LeakMonitorState` entry, since whoever opens the log later will not have the baseline. **Reported, never used to suppress**: a guard's own scatter is a few per cent, and one given a veto eventually vetoes a real leak. `RatioEditViewModel.ToDefinition()` must carry `Role` for the same reason it must carry `ProcessClass`.

## `LeakRateEstimator` + `LeakCalibrationViewModel` + `LeakCalibrationPanel` + `CalibrationPointDialog`

Leak Calibration tab: a staged wizard that turns the qualitative ratio rise into a **quantitative leak rate** (mbar·L/s). The operator picks a baseline (Golden Run), then captures one calibration point per calibrated-leak element: `LeakMonitorEngine.BeginCalibrationPointCapture(leakRate, label, seconds)` averages each ratio's fractional rise `x = rawRatio/baselineMean − 1` over a window (reusing the Golden Run capture machinery) and raises `CalibrationPointCaptured`. Save calls `LeakRateEstimator.FitAll` — a through-origin weighted least-squares sensitivity `x ≈ s·Q` per ratio — and persists a `LeakCalibration` (points + per-ratio `RatioSensitivity`, bound to the baseline and reference labels) into `LeakMonitorSettings.Calibrations` in `settings.json`, gated to Engineer+. At runtime (P2) the engine holds a `LeakRateEstimator` built from the active calibration and computes a fused estimate every frame into `LeakMonitorSnapshot.LeakRate`: each ratio's `xᵢ` comes from its % -of-baseline and `σ_xᵢ` from a per-ratio EWMA variance (`RatioMonitor._emaVar`); `Estimate` inverts each to `Qᵢ = xᵢ/sᵢ` and fuses them by inverse variance into `Q̂ ± σ_Q` with a cross-ratio consistency confidence and an out-of-calibrated-range flag. The Leak Monitor panel shows it as a readout under the status banner ("Leak rate ≈ Q̂ ± σ · NN% confidence", or `extrapolated` / `not calibrated`). Saving a calibration calls `engine.ReloadCalibration()` so it activates immediately (no acquisition restart, unlike a ratio-set change). Pure math core (`LeakRateEstimator`) has no engine/UI deps. **The calibrated leak must be air** (or match the leak being detected) — an inert leak won't raise O/OH/NO. The estimate is also logged to the Ratio CSV (`LeakRate,LeakRateSigma` columns) and replayable in Ratio Review's "Leak rate" mode (P3). A calibration only applies while the active Golden Run matches the baseline it was captured against (`LeakMonitorSnapshot.CalibrationStatus`: `NotCalibrated` / `Active` / `BaselineMismatch`); switching baselines suspends estimation rather than silently mis-scaling it, and status transitions are logged (`LeakCalibrationActive` / `LeakCalibrationSuspended` / `LeakCalibrationCleared`). Every baseline change routes through `ApplyGoldenRun` → `BuildEstimator` to re-evaluate validity (P4). Switching (or capturing) the active Golden Run also **auto-selects the calibration bound to it** (`AutoPairCalibration` — the most recent `LeakCalibration` whose `GoldenRunName` matches, or none), so the active calibration follows the recipe and a recipe change doesn't leave a stale `BaselineMismatch`; the pairing is persisted (`SelectGoldenRun` raises `ConfigurationChanged`, capture persists on `GoldenRunCaptured`). Full design + math: `docs/leak-rate-calibration.md` (P0–P4 complete: model, estimator, wizard, runtime display, CSV logging/review, validity gating).
