# Replay

Playing a recorded full-spectrum CSV through the app in test mode.

## `SpectrumReplaySource` + `ReplayViewModel` + `ReplayPanel`

**Replay tab: recorded-spectrum playback for algorithm validation.** In test mode the spectrum normally comes from the SDK's synthetic generator (`OesDevice.InitializeTestData`: `1000 + 500·sin(i·0.01) + noise`, a fixed 1000-point axis). This plays a recorded full-spectrum CSV instead — the wide format `IntensityCsvWriter` writes (`WaveLength,<wl…>` header, then `HH:mm:ss.fff,<intensity…>` rows), parsed with `RecordingCsvParser.ReadFull`, which also gives per-frame `ElapsedSec`. Engineer-gated tab with Choose CSV… / Play / Pause / Restart / Stop, a 1× / 5× / 20× speed, progress + frame counters, and a preview of the frame being delivered. The path persists as `AppSettings.SimulationCsvPath` (key name kept) and the rate as `AppSettings.ReplaySpeed`; a missing/unparseable file leaves test mode synthetic.

- **Real axis, not the synthetic one.** Frames are delivered on the *recording's* wavelength axis. Its predecessor (`SpectrumSimulationSource`, removed) resampled onto the ≈200–800 nm / 1000-point test-mode axis because all it could do was overwrite the incoming frame's fixed-length intensity array — Ar 811.5 nm was dropped outright and everything finer than the device pixel spacing was interpolated away, so ratios, σ, SNR and leak rates all differed from what the same data gives on hardware. Replacing the frame outright needs the `DeviceViewModel.SpectrumMapper` seam (`Wpf 0.1.12`), which is why this is not a within-app-only change.
- **Virtual clock.** Playback starts when Play is pressed and advances by the recording's own `ElapsedSec`, so frame timestamps are `playStart + elapsed`: the produced CSVs land in today's folder while the engine sees exactly the intervals the plasma was measured at — the EMA `α = 1 − exp(−dt/τ)`, the sustained-confirmation seconds, the σ/min slope and the leak-rate EWMA variance are all dt-bound. Speed scales the *wall* time only, so 20× is behaviourally identical, just faster. Pausing freezes both clocks and leaves no gap in the timestamps. `MaxFramesPerTick` (400) bounds one tick's catch-up burst and re-anchors the clock to what was actually delivered; the shortfall surfaces as `ReplayStatus.AchievedSpeed` and a warning line rather than silently running fast.
- **Plays once.** The recording is played through exactly once and then holds on its last frame (`ReplayState.Finished`) — deliberately not looping, which stitched the file's end to its beginning and every baseline and alarm downstream read that as a real step change. Finishing keeps the stream (`Handled = true`, no frames) so the synthetic spectrum cannot resume into the recorders behind the operator's back. **The finish is reported on `ReplayTick.Finished`, not as an event raised inside `Advance`** — an event fired before the caller had fanned that tick's frames out, so the UI-thread teardown closed the replay's recorder session first and the run's last frames opened a session of their own, under the ordinary prefix once the teardown had restored it. The first real test run produced exactly that: three stray one-row files, two of them `P_Ratio_*` holding a replayed frame. `EndReplayOutput` also closes the recorders again after reconfiguring them, so a frame landing between the two calls cannot leave a session open.
- **Test mode is a precondition, now enforced.** `SpectrumReplaySource.Advance` refuses a non-test frame (`!raw.IsTestMode → default`), so with a spectrometer attached Play delivered nothing — while the tab said `PLAYING`, the progress bar sat at 0, and `BeginReplayOutput` had already switched both recorders to the `SIM` prefix. A real session did exactly this and filed 450 KB of measured spectra as `SIMP_*`: the safeguard inverted, measurement labelled as replay. Three guards now: `ReplayViewModel.RealHardwareAttached` (fed by `MainViewModel.UpdateReplayAvailability` from `DeviceViewModel.IsConnected`/`IsTestMode`) disables Play and shows why; `Play()` re-checks before raising `ReplayStarting`, since starting is what moves the recorders; and `MapDeviceFrame` calls `AbortReplayForHardware()` on the first hardware frame that arrives while `_replayOutputActive`, which stops the replay, restores the prefix and logs `ReplayAbortedByHardware` — the connect can happen mid-run, after the button check has passed.
- **Fan-out.** `MainViewModel` installs `MapDeviceFrame` as the device's `SpectrumMapper`; it calls `_replay.Advance(raw)`, fans every due frame out itself (`FanOutSpectrum` → intensity logger, leak engine, `WavelengthTrend`) since a fast-forwarding tick owes them several frames while the device wants one to draw, and returns the newest for the plot. `OnDeviceSpectrum` (the `SpectrumAvailable` handler, still the whole path when no replay runs) skips the frame when `_replayHandledFrame[slot]` says the mapper already dealt with it. Real-hardware frames (`IsTestMode == false`) are never replaced.
- **Replayed output is marked.** While a replay runs both recorders are reconfigured with the `SIM` prefix (`MainViewModel.ConfigureRecorderOutput`, `ReplayPrefixMarker`), so files are `SIMP_OES1_…` / `SIMP_Ratio_…` — still `{prefix}_{tag}_{MMddHHmmss}`, so `Recording.TryParse` and both review tabs list them as usual, but replayed data is never mistaken for measurement. Both recorders are force-closed on start and on end, since a writer captures the prefix when its session opens. `ApplyAll` re-imposes the marker, because `Logger.ApplyCommand` pushes the unmarked prefix straight into the intensity logger.
- **Ending a replay resets the monitors.** `EndReplayOutput` calls `LeakMonitorEngine.ResetRuntimeState(clearAlarms: true, reason)` **before** it closes the recorders and restores the prefix. The replay's last frames otherwise leave an EMA, a confirmation timer and a latched alarm behind, and the first synthetic frame after teardown opens a session under the ordinary prefix and writes them into it — measured on 2026-08-20 as `P_Ratio_0820153410.csv`, a production filename whose first row carries the recording's own σ-scores and `OverallState=Alarm` three quarters of a minute after the recording ended, plus a `LeakMonitorState Idle → Alarm` in the audit log that no chamber caused. Clearing the latch is deliberate: an alarm confirmed against a recording is not a fact about the chamber, and carrying it live would ask an operator to acknowledge something that never happened. `ReplayEndResetTests` covers both that and the Monitor-tab Reset, which still leaves a confirmed alarm latched.
- **Alarms.** `LeakMonitorSettings.SuppressAlarmsInTestMode` (still true by default) is exposed as a checkbox here, because replaying a real recording is precisely the case where the alarm transitions are the thing being checked. **The switch is not scoped to the replay** — it governs every test-mode frame, so synthetic frames arriving after a replay ends are judged too (which is how the 2026-08-20 alarm above reached the log at all). `LeakMonitorViewModel.SetTestModeContext` keeps the tab's banner honest about both halves — which spectra, and whether alarms are live.
- **Expect an acquisition mismatch.** The CSV does not carry the exposure it was recorded at, so replayed frames carry the *device's* current acquisition metadata and a Golden Run captured live will report `LeakMonitorAcquisitionMismatch`. Capture a baseline from the replay itself.
