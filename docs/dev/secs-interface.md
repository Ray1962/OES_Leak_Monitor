# SECS/GEM equipment interface

The OES as SECS equipment towards the fab host (the FDC on site): profile stamping, bindings, alarms, events, slot VIDs, the traffic log.

## SECS/GEM equipment interface

lets a fab host (MES) connect over HSMS and read the leak monitor's state, receive leak alarms, and be told when acquisition starts or an operator acknowledges an alarm. Design + field tables: `docs/secs-integration.md`; wire semantics: `docs/Satellite_SECS_Specification_v2.md` (`ss=27`). The protocol itself is the `Aqusen.Secs` NuGet; this project supplies the values and the policy.

- `SecsBridge` — owns the `EquipmentSimulator`, registers the `SvBindings`, and pushes alarms/events. **It reads, it does not compute.** Every binding is invoked by the library on the requesting thread — once per S1F3, once per trace sample, several at a time — so the last `LeakMonitorSnapshot` is held as one volatile reference to an immutable object and the bindings do nothing but read a field and convert it. If a number is not already in the snapshot it does not belong in this class; that is why VID 021–023 became snapshot fields (`PlasmaPresent`, `PlasmaGateAvailable`, `DropoutCount`) instead of being re-derived, and why VID 027–029 (the process class) needed a new `ProcessClassState` on the snapshot: `ProcessClass` is empty for three different reasons — no classifier, no step, verdict not taken — and only the engine can tell them apart, so a host reading the name alone learns nothing. Sends are chained through `Enqueue` so an alarm's set and clear cannot arrive out of order — a host that receives them reversed is left holding an alarm that ended.
- `SecsChamberCoding` + `SecsProfileTemplate` — the profile is a site-editable JSON in `{ConfigDirectory}\profiles\`, written from the built-in template on first run and carrying `cc = 00`. At start-up the configured chamber code is stamped into every `svid`/`alid`/`ceid` and the result is written to `profiles\.effective\` and loaded from there. Stamping **validates**: wrong digit count, `ss ≠ 27` or `aa ≠ 00` refuses to start rather than serving ids belonging to another sensor type. `cc = 00` is not a chamber, so an unstamped profile can never be mistaken for a stamped one. The two paths are printed into the traffic log because field staff have to find them without a developer. **An existing profile is never overwritten** — it may carry site edits — which means a status variable added by a later build reaches no machine that has ever started the interface, and the library only checks the other direction (a profile naming a binding nobody registered fails by name at start-up). `SecsBridge.BindsNotInProfile` closes that half: it reports what this build can serve and the profile never asks for, into the traffic log and once as `SecsProfileMissingBinds` — Information, because a site that deleted a status variable deleted it. `SecsProfileTests` pins the shipped template against `SecsBridge.SuppliedBindNames` in both directions, so a new binding cannot ship without its profile row. The way those rows *do* reach an existing machine is the SECS tab's **Add missing rows** (Engineer+, `SecsProfileRows`): it appends what the template has and the site profile lacks across all four sections — status variables by `bind`, events by CEID, alarms by ALID, remote commands by name — after copying the file to `{profile}.bak-{yyyyMMddHHmmss}`, and logs `SecsProfileRowsAdded`. It **edits text, not a parsed document**: re-serialising would lose the site's comments and layout, and the promise is that no existing line changes, so new rows go on new lines after the last element with the separating comma leading the first one (an empty `{}`/`[]` is the one thing that has to be opened up), in the file's own line ending and BOM, and the result is re-parsed before it is written. A row whose SVID the site already uses for something else is refused and listed, the rest go in. It also restores rows the site deleted — the file cannot tell "deleted on purpose" from "written by an older build" — which is why it is a button and never done at start-up. Takes effect at the next interface start. `SecsProfileRowsTests` covers the text edits against the real 2026-09-04 template (`SecsProfileFixtures`); `SecsProfileRowsWireTests` shows that profile answering `TOOL_EVENT` HCACK 1 before and not after.
- `SecsSettings` (in `settings.json` under `secs`, **`Enabled` false by default** — an upgrade opens no port until asked) + `SecsViewModel` / `SecsPanel`. Three reporting switches: alarms, events, and *report test/replay data too* (off by default — synthetic and replayed frames are not measurements, and an alarm arriving at the host carries no marking that says so; VID 016 reports the truth either way). Switching reporting off never hides anything from a status query.
- **Alarms** are ALID `1{cc}27nnn`: 001/002 leak warning/alarm from the composite level, plus 012–014 (connection lost / acquisition error / data write failure) added to the specification's reserved range. The fault three are **not** suppressed in test mode — a spectrometer off the bus is a fact about the tool whatever the frames contain — and 012 is a *transition*, not a state, so launching disconnected is not a fault. **VIDs 030–032** read the engine's published `ToolEventStatus`, not the snapshot — see `tool-events-and-eap.md`. **Events** are CEID 502/507/508/509 — 507 is the slot-identity change, see the ratio slot section below — wired to `LeakMonitorEngine.Acknowledged` (added for this; it fires on exactly the condition that writes the `LeakMonitorAcknowledged` audit entry) and the `IsAcquiring` transition `MainViewModel` already watches.
- **The traffic list's follow-the-newest-line scroll is posted, never done inside `CollectionChanged`** (`SecsPanel.FollowTraffic`). The panel subscribes to `SecsViewModel.Traffic` when its DataContext arrives, which is before the ListBox's own collection view does, so it hears about a new line while the item generator still counts one fewer. `ScrollIntoView` forces a layout pass; with one line at a time nothing is waiting to be laid out and it gets away with it, but a message and its reply are logged in the same millisecond — the first leaves the list dirty, the pass really runs on the second, and WPF throws `ItemsControl is inconsistent with its items source` on the dispatcher with nothing to catch it. On 2026-10-13 that ended the process three times against `Test_SECS`, each at the first `S1F1` a host sent with the tab open; nothing in it was specific to that host. The cause was read off the Windows event log (`.NET Runtime` id 1026) — the app's own logs stop one line short and say nothing. `Dispatcher.BeginInvoke` at `Background` lets the view and generator finish first, and `_scrollPending` makes a burst scroll once. `SecsPanelTests` reproduces it — the panel in an unselected tab as `MainWindow` hosts it, lines added in pairs, and few enough start-up lines that a new one lands inside the viewport (appended far below the realized range, nothing is invalidated and the test passes for the wrong reason) — and also requires the newest line to end up on screen, so "fixed by no longer following" cannot pass. It is the one test here that opens a window.
- **Ratio slot VIDs 101–400** (offsets 01–25, `oes.slot{N}.{field}`) and **CEID 507**. Slot N is row N of Ratio Setup. The engine publishes an immutable `RatioSlotTable` (wavelength-corrected lines, species via `WavelengthCalibration`'s alias map, `ValueHasPedestal`) at construction and on every `ReloadRatios`, and raises `SlotIdentityChanged` only when offsets 16–25 of the ten slots differ from the previous table — a threshold or smoothing edit does not, and `ProcessClass`/`Role` are not in it because no offset carries them. `SecsBridge` holds the table as a volatile reference like `ToolEventStatus`, so identity answers with no frame at all; offsets 01–15 find the last snapshot's row **by the slot's key, never by position**, because after a reorder the snapshot in hand still lists the old order. Nothing to read goes out as 0 / "" (never NaN); an enabled slot with no row reads state 3, a disabled or empty one 6. The 25 offsets are defined once, in `SecsRatioSlots.Fields`, which both the template's 250 generated rows and the bindings read. Design and field table: `docs/secs-integration.md` §5.3.
- `SecsLogFile` — every message in and out, to `Log\secs_YYYYMMDD.log`, day-rolled and pruned. Deliberately not the audit CSV: thousands of lines an hour would bury it, and acceptance asks for this trace.
- **ALID goes out as ASCII** (`<A[8] "10227002">`), which the Satellite specification uses throughout. `Aqusen.Secs 0.5.0` only sent U4, so 0.6.0 added `GemOptions.AlarmIdFormat` (default still U4) and made `SecsItems` parse an inbound ASCII id — a host disabling an alarm by the id it was announced has to reach the same alarm.
