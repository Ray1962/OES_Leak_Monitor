# NuGet packages

The local feed, the four in-house packages, what each upgrade changed for this app, and how a new `Aqusen.Secs` reaches it.

## NuGet feed prerequisite

`nuget.config` pins a local feed at `C:\Users\infor\source\repos\Ray1962\LocalPackages` and clears default sources before adding nuget.org. Restore will fail if the three `Aqst.*` nupkgs are not present there at (at least) the pinned versions:

| Package | Pinned | Built from |
|---|---|---|
| `Aqst.OesApp.Core` | 0.1.10 | `Ray1962/DualOes_PlasmaMonitor` — `dotnet pack DualOes_PlasmaMonitor.sln -c Release -p:Platform=x64` |
| `Aqst.OesApp.Wpf` | 0.1.16 | same solution, same command |
| `Aqst.OesSpectrometer` | 0.6.2 | a **different** repo, `Ray1962/Aqst.OesSpectrometer` — the hardware SDK, not the app framework |
| `Aqusen.Secs` | 0.8.0 | a **third** repo, `Ray1962/Test_SECS` — the SECS/GEM library (see its `整合指南.md`). Packed with `dotnet pack src/Aqusen.Secs/Aqusen.Secs.csproj -c Release -o nupkgs`, then the nupkg is copied into `LocalPackages`. 0.7.0 adds `EquipmentSimulator.RemoteCommandHandler`, which is how `TOOL_EVENT` reaches this app — 0.6.0 answered every S2F41 itself; 0.8.0 adds `GemHost.QueryStatusAsync` (S1F3 that returns the S1F4) and `IDeviceProfile.PredefinedReports`/`PredefinedEventLinks`, which `EapSecsLink` and its test EAP need |

`nuget.config` also lists a second local source, `aqusen`, pointing at `Test_SECS\nupkgs`. Both on purpose: `local-aqst` is what makes a build reproducible on a machine with no `Test_SECS` checkout, `aqusen` is what picks up a fresh pack during development without a copy step. `Secs4Net` 2.4.4 comes from nuget.org (via `Aqusen.Secs`, and referenced directly for `SecsGemOptions`).

The versions above are the ones in `OES_Leak_Monitor.csproj`; treat the csproj as the source of truth and update this table when it moves. Bumping `Aqst.OesApp.*` means editing `<Version>` in that library's csproj, re-packing (the `<PackageOutputPath>` writes straight into the local feed), then bumping the `<PackageReference>` here — and in `DualOes_PlasmaMonitor`'s own app and `template/`, which pin the same packages.

`0.4.6` of the SDK is what supplied `OesAcquireMode` / `OesAverageMode`; it also stopped opting into `UAI_BackgroundRemove` implicitly, though `DeviceViewModel` still passes `EnableBackgroundRemove = true`, so this app's behaviour is unchanged.

`0.5.0` of the SDK renamed `OesAcquireMode.HardwareAverage` → `HWAvg` (and `MeasurementMode.Normal` → `Intensity`, `DeviceConnectionStatus.TestMode` → `Simulating`) **with no alias**, plus `SpectrumSample.IsTestMode` → `IsSimulated`. Two places in this app hold the old spelling as text and must keep reading it: `settings.json` (`"acquireMode": "HardwareAverage"`) — `SettingsService` registers Core 0.1.10's `OesSdkEnumJsonConverter` **before** `JsonStringEnumConverter`, without which `Load()` throws, falls back to defaults and the next Save wipes the site configuration — and every baseline / sidecar `AcquisitionFingerprint.AcquireMode`, which `Differences()` compares through `OesSdkEnumJsonConverter.CanonicalName` so an old baseline does not report `acquire mode HardwareAverage → HWAvg` on every frame. Both have tests (`SettingsSavedBeforeSdk050_StillLoad`, `AcquireModeRecordedBeforeSdk050_IsNotAChange`). `DeviceSettings.ForceTestMode`, `DeviceViewModel.IsTestMode`, the snapshot `TestMode`, `SuppressAlarmsInTestMode` and the `oes.testMode` SECS binding are this app's / the framework's own names and were deliberately left alone.

`0.6.0` of the SDK splits `IOesSpectrometer` into three contracts and obsoletes the synchronous acquisition pair; neither reaches this app, which holds the concrete `OesSpectrometer` (it implements all three) and never called that pair. It renames no enum, so nothing persisted changes. `0.6.1` fixes a race found on a real JY70 — a stop could return while its acquisition was still unwinding, and a start straight after it put two tasks on one connection, the older silently swallowing the new sequence's results; a start now waits for the connection. This host never starts right after stopping, so it never hit it. `0.6.2` is the same code with one log line demoted.

`Core 0.1.4` fixes the intensity logger's silent data loss on a mid-session wavelength-axis change. `IntensityCsvWriter.WriteRow` now takes the frame's own axis (`WriteRow(timestamp, wavelengths, intensities)`) and returns a `RowWriteResult`; when the axis differs from the one the header was written from it closes the file and continues into the next rotation file (summary companion included) carrying the new axis. Previously such rows were dropped with no signal at all, so the session stayed in `Saving` with a CSV that never gained another row. `DualIntensityLogger` surfaces it as the new `FileRolled` event (`FileRollReason.SpectrumAxisChanged` / `RowLimit`), which `MainViewModel.OnIntensityFileRolled` logs — Warning for an axis change, since it means an acquisition parameter was reapplied mid-save and any Golden Run from the old exposure no longer applies. `Wpf 0.1.8` is only a re-pack against the new Core.

`Core 0.1.7` puts the **`Description` column into the system-log CSV**. Every entry had carried one from the beginning — it is the sentence saying what happened and what to do — and `SystemLogger.FormatEntry` simply never wrote it, so the file recorded that something called `Device_RuntimeError` had occurred and nothing at all about the error. It survived only in the in-memory ring the Logs tab renders from, i.e. until the app closed, which is backwards: the file is what gets read after something has already gone wrong. The column sits after `Condition`; `SystemLogger.ResolveLogFilePath` sends this run to `{stem}_1.csv` when the hour's file was written by a build with a different header, so no file ever mixes column counts. `Wpf 0.1.11` is only a re-pack against the new Core.

`Wpf 0.1.12` adds **`DeviceViewModel.SpectrumMapper`** — an optional `Func<SpectrumSample, SpectrumSample>` applied in `OnSpectrumAvailable` before *both* the `SpectrumAvailable` invoke and the `UpdatePlot` dispatch, so returning a different sample replaces the frame for every consumer including the device's own live plot. It exists because a frame's arrays are fixed-length and `init`-only: mutating the incoming frame (the previous trick) could substitute intensities but never the wavelength axis, which is what recorded-spectrum replay needs. Null by default, so a host that doesn't set it is unaffected; it runs on the SDK callback thread, and a mapper that throws is ignored in favour of the original frame.

`Wpf 0.1.13` makes a **test-mode fallback say so**. The SDK reports one as a *successful* connect (`SetupTestMode()` returns true), so `Device_Connect` was logged as `ok` at Information and the one string that says what happened — `OesDeviceInfo.LastConnectionResult`, e.g. `"No OES hardware devices found - test mode activated"` or `"UserApplication.dll load failed at …"` — never left the SDK: `DeviceViewModel` did not expose it and no `ILogger` was passed to `Spectrometer`, so the SDK's own warnings went nowhere either. Diagnosing the 2026-08-17 fab PC needed a separate script (`tools/check-oes-connect.ps1`) purely to recover that sentence. `ApplyConnectResult` now sets `LastConnectionResult` / `ResolvedDllPath` (both public, both raising `PropertyChanged`), puts the reason in `StatusMessage`, and logs one `Device_TestModeFallback` **Warning** carrying it plus `ForceTestMode` and `DllAvailable`. `DevicePanel`'s footer shows `Test Mode` in red with the reason on the tooltip. `LogDeviceConnection` is untouched, so Core stays at 0.1.7.

`Core 0.1.8` **back-fills the frames from before the save trigger confirmed**, and it is on without anyone setting anything: the buffer window is `max(StartConfirmSeconds, PreTriggerSeconds)` and the new `PreTriggerSeconds` defaults to 0, so the confirmation window alone is already back-filled. Recordings therefore start earlier than they did under 0.1.7 — at the default 2 s / 200 ms, about 11 extra frames at the head — and each file is named from its own first row rather than from the moment the trigger confirmed. Worth knowing here specifically, because baselines are built from these recordings: the added head is below the trigger threshold by definition, so `PlasmaGate` — which measures the same quantity against the same threshold — closes on it, and `RatioFrameSampling.Evaluate` holds it out of a baseline in **both** monitor modes (a ratio entry additionally needs its own reference line, but the gate comes first for it too). Two caveats, both about the offline path: `BaselineBuilderViewModel` builds that gate from the logger's *current* settings, not the ones the recording was made under — a threshold that has moved since is what the day folder's `_config_*.json` is for — and an unusable gate (`IsUsable` false: a non-positive threshold, or `AnyMonitoredWavelength` with an empty list) makes `IsPlasmaPresent` return null, which `Evaluate` reads as open. The head then lands in the baseline, dragging the mean down and the σ up on exactly the `RawMean` entries that can least afford it. So `PreTriggerSeconds` is a Recordings-review setting, not a measurement one: leave it at 0 unless someone wants the pre-discharge background on screen. `LoggerPanel` gains a `Pre-Trigger Time (s)` box and a live buffered-frame reading; `Wpf 0.1.14` is only a re-pack against the new Core.

`Core 0.1.9` puts **every timestamp the intensity logger hands out on one clock**. `DualIntensityLogger.Stop()` and a `Configure` that disables the logger stamped their `StateChanged` event with `DateTime.UtcNow`, while frames, CSV rows and file names all carry local time. Nothing computed across the two, so nothing broke and nothing was logged as wrong — it surfaced only when someone read the audit CSV and found a session ending eight hours before it started, because `MainViewModel.OnIntensityStateChanged` writes that stamp straight through as the entry's `Value` (`e.Timestamp.ToString("O")`). Both paths now go through a private `LocalNow()`; `SystemLogger` keeps `UtcNow` for its flush deadline, which is a duration rather than a wall-clock reading. `Wpf 0.1.15` is only a re-pack against the new Core.

## Taking a new `Aqusen.Secs` from Test_SECS

The library is developed in a sibling checkout, `C:\Users\infor\source\repos\Test_SECS` (`/mnt/c/Users/infor/source/repos/Test_SECS` from WSL; GitHub `Ray1962/Test_SECS`). Its default branch is **`main`**, not `master` — base PRs there on `main`. How a release is cut on that side (version bump, `dotnet pack … -o nupkgs`, committed nupkg, `scripts/check-release.py`) is in that repo's `CLAUDE.md`; read it before changing the library.

On this side, once the new version is merged there:

1. Copy `Test_SECS\nupkgs\Aqusen.Secs.<version>.nupkg` into `LocalPackages` — the `aqusen` source finds it without the copy, but a machine without a Test_SECS checkout only has `local-aqst`.
2. Bump the `PackageReference` in `src/OES_Leak_Monitor/OES_Leak_Monitor.csproj`, and the `Aqusen.Secs` row of the table above.
3. If that version was restored before (a re-pack under the same number), delete `%USERPROFILE%\.nuget\packages\aqusen.secs\<version>` (`/mnt/c/Users/infor/.nuget/packages/aqusen.secs/<version>` from WSL) first — NuGet caches by version and keeps building against the stale copy.
