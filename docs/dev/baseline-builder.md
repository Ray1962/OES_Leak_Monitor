# Baseline Builder

Building a Golden Run offline from recordings on disk.

## `BaselineBuilder` + `RatioFrameSampling` + `BaselineBuilderViewModel` + `BaselineBuilderPanel` + `AcquisitionSidecar`

**Baseline Builder tab: a Golden Run pooled from recordings already on disk.** It exists for the two process shapes a live capture cannot serve: one that ramps before it settles (the steady segment starts where the plot says, not where a stopwatch does) and one whose whole run is shorter than a capture window (no single run holds enough frames, so several are pooled). Both need the segment chosen *afterwards*, with the trace visible. `BaselineBuilder` is pure computation — `Scan` re-extracts a parsed recording through the current wavelength-corrected ratio set, `Suggest` offers the flattest windows (deliberately dumb: it can see that a stretch is steady, never that it is leak-free), `Build` pools one window per recording into a `GoldenRun`. **Every per-frame decision goes through `RatioFrameSampling.Evaluate`, which the engine's own capture loop also uses** — a baseline built here lands in the same field and is judged by the same thresholds, so a second implementation of "does this frame count" would make two Golden Runs incomparable while both looked fine; `BaselineBuilderTests` pins that by replaying the recorded run through both paths and requiring agreement to nine decimal places. The minimum is a **frame count, not seconds** (σ's reliability follows the sample count; 120 s is 68 frames at 0.56 fps and 600 at 5 fps — the live capture counts seconds only because someone is waiting). A recording whose level disagrees with its peers is **excluded by default** and named, because pooling one run that was actually leaking makes the leak the baseline, after which nothing can detect it; overruling it is possible and usually futile, since the pooled σ then inflates past `MinBaselineMeanToSigma`. **One window per recording** — two windows out of one run are either one window with a gap or two operating points averaged together, which is the error the whole tab exists to avoid (see `docs/adr/0001`). Recordings on different wavelength axes are refused outright. **The shaded window on the chart is redrawn whenever the selected file's `FromSec`/`ToSec` change** (`OnSelectedFileChanged`), not by the commands that move it: the two window boxes set it through their binding, and until 2026-10-27 typing into them changed what Build used while the shading kept showing the previous window — someone checking the chart would have built from a stretch they never saw (`TypingAWindowRedrawsTheShadedWindow`). **Three things the result reports beyond the baselines themselves**, all added after a real build came back nearly useless and half-said so: per-recording **in-window steadiness** (`σ/mean` and drift for the worst ratio — a steady plateau reads ~1 %, and drift separates a ramp from noise), a **marginal-baseline mark** when `mean/σ < MarginalMeanToSigma` (20) since 10.2 σ and 97 σ are indistinguishable on the Leak Monitor tab while the first has thresholds ten times wider, and an explicit **"no back-check"** line when every window covers its whole recording — the back-check is what would otherwise notice a window containing an excursion, and an empty section reads as a pass. The build that prompted this pooled three whole recordings, leak rise included, and produced one baseline at 10.2 σ where its steady-window value is 97. A fourth, **between-recording spread** per ratio, was added after the next build: two well-chosen windows, each steady to ~1 %, whose absolute-intensity levels sat 19 % apart because they were different runs at different plasma brightness — pooled, that gap *became* the σ and `mean/σ` fell from ~125 to 10.7. Ratio-mode entries divide the gap out (2–5 % on the same pair); absolute-intensity ones cannot, so **they want a baseline from one recording rather than several**. It is reported from two recordings upward, unlike the outlier check, which needs three to name one: "these two disagree" is worth knowing without knowing who is wrong. **With a process classifier configured it builds one run holding a baseline per process**: `Scan` names each recording by the same classifier and the same rule the engine applies per frame (`ProcessClassifier.AppliesTo`, the single definition both paths call — a baseline built here lands in the same field and is judged by the same thresholds, so the two cannot disagree about which frames a ratio may learn from), and a ratio pools only from recordings of its own class. `Scan` takes two passes for the reason the engine does: the class is not known until several gate-open frames in, so those frames are found with the boundary threshold and only then is the class's own applied. `RecordingScan.ClassScoped` is recorded rather than inferred from an empty `ProcessClass`, because a classifier that ran and found no gate-open frame also leaves it empty, and reading that as "no classes configured" would let every class-scoped ratio draw from a recording nobody could name. **Four things filter by class, not just the pooling**: the pooled baseline (else the mean lands between two processes, a value neither ever reads, with a σ wide enough to hide a leak), the outlier check (else the minority process is always the odd one out — it differs by design), the spread report (else the top of the panel shows a number no adjustment can improve) and the back-check / steadiness rows (a ratio that does not measure this plasma still has a trace, and it would usually be the worst one). A ratio whose class is absent from the selection is rejected **by name**, saying which process it needed and which were selected — pooling from another would have produced a number, and a number is what nobody questions. Saving goes through `LeakMonitorEngine.ImportGoldenRun`, which reuses the capture's own result type and confirmation dialog rather than growing a second one. `GoldenRun.Source` records what it was built from (`LiveCapture` / `OfflineBuild`, the files and windows, and the recordings the consistency check set aside) — live captures stamp it too, so a missing `Source` now means only "stored before this existed". `AcquisitionSidecar` writes `{recording}.acq.json` beside each recording as it opens (`MainViewModel.OnIntensityFilesChanged`), because a CSV says nothing about the exposure it was taken at and the alternative — a header field — means changing `IntensityCsvWriter` *and* `RecordingCsvParser` in the Core package; older recordings have none, so their fingerprint carries only the axis the CSV itself proves. `Recording.EnumerateSpectra` holds the data-folder walk that Recordings used to have inline; both tabs share it.
