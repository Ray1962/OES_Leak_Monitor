# Tool events and the EAP link

The main tool's process events, the process windows they open, and the OES's SECS-host link to the EAP that delivers them.

## Tool events (`ToolEventSettings` + the tool-event region of `LeakMonitorEngine`, issues #25–#35)

**the main tool's own process events decide which process a frame belongs to.** PM3 interleaves Chamber Process / precoat (process A), Chamber Clean (B) and an unplaced C; the spectral classifier can only infer which, the tool knows, and the fab's EAP already receives its CEIDs. So the EAP forwards them, unfiltered, as S2F41 `TOOL_EVENT` (`CEID`, optional `TIME`) over the existing SECS link, and a CEID table (`secs.toolEvents.mappings`: CEID → class, Start/End, name, optional plasma threshold) turns them into **process windows**. Information, not control — the only remote command there is. `Enabled` and `Mappings` are **staged** (adopted with `ReloadRatios` at start-up and each acquisition Stop→Start, because the classes the table names are the ones ratios' `ProcessClass` refers to — the same reason the classifier is staged); re-adopting an identical table keeps the open window, a changed one starts from Unknown. `MaxWindowSeconds` (600) and `ApplyInTestMode` are **hot-applied** (`ConfigureToolEventsLive`) — they name no class. `ReceiveToolEvent` runs on the SECS receive thread while the host waits: it looks the CEID up, records it (VID 032, a received-count), queues it and returns; the window moves at the start of the next frame under `_gate`, so every ratio on a frame sees one window. **`CurrentFrameClass()` (#27's single entry point) decides in this order**: in a window → the window's class, per frame, not step-locked; outside any window → `Unknown` if the step machine has a step open, else no class, both scoped (class-scoped ratios read `NotApplicable`, unscoped ones judge on); Unknown or not in use → exactly the pre-feature behaviour (classifier if configured, else unscoped). Unknown is **fail-open on purpose** — "we have not been told" is not "nothing is running", and judging nothing until the EAP's first message would lose a real leak to a late one. Per-class plasma threshold, in a window: the table's value, else the classifier's, else the classifier *settings'* threshold for that class name even with the classifier off, else the base threshold. Events that don't pair up are resolved toward the process the tool is actually in and each logged as a Warning: Start over an open window closes and replaces it (`ToolEventWindowUnclosed`), an End matching nothing is ignored (`ToolEventOrphanEnd`), a window older than `MaxWindowSeconds` on the frame clock goes back to Unknown, not to "outside" — nobody said the process ended (`ToolEventWindowTimedOut`). `TIME` (`YYYYMMDDhhmmsscc` / `YYYYMMDDhhmmss`) dates the event for logs and status; a malformed one refuses the event. **Suppressed** — never during a replay (`SetReplayActive`, told explicitly by `BeginReplayOutput` / `EndReplayOutput` because a replayed frame and a synthetic one look alike here), and on synthetic test-mode frames unless `ApplyInTestMode`: events are still recorded and the underlying window still tracked (live judging resumes in the right window on the next hardware frame), but the context in force reads Unknown, and the window's `ToolEventWindowOpened` / `Closed` lines end in `(not applied: …)` so the audit log never claims a scoping that did not happen. While events decide the class, VIDs 027/028 follow them (in window 3/class; outside with plasma 4/`Unknown`; outside without 1/""), and plasma outside any window is logged per stretch as `ToolEventUnmappedPlasma` (start, length, trigger-metric median/max) — that is where an unmapped process shows up. A configured classifier still runs and is only cross-checked (`ToolEventClassMismatch`). **`ToolEventStatus` is published, not read off a frame** (`ToolStatusChanged`, raised on adopt, receive, window move, suppression change): the first version took VIDs 030–032 and the SECS-tab status from the last snapshot, so with no spectrum flowing an applied table read "not in use" / 0 and a forwarded event never reached 032 — caught only by running the app, which neither the engine nor the wire tests could see. `SecsBridge.OnToolStatus` stores the immutable record and the bindings read it, so the bridge still only reads. HCACK: the library refuses first (not REMOTE 2, RCMD not in profile 1, unlisted parameter 3/CPACK 1); then missing CEID 3, unreadable CEID or TIME 3/CPACK 2, not in use 2, unmapped 0 (`ToolEventIgnored`, once per CEID per run — the EAP forwards everything), mapped 0. **An existing site profile is never overwritten**, so a machine that ran SECS before this build answers `TOOL_EVENT` with HCACK 1 until its profile gains the `remoteCommands` row (and VIDs 030–032; `SecsProfileMissingBinds` names them). Outputs: the ratio CSV gains trailing `ToolContext,ToolWindowClass` only when tool events are in use at file open (same rule as the classifier columns; the table cannot change mid-file because it is only adopted on a restart, which closes the file), and `.acq.json` records `toolEventContext` / `toolWindowClass` *beside* the acquisition fingerprint, not in it, so a process window can never read as an acquisition mismatch. The batch layer takes a step's class from its sampling window (gate-open + 10–30 s): one class there is the step's; two or more (a window edge inside it) leave the step unsampled and unable to anchor a batch (`BatchStepClassAmbiguous`); none (too short) keeps the old last-non-empty rule. UI (on the **EAP tab** since #58; it was the SECS tab's): the ungated status row (context/class, last CEID + time, received count) and read-only CEID table with an orange "not yet in force — restart acquisition" line driven by `ToolEventSettings.SameStaged`; the Engineer-gated settings (switch labelled "takes effect at next acquisition start", max window and test-mode switch "applies on save", max window refused outside 10–86400); the Leak Monitor banner's `PROCESS CONTEXT UNKNOWN` line, hidden when the test-mode note already says events are not applied. Design: `docs/secs-integration.md` §15; host side: Satellite spec §7; EAP side: on site the SECS host is the FDC, so the OES connects to the EAP as a SECS host instead (`EapSecsLink`, `eap-tool-event-secs-spec-zh-TW.md`), and the FDC reads the window from VIDs 030/031 (`fdc-integration-spec-zh-TW.md` §6). ADR 0001 has an addendum: this is the step signal it asked for, used for scoping, Golden Run shape unchanged.

## `EapSecsLink` (+ `EapLinkSettings`, `EapViewModel`/`EapPanel`, `LeakMonitorEngine.ReportToolContext`)

**the same main-tool events, fetched by the OES acting as a SECS host towards the EAP (scheme 2b, #58), because the site's SECS host is the FDC.** HSMS-SS allows one host per session, so the EAP has no session to send `TOOL_EVENT` on; it plays equipment on the address it gave (`10.2.3.120:20347`) and the OES connects out with a `GemHost` (`TimeSyncIntervalMs = 0` — never push this PC's clock into the EAP; T3/T5–T8 fixed). On every communicating: S1F17 → S1F1 → **S2F37 on the two EAP CEIDs** → S1F3 of S1–S7 (`QueryStatusAsync`, `Aqusen.Secs` 0.8.0 — `RequestStatusAsync` only logs the S1F4), then S1F3 **every 30 s**, which is what the TCP version's heartbeat was. **No S2F33/S2F35: the platform fixes its reports**, so the S6F11 is read by position — one forwarding CEID for every tool event with `L{ tool CEID, receive time, SEQ }`, a tool-link CEID with `L{ U1 }`; anything else is `EapReportRejected` and not applied. Forwarded events go to the existing `ReceiveToolEvent`; **both sources (this and `TOOL_EVENT`) are accepted, no switch**. The poll and the tool-link event go to `ReportToolContext`, **a statement of where the window is, not an edge**: it shares the edges' queue (applied in arrival order at the next frame), changes and logs nothing when it agrees, and corrects a difference — `ToolEventContextRestored` from Unknown, `ToolEventResync` (the EAP lost an event) from a known window, `ToolEventContextUnknown` for S1 = 2 / S4 = 0 / tool link 0. S2 is read through the CEID table: a classed Start opens that window, a record-only or unmapped Start means outside (closing a window whose End was lost), an End is `ToolEventAck.Invalid`. A report never counts as a received event — VID 032 stays the EAP's last real event. **A dropped connection by itself changes nothing** (`GemHost` reconnects); only `SilenceTimeoutSeconds` (75) with no successful S1F3 and no S6F11 reports Unknown, once per silence and only after having heard something — a successful S1F3, not an HSMS linktest, because a linktest proves the socket, not the EAP's application. Two sequence numbers, deliberately: `_lastEventSeq` (last event handled) decides duplicates, `_lastKnownSeq` (highest heard, S7 included) decides gaps — after an OES restart the first S7 names the event about to be resent, and feeding it to the first would drop that event (`TheEventAnS7Names_IsStillApplied` fails under exactly that mutation). Secs4Net reports a failed connect only as an `[ERR]` line followed by arming T5 — no connection state says it — so that log pair is what counts `EapLinkConnectFailed` (first, then hourly). `secs.toolEvents.eap` is **hot-applied**, independent of `secs.enabled`, the nine ids default to 0 and the link does not start until `EapLinkSettings.IdProblem()` is null (all set, S1–S7 distinct, two CEIDs distinct), and an unchanged re-save does not reconnect. **The EAP tab** (`x:Name="EapTab"`, ungated status, Engineer-gated settings) holds the link's status and settings *and* the tool-event status, switches and CEID table moved off the SECS tab, which now carries only the FDC link; each tab persists only its part — `PersistToolEvents` writes `secs.toolEvents`, `PersistSecsSettings` keeps the `toolEvents` on disk — so neither save undoes the other. Trace in `Log\eap_YYYYMMDD.log`. For manual testing and for the EAP vendor, `Test_SECS` has an "EAP (PM3 event forwarder)" equipment profile and an "OES (2b host)" host profile (ids 6001–6007, CEIDs 6100/6101). History: #53/#54 first built this as a plain-TCP line protocol; #58 replaced it after the vendor confirmed it can be equipment with fixed reports. Design record: `secs-integration.md` §15.9.
