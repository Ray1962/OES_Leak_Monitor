事前準備

約 5 分鐘

各項都要在同一次連線裡完成（項目 8 需要重開 App，另起一次連線即可），全程開著 SECS 分頁的 Traffic 與 Host 端的收送記錄。

  • 以 Engineer 帳號登入 App
  • Host 已連上，SECS 分頁狀態燈為綠色 COMMUNICATING
  • SECS 分頁勾選 Report alarms、Report events、Report test / replay data too，按 Save & apply 最後一項僅供本次測試，收尾時要關回去
  • 記下分頁中段的 Traffic log: 路徑，填進上方欄位
  • 備妥一段含洩漏事件的全譜錄檔 CSV 例：C:\DualOES\202608\14\P_OES1_0814220358.csv
  • 比值組要能偵測這段錄檔：上例須用出廠比值組（R_N2Ar／R_NOAr／R_N2357Ar，皆除以 Ar 750.4），且製程分類器關閉 先備份 settings.json，收尾時還原。現場比值組（例如除以 CO 330、或分 A/B/C 製程的）對 8/14 的氬電漿量不到參考線、拿不到 baseline，引擎不會轉態，Host 也就收不到任何 ALID
  • Leak Monitor 分頁確認至少兩條 Role = Alarm 的比值啟用中 requireTwoForAlarm 開著時，只有一條能判定就永遠到不了 1cc27002；Guard／TrendOnly 只觀察、不計入警報
1

Replay 分頁到引擎、三個 CEID

§13.4-1

驗的是「按鈕真的會呼叫到那些方法」。按鈕以下的整條路徑（錄檔 → 引擎 → S5F1／S6F11）已自動化。

  • Replay 分頁 → Choose CSV… 選錄檔，勾 Raise leak alarms during replay
  • Connect（會落到 test mode）→ Start Host 收到 CEID 1cc27508
  • Play 後立刻到 Leak Monitor 分頁擷取 Golden Run（60 秒） 擷取結果須為接受，且上述三條比值都有 baseline；被拒或缺比值就從 Restart 重來。洩漏在錄檔約第 7 分鐘才出現，第一分鐘是乾淨的
  • 等洩漏出現（可用 5× 加速） Host 收到 ALID 1cc27001 set
  • 洩漏升級 Host 收到 1cc27001 clear ＋ 1cc27002 set
  • 收到 1cc27002 set 後立刻在 Replay 分頁按 Pause 重播播到檔尾時 App 會自動解除警報（不帶進即時監測），那筆 clear 不是 Acknowledge 送的，也不會有 CEID 1cc27502。5× 下從 Alarm 到檔尾只剩約 25 秒
  • Leak Monitor 分頁 → Acknowledge（只按一次） Host 立刻收到 CEID 1cc27502；這時還不會有 1cc27002 clear——Ack 只解除鎖存，綜合狀態要等下一幀才重判，暫停中沒有下一幀
  • Replay 分頁按 Play 繼續播放 Host 收到 1cc27002 clear。若反而又收到 1cc27002 set（比值仍在 Alarm 門檻以上、重新鎖存），再按一次 Acknowledge。之後再收到一組 1cc27001 set／clear 屬正常
  • Monitor 分頁 DevicePanel 標題列的 Stop（停止擷取） Host 收到 CEID 1cc27509。不是 Replay 分頁的 Stop——那顆只結束重播，擷取改接合成光譜繼續跑，不會送 509
  • 確認本次產生的檔名帶 SIM 前綴 SIMP_OES1_*、SIMP_Ratio_* — 重放資料不得與量測混淆

反向驗證（§13.4-2 的現場那半）：取消 Report test / replay data too → Save & apply → 重播同一段。 除了設備故障警報（1cc27012／013／014，刻意不受這個開關管）之外，不應再收到任何 S5F1／S6F11；但 Host 送 S1F3 仍讀得到值且 VID 016 = 1。

  • 重播期間確實沒有任何 S5F1／S6F11 期間若按過 Disconnect／Connect，會收到 1cc27012 set／clear，這是設備故障警報，屬正常
  • S1F3 查 1cc2700016，回 1 用 Test_SECS 時 Device profile 選 OES Leak Monitor acceptance (chamber 02) 再按 Request VID 016。內建 Request Status 查的是 Demo 的 SVID 1～4，只會回空清單

設備故障警報（拔插光譜儀）

§13.4-3

ALID 012 是轉態不是狀態——必須先連上、再拔掉才會觸發。開機時本來就沒連線，不會、也不該送警報。

  • 確認光譜儀已連線，且 DevicePanel 不是 Test Mode
  • 拔掉光譜儀 USB Host 收到 ALID 1cc27012 set
  • 插回並重新 Connect Host 收到 1cc27012 clear

比值槽位：狀態隨重播走 0 → 1 → 2

§13.4-6

與項目 1 同一次重播一起做：Play 之前先讓 Host 開始追蹤。線上讀值已自動化，這裡驗的是真實重播流程裡槽位的數值確實在動。

  • Host 以 S1F3 查槽位 1～3 的位移 25：1cc2700125、1cc2700155、1cc2700185 依序為 R_N2Ar、R_NOAr、R_N2357Ar（出廠比值組）。這一步不需要光譜，Start 之前就讀得到
  • Host 以 S2F23 追蹤槽位 1～3 的位移 05：1cc2700105、1cc2700135、1cc2700165，每 1 秒取樣 TIAACK = 0。Host 工具若只能追蹤自己 profile 裡列出的 SVID（例如 Test_SECS 的 Device profile），先把這三個加進去
  • 項目 1 的重播期間觀察三條追蹤 各自走過 0（Normal）→ 1（Warning）→ 2（Alarm）；Golden Run 擷取完成之前是 5（NoBaseline）屬正常。數值依序記在備註欄
7

比值槽位改變時收到 CEID 507

§13.4-7

Ratio Setup 沒有「移動列」的按鈕，槽位是靠刪除／新增列改變的。動手前先關閉 App、備份 settings.json（若事前準備已備份可沿用）。

  • Ratio Setup 選第 1 列（R_N2Ar）→ Remove → Save；Monitor 分頁 Stop → Start Host 收到 CEID 1cc27507（Report events 須勾著）
  • Host 重查槽位 1～4 的位移 25 槽位 1 = R_NOAr、2 = R_N2357Ar、3 = R_N2357Abs、4 = 空字串（空槽位：位移 16 = 0、05 = 6）
  • 只改一個門檻（例如第 1 列的 Sigma Warn）→ Save → Stop → Start 不應收到 1cc27507（508／509 照常）
8

舊 profile 補列後查得到新 SVID

§13.4-8

驗的是升級機台的路徑：舊 profile 不會被覆寫，新列靠 SECS 分頁的 Add missing rows 補上。先備份目前的 profile，測完還原。

  • 關閉 App，把 profiles\oes-leak-monitor.json 備份後，換成舊版的 profile（2026-10-23 之前寫出的都缺槽位列；用 2026-10-15 之前、還沒有 TOOL_EVENT 的版本才能驗下一步的 HCACK 1），重開 App Traffic 出現 [CFG] … status variable(s) this build can serve are not in the profile；SECS 分頁的說明寫 The profile is missing … row(s)
  • Host 查 1cc2700125、送一次 TOOL_EVENT 查不到該 SVID；TOOL_EVENT 回 HCACK 1
  • 以 Engineer 按 Add missing rows 按鈕下方顯示 Added N row(s), refused 0 …；資料夾出現 oes-leak-monitor.json.bak-…，內容與換上的舊版相同
  • 按 Restart interface，Host 重新連上後再查一次 查得到 1cc2700125；TOOL_EVENT 不再回 HCACK 1
  • 打開補過的 profile，確認原本的列與註解都還在、只在各區段後面多了新列
