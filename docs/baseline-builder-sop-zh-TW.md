## 1. 這份 SOP 什麼時候用

| 情境 | 說明 |
|---|---|
| **換配方後建基準**（主線） | 製程會 ramp（前幾秒功率還在爬）或很短（一次 run 比擷取視窗還短）時，站在機台前按 Capture 是猜的。這類機台**本來就該走這條路**。 |
| **清機／換光學件後重建** | 視窗結垢會讓絕對強度整個平移，舊基準不再成立。 |
| **現場 Capture 失敗後補救** | 日誌出現 `GoldenRunEmpty`、或大量比值被拒（`GoldenRunRatioLowSnr`、`GoldenRunRatioUnstableBaseline`）。 |
| **評估既有錄製** | 想知道某幾天的錄製能不能拿來當基準。走到第 [9](#9-只是想評估停在這裡) 節就停，**不要存檔**。 |

**週期綁事件，不綁日曆。** 配方變更、清機、換光學件之後必做；製程沒變時不需要定期重建——沒有必要的重建只會讓每條基準線的來歷變得更難追。

## 2. 角色與分工

分頁**不受權限限制**，任何人都能進去看、掃描、按 Build。只有 **Save 需要 Engineer 以上**（權限不足時畫面會顯示橘字 `Engineer sign-in required to save`）。

| 步驟 | 誰做 |
|---|---|
| 第 3–5 節（凍結設定、對照表、列出、掃描、看曲線） | Operator 或 Engineer |
| 第 6–14 節（分岔判斷、選視窗、Build、判讀、存檔、驗證） | **Engineer** |

> ⚠️ **Build 與 Save 必須由同一人、同一次連續完成。**
>
> 程式**不會**因為你改了勾選、改了視窗或改了 `Keep anyway` 就讓上一次的 Build 結果失效——`Save as active baseline` 仍然可按，而它存下去的是**上一次 Build 的結果**，不是畫面上現在的樣子。交接給別人做最後一步，正是這個陷阱會發作的場景。

## 3. 前置一：掃描前必須凍結的設定

掃描會用**當下的設定**把每一幀重新萃取一次。之後改動下列任何一項，既有掃描就失效了，而且**畫面上沒有任何提示**——它看起來還是掃好的。

掃描是整個流程唯一花時間的一步，所以這個確認放在最前面：

- [ ] **Ratio Setup**：比值定義（監控方式、譜線、萃取方式、Role、ProcessClass）已定案
- [ ] **Wavelength Calibration**：波長修正表已定案
- [ ] **Process Classifier**（若有啟用）：分類規則已定案
- [ ] **Logger 的觸發門檻**（Configuration 分頁）：電漿閘門用它決定哪些幀算數，改了它就改了「哪些幀進得了基準」
- [ ] **日期範圍**已經想好

最後一項特別容易誤觸：**改日期範圍或按 `Refresh`，會清光所有掃描、勾選、已選視窗與結果面板**，全部要重來。

> 為什麼要把這四項列出來：其中**波長修正**和**觸發門檻**都不在 Baseline Builder 分頁上。人在這個畫面工作時，根本不會想到它們。

## 4. 前置二：站台比值對照表

結果面板只列比值的顯示名稱，**不顯示 `Role`，也不顯示 `ProcessClass`**。但第 [11](#11-go-與-no-go-判斷表) 節的 go/no-go 判斷和附錄 A 的缺 class 處置，都要靠這兩個欄位。

所以先到 **Ratio Setup** 抄一張表，跟著紀錄一起存（第 [12](#12-紀錄必做不可省略) 節）：

| 比值顯示名稱 | 監控方式 | Role | ProcessClass |
|---|---|---|---|
| 例：N2 337.1 / Ar 750.4 | Ratio | Alarm | （空白＝全製程） |
| 例：N2 337.1（絕對強度） | AbsoluteIntensity | Alarm | A |
| 例：CO 607.9 / Ar 811.5 | Ratio | Guard | A |

**這張表不必每次重抄**——只有改比值設定或改配方時才會變。每次執行本 SOP 時確認它還是最新的即可。

一張表同時服務兩個判斷：

- **監控方式**欄告訴你哪些是**絕對強度項**——第 [8](#8-流程-b跨檔合併建基準) 節對它們有一條會推翻決定的限制。
- **Role** 欄告訴你某條比值沒拿到基準時，那是**必須退回**（`Alarm`）還是**可以註記待補**（`TrendOnly` / `Guard`）。

## 5. 共同步驟：列出錄製與掃描

1. 進 **Baseline Builder** 分頁。
2. 設定 **From / To** 日期範圍（預設是最近 14 天），按 **Refresh**。
   - 清單會列出資料夾裡的全光譜錄製，**壓縮進 `DD.zip` 的也會列出來**（`zip` 欄有標記）。
   - 狀態列會顯示 `{n} recording(s) in {資料夾}`。列出 0 筆就是日期或資料夾不對。
3. 在 **`Use`** 欄勾選要用的錄製。
   - **勾選（`Use`）和點選（看曲線）是兩回事**：清單只能單選，點某一列只是把它的曲線畫到右邊，不代表要用它建基準。
4. 按 **Scan ticked**。這是唯一花時間的一步，掃描期間所有按鈕都會停用。
5. 掃完看 **`State`** 欄：
   - `{幀數} frames, {秒數} s` —— 正常。
   - `{製程名} · {幀數} frames, {秒數} s` —— 分類器有啟用，見[附錄 A](#附錄-a多製程站台分類器開啟時)。
   - `failed: not a full-spectrum recording` —— 這不是全光譜錄製（例如選到 Ratio CSV），取消勾選。
   - 掃描失敗的檔**永遠進不了 Build**，不必特別處理。
6. 點選任一筆看它的曲線。

**曲線怎麼看**：每條比值都除以它自己在整段錄製的**中位數**，所以量級差很多的線可以共用一個縱軸（軸上寫 `× own median over the recording`）。這**不是** Leak Monitor 的「% of baseline」——這個分頁的前提就是基準還不存在。

## 6. 分岔：單檔還是跨檔

掃描完成後，看 `State` 欄的幀數，並在曲線上找平台段：

| 條件 | 走哪條 |
|---|---|
| 單一錄製的**平台段** ≥ 120 幀，而且曲線在那一段確實是平的 | [流程 A：單檔](#7-流程-a單檔建基準) |
| 單一錄製湊不出來（短製程、或平台段太短） | [流程 B：跨檔](#8-流程-b跨檔合併建基準) |

**為什麼用幀不用秒**：硬門檻是幀數——所有選中視窗**加總**要有 60 幀，不足就整條比值被拒。而秒數在這裡會騙人：同樣 60 秒，5 fps 是 300 幀，0.56 fps 只有 34 幀，後者連門檻都過不了。建議抓 **120 幀**（門檻的兩倍）留餘裕，因為你之後很可能會把視窗縮小。

**幀數夠不代表那一段是平的。** 曲線有否決權：看起來還在爬升，就回頭走流程 B 或重錄，不要硬選。

## 7. 流程 A：單檔建基準

適用：製程會 ramp，但一次 run 夠長，平台段自己就湊得出 120 幀以上。

1. 點選那一筆錄製，讓它的曲線顯示在右邊。
2. 按 **Suggest** 當起點。它會填入「最平的一段」，長度等於 Configuration 分頁的 `GoldenRunCaptureSeconds`（預設 60 秒）。
   - 狀態列會顯示 `Flattest {n} s window: {a}–{b} s ({幀數} frames).`
   - 若顯示 `No steady stretch found` —— 直接跳到第 3 步自己拖。
3. **在圖上按住左鍵拖曳**，確認或調整這一段。左右拖都可以。
   - 也可以在上方 `Baseline window:` 兩個框直接打數字（離開欄位才生效）。
4. 檢查視窗落在平台上，不含起始爬升段、不含結束段。
5. 填 **Golden Run name** → 按 **Build**。
6. 跳到第 [10](#10-判讀結果面板) 節判讀。

> ⚠️ **Suggest 不能當決定。** 它的提示文字自己寫得很清楚：**它看得出一段很平，看不出一段沒有漏**。它的工作是把游標放到對的位置附近，判斷仍然是你的。

> ⚠️ **不要用 `Whole file` 做正式建置。** 視窗一旦涵蓋整份錄製的 95 % 以上，**回套檢查就被關掉了**——那是唯一會發現「這份錄製別的地方跑到 59 σ」的守衛。結果面板會明白印出 `No back-check`。`Whole file` 只用在第 [9](#9-只是想評估停在這裡) 節的評估用途。

**流程 A 的驗收重點**（詳見第 10 節）：**視窗穩定度** 與 **回套檢查**。

## 8. 流程 B：跨檔合併建基準

適用：短製程，一次 run 湊不出足夠的幀，要把好幾次合起來。

1. 勾選要合併的**所有**錄製，確認全部掃描成功。
2. **逐一**點選每一筆，各自選一段（方法同流程 A 第 2–4 步）。
   - **一個檔只能選一段。** 沒有「新增視窗」的控制項，每一次拖曳都是**取代**上一段。
   - 理由：同一份錄製的兩段若是**同一個**操作點，它們本來就該是連續的一段（中間有空隙不影響）；若是**不同**操作點，把它們平均成一個 mean 正是這整件事要避免的錯誤。
3. 確認每一筆的 **`Window`** 欄都有數字——空白的表示你漏了那一筆，它會以整份錄製參與建置。
4. 填 **Golden Run name** → 按 **Build**。
5. 跳到第 [10](#10-判讀結果面板) 節判讀，**但先讀下面這段**。

### 跨檔的特殊風險：絕對強度項

**每個視窗都很穩，合併後 `mean/σ` 還是很差**——這種情況幾乎都是「檔間差距」造成的：不同 run 的電漿亮度本來就不完全一樣，合併等於把那個差距寫進 σ。

- **比值項會把它除掉**——這正是參考線的用途。
- **絕對強度項沒得除**，差多少就原封不動進 σ。

實測（同一天相隔一小時的兩次 run，各自視窗內都只有 0.7–1.3 % 散度）：

| 比值 | 檔間差距 |
|---|---|
| N2 337.1 / Ar 750.4 | 2.1 % |
| **N2 337.1（絕對強度）** | **19.0 %** |
| uN2 335.5 / Ar 750.4 | 4.8 % |
| N2 353.7 / Ar 750.4 | 4.0 % |

那條絕對強度項的 `mean/σ` 因此從單檔的 ~125 掉到合併後的 **10.7**，剛好擦過門檻並被標成 marginal。

> **做法**：對照第 [4](#4-前置二站台比值對照表) 節的表，**絕對強度項盡量只用單一錄製**建基準；真要合併，先看結果面板的「檔間差距」那一段確認亮度一致。比值項則可以放心合併。

**流程 B 的驗收重點**：**檔間差距**（第一優先）、視窗穩定度、被擱置的錄製。

---

## 9. 只是想評估？停在這裡

想知道某幾天的錄製能不能當基準，走完第 5 節 → 隨便選視窗（這時 `Whole file` 是合理的）→ 按 **Build** → 讀結果面板 → **不要按 Save**。

**這樣做是安全的**：`Build` 只計算，**不會動到現在使用中的基準線**。只有 `Save as active baseline` 會。

## 10. 判讀結果面板

結果面板（畫面最下方的文字框）由上而下有這幾段：

| 區塊 | 意思 |
|---|---|
| `Baselines (n):` | 每個比值的 `mean ± σ`、`mean/σ`、採用幀數 |
| `No baseline for:` | 沒拿到基準的比值與原因 → 第 [11](#11-go-與-no-go-判斷表)、[15](#15-baseline-builder-獨有的拒絕訊息) 節 |
| `Set aside by the consistency check` | 水準跟其他檔差太多（> 5 σ）而**預設被排除**的錄製 |
| `How far the recordings disagree with each other` | **檔間差距**：每條比值在各錄製之間的水準差，以及那是「檔內散度」的幾倍 |
| `How steady each chosen window is` | **視窗穩定度**：每個檔在**自己視窗以內**的 `σ/mean` 與漂移（取該檔最差的那條比值） |
| `Furthest each recording goes outside its own window` | **回套檢查**：每個檔在**自己視窗以外**最遠跑到幾 σ |

### `mean/σ` 剛好過門檻要當回事

硬門檻是 **10**（低於就整條被拒）。但 `mean/σ = 10.2` 和 `mean/σ = 97` 在 Leak Monitor 分頁上長得**一模一樣**（都只是「有基準」），而前者的警報門檻寬了十倍——看起來設定完成、真的漏氣時不會叫。

低於 **20** 時結果面板會在該行尾端標 `<< only just clears the floor`。**看到它就回頭檢查視窗**，通常代表視窗框進了不該進來的東西。

### 視窗穩定度怎麼讀

一段真正的平台大約是 `σ/mean ≈ 1 %`。十倍於此，代表視窗吃進了製程正在做的事：

- **漂移大** → 那是一段爬升，視窗放錯位置。
- **只有 σ 大、漂移小** → 是雜訊，電漿本身不穩。

### 回套檢查

數字大**不代表壞**——視窗以外本來就是製程在變的地方。但如果那份錄製裡真的有一次洩漏，這個數字就是它。

**整檔框選會讓這道檢查失效**，結果面板會印 `No back-check`。這時**視窗穩定度是唯一的判準**。

### 被擱置的錄製 與 `Keep anyway`

**預設排除是對的。** 這道檢查擋的是這整件事裡最危險的一種錯誤——把一份**當時真的在漏**的錄製混進基準。一旦混進去，那個漏就變成「正常」，之後永遠測不到它。

**勾 `Keep anyway` 的條件**：你**說得出**那份錄製水準不同的原因，而且那個原因**不是洩漏**（例如已知它是清機後第一批、或中間換過視窗）。「看起來還好」不是原因。覆寫一定要寫進紀錄。

兩點提醒：

- 這道檢查需要**至少 3 份錄製**才會啟動。只有兩份時這一段不會有東西——兩個檔選不出誰是異類；但「檔間差距」照樣會報，因為「這兩個彼此不合」不需要先知道誰錯。
- **覆寫常常白費工**：差很遠的錄製合進來會讓 σ 膨脹，`mean/σ ≥ 10` 那道硬門檻通常會自己把結果擋掉。這時該做的是**重錄**，不是硬推。

## 11. go 與 no-go 判斷表

判讀完只要回答一個問題：**這次還能不能往下走？**

| 看到什麼 | 判斷 | 下一步 |
|---|---|---|
| `Refused: …`（整批被拒） | **NO-GO** | 見第 [15](#15-baseline-builder-獨有的拒絕訊息) 節。`Save` 本來就會是停用的 |
| 有 `Alarm` 比值出現在 `No baseline for:` | **NO-GO** | 對照第 4 節的表確認 Role。是 `Alarm` 就退回：那個製程整段沒有洩漏監測，而 Leak Monitor 分頁上「No Baseline」看不出是缺錄檔還是比值壞了 |
| 只有 `TrendOnly` / `Guard` 比值沒拿到基準 | **GO（有條件）** | 可以存，但在紀錄裡註明待補 |
| 有比值標 `<< only just clears the floor` | **暫停** | 回頭縮小／移動視窗再 Build。改善不了才考慮接受，並寫進紀錄 |
| 視窗穩定度 `σ/mean` > 10 %，漂移也大 | **NO-GO** | 視窗選在爬升段，重選 |
| 印出 `No back-check` 而你不是在做評估 | **NO-GO** | 你用了 `Whole file`。改成拖曳選段 |
| 檔間差距大，且大的是絕對強度項 | **暫停** | 見第 [8](#8-流程-b跨檔合併建基準) 節：那條改用單一錄製 |
| 以上皆無 | **GO** | 往第 [12](#12-紀錄必做不可省略) 節 |

## 12. 紀錄（必做，不可省略）

**結果面板裡的判斷依據不會被保存。** `mean ± σ`、`mean/σ`、檔間差距、視窗穩定度、回套檢查這些數字**只存在那個文字框裡**，重按一次 Build 就沒了；`settings.json` 只留下最後的 mean/σ。三個月後有人問「這條基準線當初為什麼可以接受」，能回答的只有那段文字——尤其 `mean/σ = 10.2` 和 `97` 事後從 `settings.json` 完全分不出健康程度。

所以 **Build 之後、Save 之前**，做兩件事：

1. **存進日資料夾**：把結果面板全文複製出來，存成文字檔放進這次用到的錄製所在的日資料夾：

   ```
   {資料夾}\YYYYMM\DD\_baseline_{Golden Run 名稱}_{yyyyMMdd}.txt
   ```

   **檔名一定要用底線開頭**——底線開頭的檔會被錄製檔掃描跳過，不會污染 Recordings／Ratio Review 清單，壓成 `DD.zip` 時也會一起收進去。這樣「這些錄製」和「它們被判定可以當基準的理由」會被一起複製走。

2. **貼進工單／機台變更紀錄**，連同：
   - 第 [4](#4-前置二站台比值對照表) 節的比值對照表
   - 用了哪幾個檔、各自的視窗
   - 任何 `Keep anyway` 覆寫及其理由
   - 任何接受 marginal 基準的理由
   - 若用到沒有 `.acq.json` 的舊錄製：註明「**取像條件無法驗證**」（見下）

> **程式不會自動寫這份報告**，這是人工複製貼上的步驟。系統日誌只會記 `GoldenRunBuiltOffline`（名稱、用了幾個檔、幾條比值、幾個檔被擱置、每個檔的視窗時間）——**不含**上面那些判斷依據。

### 舊錄製沒有 `.acq.json` 時

每個錄製檔旁邊的 `{檔名}.acq.json` 記錄當時的積分時間與平均設定，但那是後來才加的功能，**之前錄的檔沒有**。

用沒有 sidecar 的錄製建基準，`LeakMonitorAcquisitionMismatch` 這道自動守衛就**只比得了波長軸**，積分時間差異完全偵測不到（這是刻意的：猜一個填進去，會讓該擋的時候放行）。而**絕對強度會隨積分時間整個縮放**。

**可以用，但**：紀錄裡要寫明「這條基準線的取像條件靠人工確認」，而且第 [14](#14-收尾驗證) 節的實跑驗證要**特別盯絕對強度項**——那是唯一還能發現積分時間對不上的機會。

## 13. 存檔

1. 確認畫面上的勾選與視窗，**就是你剛剛 Build 的那一組**。任何改動之後都要**重按 Build**（見第 2 節的警告）。
2. 按 **Save as active baseline**。需要 Engineer 以上。
3. 若跳出 **`Replace Golden Run?`** 對話框：
   - 它表示同名的既有基準線裡，**有些比值在新的這份裡沒有基準**，而且這個取代**無法復原**。對話框會列出是哪幾條。
   - 對照第 4 節的表：其中有 `Alarm` 比值就按 **No**，回頭補足再來。
   - 沒有這個對話框，代表沒有任何比值會失去基準，直接存檔。
4. 狀態列出現 `Golden Run "{名稱}" saved and made active.` 才算完成。

**存檔是立即生效的**——不需要重啟擷取，也不用重開程式。

## 14. 收尾驗證

存檔只證明「存進去了」，**不證明「這條基準線對得上現在這台機」**。有三條路徑會**安靜地**讓它失效或不完整：

- `ApplyGoldenRun` 只在**監控方式、參考線名稱、萃取版本**全部相符時才採用該比值的基準。**Scan 之後改過 Ratio Setup，那條基準就會被忽略，畫面不報錯。**
- 取像條件不符，只在 Leak Monitor 的橫幅出現一行。
- 洩漏率校正可能因為**新的 Golden Run 名稱**而被自動解除配對，估算整個關掉。

所以四步都要做：

1. [ ] **Leak Monitor** 分頁 → **Baseline** 下拉已經切到新的名稱。
2. [ ] 橫幅**沒有**取像條件警示（`Acquisition differs from Golden Run …`）。有的話，那條基準線不適用於目前的積分／平均設定。
3. [ ] 該有基準的比值**都不是** `No Baseline`。
4. [ ] **洩漏率校正狀態**正常（不是 `Not calibrated` / `Baseline mismatch`，除非本來就沒有校正）。
5. [ ] **實跑一個 step**，看各比值的 **% of baseline 是否落在 100 附近**。

> 第 5 步是唯一能同時驗證上面三條安靜失效路徑的動作：基準沒被採用的話 % of baseline 不會在 100 附近；取像條件不對的話絕對強度項會整個偏掉。**少了這一步，這份 SOP 的終點是「我按了 Save」，而不是「它在量」。**

## 15. Baseline Builder 獨有的拒絕訊息

下面四種訊息**只有這個分頁會出現**，[`golden-run-baseline-troubleshooting-zh-TW.md`](golden-run-baseline-troubleshooting-zh-TW.md) 沒有收。其餘的拒絕句子跟現場擷取共用，請查那份文件。

| 訊息（節錄） | 意思 | 做什麼 |
|---|---|---|
| `The selected recordings were taken on different wavelength axes …` | 選到的錄製**波長軸不同**（點數或起迄波長不同），合起來的基準沒有意義 | 只選同一軸的錄製。軸是從 CSV 標頭讀的，跟有沒有 sidecar 無關 |
| `only {n} usable frames across the selected windows, fewer than the {60} required` | 所有視窗**加總**不足 60 幀 | 放寬視窗，或再加一份錄製（流程 B） |
| `none of the selected recordings ran process {X}, which is the class this ratio measures (they are: …)` | 這條比值只量製程 X，但選到的錄製裡沒有 X | 見[附錄 A](#附錄-a多製程站台分類器開啟時) |
| `Every selected recording was set aside by the consistency check.` | 每一份都被判為異類 | 錄製之間差異太大，多半是操作點根本不同。重新挑檔，不要用 `Keep anyway` 硬推 |

其餘會出現在 `No baseline for:` 的句子（沒有可用幀、SNR 不足、基準不夠遠離 0），**意思與處置和現場擷取完全相同**，查 troubleshooting 文件。

## 16. 現行版本的限制

下列是**目前實作的限制**，不是設計原則——程式擴充時它們可能改變。改版時只要改這一節。

| 限制 | 現況 |
|---|---|
| 最少幀數 | 固定 **60**，所有視窗加總，**操作員不可調** |
| 異常錄製門檻 | 固定 **5 σ**，**不可調**；需要至少 3 份錄製才啟動 |
| 一個檔一段 | 沒有「新增視窗」的控制項，每次選取都是取代 |
| 多操作點 | 一條 Golden Run 只描述**一個**穩定操作點。多步驟製程要每個 step 各一份基準、人工切換 |
| 製程分類 | 只顯示在 `State` 欄，**不能篩選、不能人工覆寫**判定結果 |
| Build 結果不會失效 | 改勾選／視窗／`Keep anyway` **不會**使上次 Build 的結果失效，`Save` 仍可按且存的是舊結果 |
| 掃描會被靜默作廢 | 改 Ratio Setup／波長修正／分類器／觸發門檻後，既有掃描**沒有任何提示**就不再正確 |
| `Refresh` 會清空 | 改日期或按 Refresh 會清掉所有掃描、勾選、視窗與結果 |

> 其中「**改完要重按 Build**」同時也是第 [2](#2-角色與分工) 節的硬性動作——它會直接造成存錯基準線，不能只放在這一節讓人自己想起來。

## 附錄 A：多製程站台（分類器開啟時）

啟用 Process Classifier 後，**每個比值只從自己 class 的錄製取樣**。`MinFrames = 60` 是按取樣後的結果算的，等於**每個 class 各自要湊滿 60 幀**。

**流程照舊走[流程 B（跨檔）](#8-流程-b跨檔合併建基準)**——單一 class 的一次 step 很難自己湊滿，跨檔就是它的流程。只多兩件事：

### A.1 掃描後按 class 盤點

`State` 欄會顯示 `{製程名} · {幀數} frames, {秒數} s`。這是**唯一**顯示 class 的地方：沒有 class 欄位、沒有篩選、不能人工改判。

盤點方式：對照第 [4](#4-前置二站台比值對照表) 節的表，逐一確認**每一個有比值在用的 class**，勾選的錄製裡都有它，而且該 class 的幀數加總 ≥ 60（建議 ≥ 120）。

兩種 `State` 要注意：

- **`Unknown ·  …`** —— 沒有規則match得上，或錄製在判定幀之前就結束了。這份錄製**任何 class-scoped 的比值都用不到**。
- **沒有 class 前綴** —— 分類器沒有啟用，或設定不可用。這時所有比值都適用所有錄製（等同單製程）。

### A.2 缺 class 時的處置

結果面板會具名拒絕：`none of the selected recordings ran process {X}, which is the class this ratio measures (they are: …)`。

對照第 4 節的表看那條比值的 **Role**：

| 缺的比值 Role | 判斷 | 做法 |
|---|---|---|
| **`Alarm`** | **NO-GO** | 補錄那個製程的錄製再重建。存下去等於**那個製程整段沒有洩漏監測**，而 Leak Monitor 分頁上看不出是缺錄檔還是比值本身壞了 |
| `TrendOnly` / `Guard` | GO（有條件） | 本來就不參與警報，可以先存，**紀錄裡註明待補** |

### A.3 其他會按 class 分開算的東西

這幾項都只拿**同 class** 的錄製比較，所以數字比單製程站台少是正常的：

- **異常錄製檢查**：需要同一 class 內至少 3 份錄製
- **檔間差距**、**視窗穩定度**、**回套檢查**：不同 class 的錄製互不比較（否則別的製程的電漿會讓每一項看起來都很糟）
