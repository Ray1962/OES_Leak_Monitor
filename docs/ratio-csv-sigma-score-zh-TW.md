# Ratio CSV 的兩個數值欄：`_pctBaseline` 與 `_sigmaScore`

本文說明 `{prefix}_Ratio_{MMddHHmmss}.csv` 裡每個 ratio 佔的兩個數值欄位是什麼、怎麼算出來的，
以及為什麼其中一種欄位用 σ 標度而不是百分比。範例取自
`C:\DualOES\202608\19\P_Ratio_0819175504.csv` 的 `N2 337.1 [R_102ba093]`。

程式碼位置：`src/OES_Leak_Monitor/RatioMonitor.cs`（計算）與
`src/OES_Leak_Monitor/RatioCsvLogger.cs`（寫檔）。本文引用的行號以撰寫當時
（2026-08-27）的原始碼為準。

---

## 1. 兩個欄位的關係

每個 ratio 在 CSV 裡佔**兩欄**，欄名都是 `{顯示名稱} [{key}]`，第二欄再加後綴：

| 欄位 | 內容 | 單位 | 用哪個值算 |
|---|---|---|---|
| `… [R_xxxx]` | 該幀**原始監測值**（`RatioSnapshot.RawRatio`），未平滑 | ratio 模式為無因次比值；absolute 模式為 counts | 當幀 |
| `… [R_xxxx]_pctBaseline` | `ema / baseMean × 100` | % | EMA 平滑值 |
| `… [R_xxxx]_sigmaScore` | 「高於基線多少個 σ」換算到 100/120/150 顯示軸 | 無因次（點數） | EMA 平滑值 |

同一列的兩欄**不是同一個量的兩種寫法**：一個是生值、一個是平滑後的偏離程度，連平滑狀態都不同。
寫入處 `RatioCsvLogger.cs:143`。

第二欄用哪個後綴，由 `RatioDefinition.ValueHasPedestal` 決定（`RatioCsvLogger.cs:221`），
而它的定義是「分子用 `RawMean` 抽取」（`LeakMonitorSettings.cs:88`）——
**與 ratio / absolute 監測模式無關**，除以參考線只是把台階等比例縮放，並不會把它移除。

### 為什麼帶台階的值不能用百分比

`RawMean` 不扣連續背景，讀數裡大部分是連續譜台階（pedestal）。此時
*(值 ÷ 基線) × 100* 會被壓縮到零點幾個百分比，100 / 120 / 150 三條參考線會落在幾十個 σ 之外——
看起來有警戒線，實際永遠打不到。所以這種欄位改用 σ 標度。

> 範例檔的六個 ratio 裡，`R_N2Ar`、`R_NOAr`、`R_8b2434ca` 是 `_pctBaseline`；
> `R_N2357Abs`、`R_102ba093`、`R_e97c9ee6` 是 `_sigmaScore`。兩者在圖上刻度相同、意義不同，
> **欄名是唯一的區分**。

## 2. `_sigmaScore` 的完整公式

`RatioMonitor.PercentOfBaselineDisplay()`（`RatioMonitor.cs:392`）：

```
                    20        ema − baseMean
score = 100 + ───────────  ·  ──────────────
                SigmaWarn      EffectiveSigma
```

四個輸入量的來源各不相同，這是理解這個數字的關鍵：

| 符號 | 來源 | 何時改變 |
|---|---|---|
| `baseMean` / `baseSigma` | Golden Run 捕捉時算出並存進 `settings.json`（`RatioMonitor.SetBaseline`，`:125`） | 只在換／重捕基線時 |
| `ema` | 本次量測串流的即時平滑值 | 每幀 |
| `EffectiveSigma` | `max(baseSigma, liveSigma)`（`:203`） | 每幀 |
| `20 / SigmaWarn` | ratio 設定（範例為 `sigmaWarn = 3` → 6.6667 點/σ） | 只在改設定時 |

### (a) `ema` — 為什麼不用生值

`RatioMonitor.cs:276-292`，時間常數 τ = `EmaTauSeconds`（範例為 5 s）：

```
dt    = 本幀時間 − 上幀時間        （範例檔約 2 s）
α     = 1 − exp(−dt / τ)          （2/5 → α = 0.32968）
delta = raw − ema
ema  += α · delta
```

α 由**實際幀間隔**算出，不是固定係數——所以 replay 用 20× 快轉、或曝光時間改變導致幀率變化時，
平滑的時間尺度不會跟著漂掉。第一幀沒有前值，直接 `ema = raw`、變異數歸零（`:276`）。

### (b) `liveSigma` — 現場雜訊估計

同一迴圈裡用 West (1979) 的 EWMA 變異數（`:291`）：

```
emaVar    = (1 − α) · (emaVar + α · delta²)
liveSigma = √emaVar
```

它量的是**生值繞著移動平均的散佈**，不需要保留視窗緩衝區，而且和 `ema` 用同一個 α，
所以兩者的時間尺度一致。特性：值一旦跳動，`delta²` 立刻把它推高；之後每幀乘 `(1 − α)` 衰減，
α = 0.33 時約 5 幀（10 s）掉一半。

### (c) `EffectiveSigma = max(baseSigma, liveSigma)`

取大的那個（`:199-203`）。基線是安靜時量的，如果現場比當時吵（電漿不穩、訊號接近雜訊），
就改用現場值——**門檻自動變寬**，避免自己的抖動觸發告警。

這一項是整個分數最容易被誤讀的地方，見 §3、§4 的例子。

### (d) `20 / SigmaWarn` — 為什麼是這個縮放

要讓 σ 標度和 `_pctBaseline` 共用同一張圖的 100 / 120 / 150 參考線：

- `ema = baseMean` → score = **100**（基線）
- `ema = baseMean + SigmaWarn·σ` → score = 100 + (20/3)·3 = **120**，剛好落在 Warn 參考線上

而狀態機比較的是 `_ema ≥ baseMean + SigmaWarn · EffectiveSigma`（`:338`）——分子分母同一組數，
所以 **score ≥ 120 與「越過 Warn 門檻」在數學上完全等價**，圖上看到的和引擎判斷的是同一件事。

### (e) 分母的動態：為什麼一個階躍會把 σ 撐大，又要多久才回來

§4.1 那段上升幾乎全由分母造成，所以分母的行為值得單獨推導一次。

#### 根因：`delta` 是「預測殘差」，不是「與真實平均的偏差」

```
delta  = raw − ema          ← ema 是落後的、會被自己拉動的平均
emaVar = (1 − α) · (emaVar + α · delta²)
```

這個估計器**沒有「平均值會移動」的模型**。它只看得到「這一幀離我原本的預期有多遠」，
至於那個距離是雜訊還是平均真的搬家了，它無法區分——於是一個階躍只能被登記成**一次巨大的雜訊**。
這不是實作瑕疵，是任何「不知道真實均值軌跡」的線上噪音估計器的本質限制。

#### 封閉解 1：階躍當幀的 `liveσ`

階躍前若已收斂（`emaVar ≈ 0`、`delta ≈ Δ`），代入遞迴式：

```
liveσ_peak = √(α(1 − α)) · Δ
```

α = 0.32968 時係數為 **0.4701**。範例檔 Δ = 268.076 → `liveσ = 126.02`，
與 CSV 反算值完全一致。係數在 α = 0.5 時取最大值 0.5，所以**任何 α 之下，
一個階躍最多被記成 Δ/2 的「雜訊」**。

#### 封閉解 2：階躍當幀的分數增量與 Δ 無關

分子增加 `α·Δ`，分母變成 `√(α(1−α))·Δ`，Δ 直接約掉：

```
score 增量 = (20/SigmaWarn) · α / √(α(1 − α)) = 4.675 點
```

| Δ | ema 增量 | liveσ | score − 100 |
|---|---|---|---|
| 10 | 3.30 | 4.70 | **4.675** |
| 50 | 16.48 | 23.51 | **4.675** |
| 268 | 88.35 | 125.99 | **4.675** |
| 5000 | 1648.40 | 2350.48 | **4.675** |

**一個 10 σ 的階躍和一個 1000 σ 的階躍，在發生的那一幀分數完全相同。**
換句話說，σ-score **在單一幀上永遠不可能告警**——這是公式的結構性質，不是參數調出來的。
（範例檔第 2 幀是 109.2 而非 104.7，是因為階躍前 `ema` 已經高於基線 85.0，
那部分偏移不受 Δ 約分影響。）

#### 封閉解 3：要多久才回得來

階躍後 `delta` 以 `(1−α)ⁿ` 幾何衰減，變異數的殘留項由 `(1−α)ⁿ` 主導，故
`liveσ ∝ (1−α)^(n/2)`——**σ 的衰減時間常數是 `2τ`，正好是平均的兩倍慢**。
分母掉回 `baseσ`（亦即抑制解除）所需時間：

```
t ≈ 2τ · ln(0.47 · N)        N = 階躍高度，以 baseσ 為單位
```

| 階躍高度 | `liveσ` 峰值 | 分母回到 `baseσ` | 相對 `ConfirmSeconds = 15 s` |
|---|---|---|---|
| 3 σ | 1.4 × baseσ | 3.4 s | 完全藏在確認窗內 |
| 6 σ | 2.8 × baseσ | 10.4 s | 仍在確認窗內 |
| 10 σ | 4.7 × baseσ | 15.5 s | 剛好等於確認窗 |
| 20 σ | 9.4 × baseσ | 22.4 s | 開始主導偵測時間 |
| 33 σ | 15.5 × baseσ | 27.4 s | ← 範例檔（實測 32 s） |
| 60 σ | 28.2 × baseσ | 33.4 s | 完全由噪音估計器決定 |

**這個機制的代價只落在遠高於門檻的大階躍上。** 對一個剛好在 3 σ 警戒線附近的變化，
它只花 3.4 s，早已被 15 s 的確認窗吸收；要到 N ≳ 9.5 σ 之後，
決定偵測時間的才從 `ConfirmSeconds` 換成噪音估計器。

#### 對緩慢變化幾乎沒有影響

以上全部針對**階躍**。真正的洩漏發展是漸進的：每幀 `delta` 都很小，
`liveσ` 停在白噪音的穩態值附近，`max()` 的地板 `baseσ` 接管，分母根本不動。
會製造大階躍的通常**不是洩漏**——電漿點燃、閘門開啟、配方換步、量測開始的第一幀——
也就是說，這個抑制打到的，多半正是那些不該告警的事件。

#### 順帶一提：穩態下 `liveσ` 略為低估

白噪音 σ 之下遞迴式的期望值為 `E[emaVar] = (1−α)·2σ²/(2−α)`，
α = 0.32968 時 `√E[emaVar] = 0.896 σ`（模擬的 `E[liveσ]` 為 0.856 σ，差額是 Jensen 不等式）。
`liveσ` 在穩態會低估真實散佈約 10–15 %——這也是 `EffectiveSigma` 必須以 `baseσ` 為地板、
而不是單獨採用 `liveσ` 的理由之一。

#### 為什麼不換一個估計器

| 做法 | 為什麼沒有採用 |
|---|---|
| 只用 `baseσ`（不估現場雜訊） | 現場比基線吵時會直接誤報，`max()` 存在的初衷就是防這個 |
| MAD／中位數等 robust 估計 | 需要視窗緩衝區與視窗長度的選擇；而且它壓抑離群值的同時，也會壓抑**真正的持續位移** |
| 相鄰差分（Allan variance 式） | 階躍一樣會落在差分上，沒有改善 |
| CUSUM／GLR 變化點偵測 | 這才是「階躍 vs 雜訊」的正解，但屬於另一套架構，不是在現有 EWMA 上調參數能得到的 |

目前的選擇是刻意的取捨：**寧可讓一個巨大的階躍慢 30 秒被承認，
也不要讓一個變吵的訊號自己把自己送進告警。** 代價已量化在上面的表裡。

## 3. 例子 A：乾淨數字手算

設 `baseMean = 300`、`baseSigma = 10`、`SigmaWarn = 3`、τ = 5 s、dt = 2 s
（α = 0.3297、6.6667 點/σ）。Warn 門檻 = 300 + 3×10 = **330**。

前三幀在基線上小幅抖動，第 4 幀起真的漲到 330 並停住：

|---|---|---|---|---|---|---|---|
| 1 | 300 | — | 300.00 | 0 | 0.00 | 10.00 | **100.00** |
| 2 | 302 | +2.00 | 300.66 | 0.9 | 0.94 | 10.00 | 100.44 |
| 3 | 298 | −2.66 | 299.78 | 2.2 | 1.47 | 10.00 | 99.86 |
| 4 | 330 | +30.22 | 309.74 | 203 | 14.26 | **14.26** | 104.56 |
| 5 | 331 | +21.26 | 316.75 | 236 | 15.37 | **15.37** | 107.27 |
| 6 | 329 | +12.25 | 320.79 | 191 | 13.84 | **13.84** | 110.02 |
| 8 | 330 | +6.17 | 325.86 | 107 | 10.34 | **10.34** | 116.67 |
| 9 | 330 | +4.14 | 327.23 | 76 | 8.69 | 10.00 | 118.15 |
| 12 | 330 | +1.25 | 329.16 | 24 | 4.94 | 10.00 | 119.44 |
| 18 | 330 | +0.11 | 329.92 | 2.3 | 1.51 | 10.00 | **119.95** |

（粗體 = `liveSigma` 接管分母的區間。）

三件事可以直接讀出來：

1. **基線 = 100，不論值本身是 300 還是 3000。** σ 標度把絕對水位吃掉了。
2. **第 4 幀值就到位了，分數卻只有 104.6。** 因為跳變本身把 `liveSigma` 從 0 撐到 14.3，
   `EffectiveSigma` 被它接管，分母變大。這是**設計上的遲滯**：值剛動的當下，
   我們對「這是雜訊還是真事」還沒有把握。
3. **第 9 幀起 `liveSigma` 衰減到 `baseSigma` 以下，分母鎖回 10**，分數才平順爬向 119.95 ≈ 120。
   搭配 `ConfirmSeconds = 15 s` 的持續確認，一次孤立的尖峰不會留下任何告警。

第 4→18 幀之間分數從 104 走到 120，用了約 30 s——這就是這套參數（τ = 5 s、確認 15 s）
換來的「不誤報」的代價。

## 4. 例子 B：真實資料逐步對帳

檔案：`C:\DualOES\202608\19\P_Ratio_0819175504.csv`，欄位 `N2 337.1 [R_102ba093]`。

由 CSV 反推出該 ratio 的基線為 `baseMean = 296.50`、`baseSigma = 9.27`。
Warn 門檻 = 296.5 + 3×9.27 = **324.3**，6σ Alarm = **352.1**。

> **為什麼要反推：** 該 ratio 已從現行 `settings.json` 刪除，2026-08-19 的資料夾裡也沒有
> `_config_*.json` 快照（`ConfigSnapshot` 是之後才加的）。一份沒有設定快照的 recording，
> 其 `_sigmaScore` 欄只能靠反推重建——這正是 `ConfigSnapshot` 存在的理由，
> 參見 `docs/leak-test-20260819-analysis.md` §9。

**第 1 幀 17:55:16，raw = 381.482**（本次量測的第一幀）

```

emaVar = 0 → liveσ = 0
effσ   = max(9.27, 0) = 9.27

       = 100 + 6.6667 × 84.982 / 9.27
       = 100 + 61.12 = 161.12         ← CSV: 161.119 ✓
```

**第 2 幀 17:55:18，raw = 649.558**（dt = 2 s，α = 0.32968）

```
emaVar = (1 − 0.32968) × (0 + 0.32968 × 268.076²) = 15 881.5
liveσ  = 126.022                                    ← 被這一跳撐大 13.6 倍
```

**生值從 381 跳到 650（+70 %），分數卻從 161 掉到 109。**

**第 3 幀 17:55:20，raw = 638.851**

```
ema   = 469.861 + 0.32968 × 168.990 = 525.574
liveσ = 130.218                                     （還在高檔）
score = 100 + 6.6667 × (525.574 − 296.5) / 130.218 = 111.73    ← CSV: 111.729 ✓
```

### 4.1 為什麼 17:55:18 → 17:55:50 分數從 109 爬到 310

這 32 秒是整個檔案最容易被誤讀的一段：**分數翻了將近三倍，而訊號本身其實在緩慢下降。**
逐幀展開（最後一欄是反事實對照：假設分母固定用 `baseSigma = 9.27` 會是多少）：

**生值在這段期間從 649.6 一路降到 599.2（−8 %）。分數卻上升了 22.9 倍。**

#### 把上升拆成兩個因子

分數的偏離量 `score − 100` 是一個分數式，兩端各自變化：

```
score − 100 = 6.6667 × (ema − baseMean) / EffectiveSigma
                        ↑ 分子              ↑ 分母
17:55:18 →  17:55:50：
   分子   173.4 → 306.3   ＝ ×1.77      （EMA 還在追趕階躍）
   分母   126.02 → 9.71   ＝ ÷12.98     （liveσ 從跳變的餘波衰減回基線水準）
   合計   9.17 → 210.2    ＝ ×22.9      （＝ 1.77 × 12.98 ✓）
```

取對數看貢獻比例：**σ 衰減佔 82 %，EMA 追趕只佔 18 %**。
也就是說，這段上升**主要不是訊號變化，是噪音估計器在收斂**。

#### 兩個時間常數

（封閉解與推導見 §2(e)；這裡只對範例檔取數。）

| 過程 | 時間常數 | 這段期間走完了嗎 |
|---|---|---|
| `ema` 追上階躍 | τ = 5 s | 到 17:55:34（階躍後 16 s ≈ 3τ）已收斂，`ema − base` 之後只在 322 → 306 之間緩降 |
| `liveσ` 衰減 | **2τ = 10 s** | 慢一倍，是它決定了整段的長度 |

`liveσ` 的衰減率可以直接從遞迴式讀出來：小 delta 時 `emaVar ×= (1 − α)`，
所以 `liveσ ×= √(1 − α)`。dt = 2 s、α = 0.32968 時，每幀 ×0.8187，
折合每秒 ×0.9048 = `exp(−1/10)`——**σ 的衰減時間常數正好是 2τ**。
從 126.02 掉到 9.27 需要 `ln(13.59) × 10 s ≈ 26 s`；實測 34 s，
多出來的部分是期間殘餘的 delta 仍在往變異數裡餵料。

#### 反事實對照欄說明了什麼

最後一欄假設我們一開始就知道真正的噪音水準（`σ = baseSigma = 9.27`）。
那樣的話分數在 17:55:18 就已經是 **224.7**，17:55:26 就到 321，之後幾乎是一條平線。
**真正的資訊在第一幀就已經到齊了**：這次量測的水位比 Golden Run 基線高
`306 / 9.27 ≈ 33 σ`，分數的天花板 ≈ 320 就是這個 33 σ 的換算值（100 + 6.6667 × 33）。

那 32 秒的爬升，是 `EffectiveSigma = max(baseσ, liveσ)` 這條保護規則的代價：
階躍自己製造的 `liveσ = 126`（比基線 σ 大 13.6 倍）把訊號蓋住，直到它衰減掉為止。
這是**刻意的**——引擎在階躍剛發生時無法區分「真的漲了」和「訊號開始劇烈抖動」，
於是先假設是後者，把門檻放寬，等雜訊估計收斂再說。

#### 與告警時序完全對上

同一條規則也解釋了 `OverallState` 的時間點，可以拿來當作交叉驗證：

- 分數在 **17:55:26** 首次越過 120（＝ `ema` 首次 ≥ `baseMean + 3·effσ`，`RatioMonitor.cs:338`）
- `ConfirmSeconds = 15 s` 的持續確認
- `OverallState` 在 **17:55:42** 轉為 `Warning`——26 + 15 = 41，下一幀 42 ✓

（該幀其他 ratio 都遠低於各自的門檻：`R_N2Ar` 的 `_pctBaseline` 約 50–56，
兩個 `_sigmaScore` 分別為 42.5 與 5，所以 `Warning` 完全來自 `R_102ba093`。）

#### 這段的正確讀法

1. **不要把 109 → 310 讀成「洩漏在這 32 秒內惡化了 3 倍」。** 生值是往下走的。
2. **不要把 17:55:18 的 109.2 讀成「接近基線」。** 那一幀實際上已經在基線之上約 19 σ
   （173.4 / 9.27），只是被自己造成的 `liveσ` 壓成 109。
3. **穩定後的水位才是結論**：約 320 分 ＝ 33 σ ＝ 生值約為基線的 2.0 倍。
   對照 `docs/leak-test-20260819-analysis.md`，這一天的操作點本來就與 Golden Run
   捕捉時的操作點不同，這個 33 σ 主要反映的是**基線不適用於這次量測**，
   而不是 32 秒內發生了什麼事。

#### 反向的同一件事

同一段檔案稍後出現鏡像的情形，機制完全相同：

```
17:56:30  raw=544.3  ema=548.3  effσ= 9.27  score=281.1   ← 分母已鎖在 baseSigma
17:56:32  raw=277.2  ema=459.0  effσ=127.5  score=108.5   ← 值掉一半，σ 再次被撐大
17:56:34  raw=146.3  ema=355.9  effσ=180.3  score=102.2
```

生值崩掉 73 %，分數卻只從 281 掉到 102，而且是**因為分母變大**而不是因為分子歸零。
**分數回到 100 附近不代表回到基線。** 要判斷方向，永遠要把生值欄並排看。

> 上面兩張表的每一個 `score` 欄都是依 §2 的公式重算的，不是從 CSV 抄的。
> 整檔 41 個有值的列全部重算後，與 CSV 的最大差為 **0.008 點**——公式與反推參數確認一致。

### 重建方法（可用於其他檔）

若 CSV 有值但基線已不可考，可用兩幀聯立解出 `baseMean`，再用首幀（`liveσ = 0`，
分母必為 `baseSigma`）解出 `baseSigma`：

1. 依 §2(a)(b) 從生值欄重算 `ema` 與 `liveσ`（需知道 τ 與 `SigmaWarn`）。
2. 取兩幀 `liveσ > baseSigma` 的列，`score − 100 = k·(ema − m)/liveσ` 兩式相除消去 `k`，解 `m`。
3. 以首幀 `score − 100 = k·(ema − m)/S` 解 `S`。
4. 用全部列回算驗證——誤差應在 0.01 點以內，否則 τ 或 `SigmaWarn` 猜錯了。

## 6. 空白與邊界情況

| 情形 | CSV 表現 | 程式位置 |
|---|---|---|
| 電漿閘門關閉／無電漿 | 兩欄皆空，並且 `_hasEma = false`（平滑重新開始，不會跨越空窗接續） | `:250-266` |
| 尚未有 Golden Run 基線 | 分數欄空（NaN），生值欄仍有值 | `:394` |
| 有基線但 σ = 0（基線與現場都無散佈） | 退回 `ema / baseMean × 100`，避免除以零留下空洞 | `:401` |
| SNR 低於 `MinSnr` | **趨勢照畫**（兩欄都有值），只是不參與 Warn/Alarm 判定 | `:307-328` |

最後一列值得強調：**分數欄有數字不代表該幀有參與告警判斷**。
要看那一幀是否真的被採信，得配合 `OverallState` 欄與系統記錄檔。

## 7. 讀這欄的三條守則

1. **看穩定後的水位，不看跳變當下。** 值一旦階躍，分數要 `2τ × ln(liveσ/baseσ)` 的時間
   才反映真實高度（範例檔是 32 s，見 §4.1）。這段期間分數是被自己造成的噪音估計壓低的，
   **上升或下降都不代表製程在變**。
2. **分數的變化不等於製程的變化。** 分子（`ema − baseMean`）和分母（`EffectiveSigma`）
   都會動，而分母動得更快。要判斷方向，把生值欄和分數欄並排看：
   生值升、分數卻降 → 分母主導；生值平、分數卻爬 → σ 在衰減（§4.1）；兩者同升 → 真的在漲。
3. **跨檔比較分數要先確認基線相同。** 分數是相對於某一次 Golden Run 的 `baseMean`/`baseSigma`；
   換過基線之後，同樣的 120 是完全不同的物理狀態。
