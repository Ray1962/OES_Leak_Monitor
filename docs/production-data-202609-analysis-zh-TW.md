# 生產機台製程資料分析(2026-09-03 / 08 / 10)

`C:\DualOES\202609\03`、`08`、`10` 共 119 筆全譜錄檔,全部來自**生產機台**的日常批次。

這份分析原本要比照 `leak-test-20260904-analysis-zh-TW.md` 做,但那份的核心 —— 劑量曲線、`k`、`φ_min` ——
需要每筆錄檔的**已知漏氣量**(09-04 每筆都有 `notes.txt` 記 dosing valve index)。這三天沒有任何
漏氣紀錄,也**沒有刻意引入漏氣**(2026-09-17 確認),所以那一套做不了。

這三天資料能回答的是另一個更急的問題:**09-08 與 09-10 的 Leak Monitor 整天 Alarm,到底有沒有漏?**

> **一句話結論**:**沒有漏。** 正常製程 C 的 N₂ 337 / CO 330 三天都在 0.0186–0.0188,
> 比 8 月的無漏參考還低 5 %,而規格大小的漏氣會讓它變成兩到三倍。
> 整天 Alarm 是 **09-03 21:01 一次 10 秒的 Golden Run 重錄**造成的 —— 它錄在一段**沒有氬氣的製程 A** 上,
> 丟掉了全部三條比值基準,只留下三條 σ 僅 1 % 的絕對強度基準,之後每一段 B、C 都是數百 σ。
>
> 順帶發現一件會直接打到計畫的事:九月出現了一個**低氬的 C 變體(C′)**,它的 N₂/CO 比正常 C 高 24 %,
> 超過 P3′ 的逐幀 Alarm 門檻。它可以用 **Hα 656.5 / O 616.0 > 6.25** 分出來,但判定時間要拉長到第 8 幀。

## 4. 新的 C 變體:C′

### 4.1 它長什麼樣

§2.3 表格的最後一列:**Ar 750 從 43–48 k 掉到約 33.6 k,N₂/CO 跳到 0.0232**。
它不是結垢的延續(結垢是每段掉約 2 %,這裡一次掉 22 %),而是一個不同的步驟。

| | n | Ar 750 | N₂/CO(固定取樣點) | 組內散度 |
|---|---|---|---|---|
| 正常 C(九月) | 42 | 42.8–48.5 k | 0.01870(0.0182–0.0197) | 1.8 % |
| **C′(九月)** | 9 | 33.6–35.6 k | **0.02310**(0.0221–0.0235) | 2.1 % |
| 8 月 | 74 | — | — | 只有 1 筆疑似 C′ |

它出現在**批次尾端的一到兩個 C 段**,九月三天每一天都有,8 月幾乎沒有。已確認是**刻意的配方步驟**
(2026-09-17)。

### 4.2 為什麼這件事重要

**C′ 比正常 C 高 +23.5 %,超過計畫 P3′ 的逐幀 Alarm 門檻(18.2 %)。** 如果照計畫把 `R_N2CO_C` 設成逐幀 Alarm,
而分類器把 C′ 當成 C,**每一批都會誤報**。

跨批次層不受影響 —— 它只取每批**第一個** C,而那一段永遠是正常的高氬 C(§2.2)。
這是「批次錨點取第一段」這個設計選擇的又一個理由。

### 4.3 找分類規則:兩次差點下錯的結論

**第一次看,現有的三個比值都和 C 重疊**,而 C′ 的 Ar 與 O 同時降到約 0.70 倍,
看起來就是「同一種氣體配比、只是放電較弱」—— 比值不會動。絕對強度又不能拿來分類
(結垢本身就會讓它變),所以改成**全譜搜尋**:取九月每個 C 段的中位光譜,找出 95 條峰,
兩兩相除,以「兩組之間的空隙 ÷ 正常 C 的散度」排序。

結果**最好的比值也只分得開 0.89 σ**。差一點就寫成「沒有穩健的判別方式」。

問題出在標註。C′ 是用「Ar 750 比**前一段** C 掉超過 15 %」來標的,而 09-03 下午有**兩段 C′ 連在一起** ——
第二段只比前一段低 4 %,被標成了正常 C。再加上 09-03 晚上那批不同配方(§1 第 2 點)混在 C 組裡。
改成「比**這一批正常 C 的基準**低 15 %」並排除那一批之後,全譜最佳的幾條變成:

| 比值 | 分離度 |
|---|---|
| UV 265.95 / 251.62 | 13.5 σ |
| **Hα 656.48 / O 616.04** | **13.0 σ** |
| Hα 656.48 / 668.12 | 12.9 σ |
| Hα 656.48 / 687.54 | 11.6 σ |
| 411.70 / 419.76 | 10.6 σ |

**而同一個錯也污染了第一眼的判斷。** 用正確的標註重看那三個現有比值:

| 比值 | 正常 C | C′ | |
|---|---|---|---|
| Ar 750 / O 777 | 1.415–1.461 | 1.441–1.475 | **真的重疊** |
| Hα 656 / O 777 | 0.130–0.141 | 0.151–0.156 | **分得開** |
| CO 608 / Ar 811 | 0.083–0.096 | 0.099–0.104 | 勉強分得開 |

所以「現有的比值分不開」只對 Ar/O 成立。

> **一筆標錯,兩個結論同時被翻過來。** 做任何分群分析之前,
> 先檢查標註規則對**連續出現**的樣本是不是成立。

### 4.4 選哪一條

分類器是**依序比對、第一條成立就採用**的規則清單,不能寫「是 C 而且 X > T」。
所以 C′ 規則必須**排在 C 規則前面**,而它的比值**不能讓 A 或 B 也成立**。
這一條件要拿**所有**A、B 段來驗,不能只看九月那幾段:

| 候選 | A | B | C | C′ | 能放第一條? |
|---|---|---|---|---|---|
| **Hα 656.48 / O 616.04** | ≤ 1.77 | ≤ 3.79 | 5.45–5.73 | 6.57–6.76 | **可以** |
| Hα 656 / O 777(現有) | 0.037–0.059 | 0.089–**0.523** | 0.130–0.141 | 0.151–0.156 | 不行:8 月有一段 B 到 0.523 |
| 411.70 / 419.76 | 1.65–1.91 | 1.70–2.28 | 1.08–1.15 | 1.28–1.32 | 不行:A、B 比 C′ 還高 |
| UV 265.95 / 251.62 | 0.26–0.60 | 0.12–0.20 | 0.70–0.76 | 0.94–1.06 | 不建議:紫外端結垢最嚴重 |
| Hα / 668、Hα / 675、607 / 603 | 分母 ≤ 50 | 分母 ≤ 50 | — | — | 不行:A、B 上算不出來 |

Hα/O616 的 A、B 上限是**8、9 月全部 128 段 A、87 段 B 在第 8 幀的單幀最高值**;
離門檻 6.25 分別差 3.5 倍與 1.6 倍。C、C′ 兩欄是九月的 10–30 s 中位數。

**留一天驗證**(用兩天定門檻、第三天測):三個組合**全部零錯誤**。

### 4.5 判定時間:這是分類器最容易出錯的地方

上面用的是 10–30 s 中位數,但**引擎只拿電漿開始後第 `DecideAfterFrames` 幀的那一幀**做判定。
改用單幀重驗,門檻 **6.25**:

| 判定幀 | 1.24 fps(約幾秒) | 錯誤 | 1.66 fps(約幾秒) | 錯誤 |
|---|---|---|---|---|
| 3(計畫現值) | 1.6 s | **4 / 90** | 1.2 s | **2 / 19** |
| 4 | 2.5 s | 0 / 90 | 1.9 s | **1 / 19** |
| 5 | 3.3 s | 0 / 90 | 2.5 s | 0 / 19 |
| **8(建議)** | **5.7 s** | **0 / 90** | **4.3 s** | **0 / 19** |
| 10 | 7.4 s | 0 / 90 | 5.5 s | 0 / 19 |

**計畫寫 `DecideAfterFrames = 3`「≈ 6 s」,那是 8 月 0.51 fps 的換算。** 這個設定以幀計,
所以幀率一變,它代表的時間就悄悄變了 —— 在九月的 1.24 / 1.66 fps 下,3 幀只剩 1.6 / 1.2 秒,還在點火暫態裡。

**好消息是原本的 A/B/C 兩條規則完全不受影響**:從第 1 幀到第 8 幀、兩種幀率,109 段全部判對。
它們的比值相差好幾倍,暫態搬不動。只有 C′ 這條 C 與 C′ 只差約兩成的規則需要等暫態過去。

**餘裕要誠實說**:在第 5–10 幀之間,正常 C 單幀最高到 **6.07**,C′ 最低 **6.40**。
門檻 6.25 距兩邊各約 3 %。夠用,但不寬 —— 累積更多批次後要重驗(§7)。

### 5.1 與 09-04 §4.2 的數字差 8 %

已經不存在,無法追出原因。

**不影響偵測結論** —— 門檻與漏氣響應都是相對變化。但它說明一件事:分析腳本不留下來,
下一次連「數字對不對得上」都查不了。本文的腳本因此放進了 repo(附錄)。

### 5.2 09-10 重開後幀率從 1.24 升到 1.66 fps

取像設定前後完全相同(80 ms × 5 次硬體平均,理論上限 2.5 fps)。重開前每幀約 800 ms,
重開後約 600 ms —— **有約 200 ms 不是花在光譜儀上**。09-03 到 09-10 重開前一直是 1.24 fps,
不是逐漸變慢,而是重開時一次跳上去。原因從這份資料無法判斷。

它直接影響 §4.5:**`DecideAfterFrames` 換算成秒數,會隨這個 200 ms 改變。**

### 5.3 現場沒有登錄波長修正

三份快照的 `wavelengthCorrections` 都是空的。8 月量到的 **+0.30 nm 軸偏移**從未登錄,
所以現場那幾條比值(中心寫的是型錄波長 337.1、750.4)的窗口都偏了 0.3 nm。
計畫 §4.2 的站點設定已經把偏移寫進 `centerNm`,換成那一套之後這件事自然消失。

依先後順序做。

### 6.1 目前的 Alarm 不是漏氣

可以停止據此處置。但也**不要**把 Leak Monitor 關掉或降低門檻 —— 問題在基準線,不在判定。

### 6.2 更新現場程式到 `b3d00fe` 之後的版本

沒有分類器,任何基準線都只能用一份數字判三種製程,同樣的事會再發生。

### 6.3 套用站點設定,並加上 C′

在計畫 §4.2 / §4.3 的站點設定上,把下面這條規則**放在規則清單的第一條**,並把判定幀改成 8:

```jsonc
"processClassifier": {
  "enabled": true,
  "decideAfterFrames": 8,
  "rules": [
    { "className": "Cp", "displayName": "Ha656/O616",
      "numerator":   { "label": "Ha 656.3", "centerNm": 656.48, "halfWidthNm": 0.70,
                       "baselineGapNm": 1.30, "baselineWidthNm": 1.10, "mode": "PeakHeight",
                       "peakSearchHalfWidthNm": 0.0 },
      "denominator": { "label": "O 615.8",  "centerNm": 616.04, "halfWidthNm": 0.70,
                       "baselineGapNm": 1.30, "baselineWidthNm": 1.10, "mode": "PeakHeight",
                       "peakSearchHalfWidthNm": 0.0 },
      "op": "GreaterThan", "threshold": 6.25 }
    // 其後接計畫 §4.3 原有的 C、A 兩條規則,順序不變
  ],
  "classes": [ /* 原有 A、B、C,另加 { "name": "Cp", ... } */ ]

```

類別名稱用 **`Cp`**(本文稱 C′):它會出現在比值 CSV、系統日誌與 SECS 的製程類別欄位,
識別字裡不要放撇號這類符號。

`R_N2CO_C` 維持 `processClass: "C"`,只判正常 C。若要監看 C′,另建一條 `processClass: "Cp"` 的
`R_N2CO_Cp`,**不要**與 C 共用基準,而且在有 C′ 的受控漏氣資料之前先設成 `TrendOnly`(§7 第 3 點)。

> ⚠️ `decideAfterFrames: 8` 是依 1.24 / 1.66 fps 驗證的。**幀率若再變(改積分時間、平均次數,
> 或 §5.2 那種原因不明的跳動),這個數字要重新換算**,目標是閘門開啟後至少約 4 秒。

### 6.4 用 Baseline Builder 分製程重建基準

**不要再用 10 秒的現場擷取。** 照 `baseline-builder-sop-zh-TW.md` 附錄 A(多製程站台)做。
C′ 每批只有一到兩段,**一定要跨檔合併**(流程 B)。09-08 那 23 段正常 C 的日內散度只有 1.5 %,
是很好的建置素材。

### 6.5 把 `goldenRunCaptureSeconds` 改回 60

10 秒在 1.24 fps 下只有約 12 幀,而且這次兩個 10 秒視窗,一個落在錯的製程、一個落在空檔裡。

## 7. 這份資料不能回答的事

1. **靈敏度。** 沒有已知漏氣量,這三天只能說「沒漏」,不能說「漏了會看到多少」。那仍然只有 09-04 的外推。
2. **C′ 規則的長期穩定性。** 9 段 C′、42 段正常 C、三天、單幀餘裕約 3 %。視窗清洗前後、
   更換光學件之後會不會移動,**要在累積兩到三週資料後重驗 §4.5 的表**。
3. **C′ 對漏氣的響應。** 它的放電較弱,N₂/CO 的斜率 `k` 可能和正常 C 不同。
   在有 C′ 的受控漏氣資料之前,**C′ 不宜單獨設 Alarm**,建議先用 `TrendOnly`。
4. **09-03 晚上那一批(A 108 s / C 78 s)是什麼配方。** 只有一批,本文排除在外。
5. **§5.1 的 8 % 差距**與 **§5.2 的 200 ms** 的原因。

## 8. 對程式的影響

**沒有必須修的 bug。** 這次發生的兩件事,程式都照設計運作:

- 09-10 的 10 秒空擷取被正確**拒絕存檔**(`GoldenRunEmpty`),沒有把事情變得更糟。
- 09-03 那次會丟掉三條基準的同名重錄,**新版程式會先跳確認視窗**(`NeedsConfirmation`)。
  現場的舊版有沒有這道防護,從資料無法確認。

但有一個**以幀計數的設定悄悄改變語意**的問題值得記下來:`DecideAfterFrames` 的註解與計畫都寫
「≈ 6 s」,那個等號只在 0.5 fps 成立。目前的 A/B/C 規則強到不受影響,所以沒有出事;
一旦加入像 C′ 這樣兩類只差約兩成的規則,它就成了唯一決定對錯的參數。
若要處理,方向是**以秒數表達判定時間**,或至少在套用設定時,依實際幀率把換算出來的秒數寫進日誌。
