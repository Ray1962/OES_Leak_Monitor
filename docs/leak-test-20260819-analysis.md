## 1. 結論

1. **洩漏閥的作用看得到**。測試 1 在 **17:55:16.058** 那一幀，比值從無值變成有值、`N₂337/Ar750 = 0.01519`。
   之前 12 秒（6 幀）全部空白。那 12 秒對應現場描述的「電漿穩定約 10 秒」——**空白不是電漿沒亮，
   是閘門關著**。

2. **（最重要）save 門檻高於無洩漏時的電漿**。因此：
   - 無洩漏狀態**一幀都沒有被評估過**，比值檔那段全是空白；
   - 這個操作點**錄不出 Golden Run**——擷取時每一幀都會被閘門擋掉；
   - 監控只有在**漏得夠大、亮度夠高**時才開始判斷，也就是說它在該預警的時候是靜止的。

3. **全光譜記錄錯過了整個轉態**。它比洩漏晚 **13.977 秒**開始（其中 12 秒是閘門、2 秒是
   `StartConfirmSeconds`），第一幀已經是洩漏後的第二幀。**沒有任何一幀是洩漏前的原始光譜。**

4. **幀率是 2.0005 秒一幀**，由光譜儀決定（不是 polling）。整個洩漏轉態只佔 **1 幀**。
   而且 17:34 把積分時間從 200 降到 100，**幀率完全沒變，只是光少了一半**。

5. **`N2 337.1 [R_102ba093]` 監看的量有 76 % 是連續背景**（`RawMean` 不減背景）。它的讀數會跟著
   電漿亮度走，不只跟著氮走。

6. **100 單位 vs 50 單位是否分得出來，目前無法斷定**——見 [§6](#6-100-單位-vs-50-單位目前無法斷定)。

## 2. 17:55:16 的上升就是洩漏閥

`P_Ratio_0819175504.csv` 的開頭：

```
17:55:04  ,,,,,,  Idle     ← 6 幀（12 秒）全部空白
17:55:06  ,,,,,,  Idle
17:55:08  ,,,,,,  Idle
17:55:10  ,,,,,,  Idle
17:55:12  ,,,,,,  Idle
17:55:14  ,,,,,,  Idle
17:55:16  0.0151903, 50.83, ... 381.482, 161.12, ...  Normal   ← 洩漏閥打開
17:55:18  0.0171384, 52.98, ... 649.558, 109.17, ...  Normal
```

**空白列代表閘門關著，不代表電漿沒亮。** 決定性的證據是：空白的不只需要參考線的比值項，
連 `N₂ 358 absolute [R_N2357Abs]` 這個**只看 plasma gate 的絕對強度項**也是空的。
`PlasmaGate` 只有一個判準——整張 frame 的觸發量測是否高於 `SaveStartThresholdIntensity`——
所以那 12 秒就是「電漿亮著，但沒亮到門檻」。

12 秒（6 幀 × 2 秒）與現場描述的「電漿啟動穩定約 10 秒後再開洩漏閥」一致。

測試 2 同樣：18:01:11–18:01:27 共 9 幀空白（18 秒），18:01:29 出現第一筆值。

> **這一節推翻了本文初版的結論。** 初版把空白列讀成電漿未點燃，因而把 17:55:16 的跳升判定為
> 「點火」。判定的依據是 Ar 750 同時跳升——但在 540 torr 下通入空氣會改變放電本身，
> Ar 跟著變亮並不能證明是點火。見[附錄 C](#附錄-c修訂紀錄)。

## 4. save 門檻推算

實測基準：**暗態**（電漿熄滅後三幀）p99 = **77–79**。

**硬上界**：閘門在 17:55:16 打開，該幀 `Ar 750 = 25115`。亮態時 p99 : Ar750 = **0.4232**
（由 17:55:18 實測 p99 = 12826、Ar750 = 30309 得到），所以該幀 p99 ≈ **10630**，
而它必須高於門檻 → **門檻 < 10630**。

**下界**由收檔行為約束。光譜檔尾端的 p99：

| t (s) | 72 | 74 | 76 | 78 | 80 | 82 | 84（末幀） |
|---|---|---|---|---|---|---|---|
| p99 | 11590 | 4965 | 5005 | 4927 | 77 | 78 | 79 |

| 門檻 | 無洩漏 p99 上限 | 開閥時最小跳幅 | 收檔是否合理 |
|---|---|---|---|
| 1000 | 1000 | ≥ 10.6× | ✓ 需 `StopConfirm` ≈ 5 s |
| 2000 | 2000 | ≥ 5.3× | ✓ ≈ 5 s |
| **4000** | 4000 | ≥ 2.7× | ✓ ≈ 5 s |
| 5000 | 5000 | ≥ 2.1× | ✗ t=74 (4965) 與 t=76 (5005) 會在門檻上下彈跳 |
| 10000 | 10000 | ≥ 1.06× | ✗ 需 `StopConfirm` ≈ 12 s（預設 3 s） |

**最自洽的區間是 2000–4900**：開閥時的亮度跳幅 2.1–5.3 倍（大，但在 540 torr 下改變氣體組成
足以切換放電模式的範圍內），收檔行為也解釋得通。

10000 只有在 `StopConfirmSeconds` 確實設在 10 秒以上時才成立。

> **注意**：以上全部假設 `TriggerMode = SpectrumPercentile`（99th）。**若現場其實用的是
> `Wavelength` 模式**（盯單一波長的強度），比較的量完全不同，上述推算全部要重做——
> 那時 10000 會變得非常合理。這是 [§9](#9-待確認事項) 的第一個問題。

## 5. 幀率：2 秒一幀，而且改積分時間沒有用

實測幀間隔 **2.0005 s**，抖動僅 ±2 ms（43 幀，min 1.999、max 2.002）。

**決定節奏的不是 polling。** 若 1005 ms 的輪詢在決定節奏，間隔只能是 1.005 s 或 2.010 s；
取 2.010 s 則 42 個間隔會累積成 84.42 s，實測是 84.020 s——差 400 ms，遠超過抖動。
實測值對齊的是 **1000.25 ms 的整數倍**，那是儀器自己的時鐘。

當天節奏變過三次：

| 時段 | 平均間隔 | 抖動 | 對應筆記 |
|---|---|---|---|
| 16:28 – 17:15 | 2.009 – 2.017 s | ±10 ms | integration = 200 |
| 17:20 – 17:27 | 1.210 s | | |
| 17:34:25 | 1.397 s | | 設定切換中 |
| **17:36 – 18:01** | **2.0002 – 2.0005 s** | **±2 ms** | integration = 100 |

**把積分時間從 200 砍到 100，幀率完全沒變（都是 2 秒），只是光少了一半。**

`2.0005 s = 10 × 200.05 ms`——每一發 100 ms 的曝光實際佔了 200 ms。而 17:34 之前的
`2.010 s ≈ 10 × 201 ms`，那時 integration 是 200，**每一發剛好就是曝光時間**。
最可能的差別是平均的做法：

| | 每發成本 | 10 發 | 符合 |
|---|---|---|---|
| **硬體平均**（晶片上累加，最後讀出一次） | 曝光時間 | 200×10 + 一次讀出 ≈ 2010 ms | 17:34 前 |
| **軟體平均**（每發各自讀出） | 曝光 + 讀出 | (100+100)×10 = 2000 ms | 17:34 後 |

讀出約 100 ms 且與曝光時間無關，所以**曝光設得越短，讀出佔的比例越高**。

**要確認**：Configuration 分頁的 `AverageMode` / `AcquireMode`。若是 `Software` / `Standard`，
改成 `Hardware` / `HardwareAverage` 後幀間隔應降到約 **1.01 s**——光量不變、時間解析度加倍。

**為什麼重要**：2 秒一幀時，整個洩漏轉態只有 1 幀，所以無法從波形判斷它是漸變還是階梯。
而且引擎裡的時間常數都是以 dt 計算的：EMA 的 `α = 1 − exp(−dt/τ)`、
`ConfirmSeconds`（15 秒 = 只有 7 幀）、σ/min 斜率。在 0.5 Hz 下這些都建立在很少的樣本上。

## 6. 100 單位 vs 50 單位：目前無法斷定

兩次測試在 0–72 秒（電漿全開段）的平均，皆為減掉連續背景後的峰高：

| 量 | 100 單位 | 50 單位 | 差 |
|---|---|---|---|
| N₂ 337 峰高 | 130.7 ± 8.7 (6.7 %) | 114.7 ± 8.6 (7.5 %) | +14.0 % |
| **N₂337/Ar750** | **3.533 ± 0.205** | **3.179 ± 0.220** | **+11.1 %** |
| NO237/Ar750 | 6.067 ± 0.228 | 5.534 ± 0.183 | +9.6 % |
| Ar 750 峰高（參考線） | 36 980 ± 435 | 36 060 ± 391 | +2.5 % |

方向對（開比較大的閥門讀數比較高），統計上也不是雜訊（對平均值而言約 7σ）。

**但這 11 % 無法歸因於洩漏閥**，因為當天 17:36 之後每一次 run 之間本來就在掉相同的幅度：

| 時間 | N₂337/Ar750 | 相對前一次 |
|---|---|---|
| 17:36:11 | 6.607 | — |
| 17:38:27 | 5.709 | −13.6 % |
| 17:41:50 | 5.043 | −11.7 % |
| 17:44:06 | 4.418 | −12.4 % |
| 17:46:34 | 3.933 | −11.0 % |
| **17:55:18** | **3.546** | **−9.8 %**（洩漏 100 單位） |
| **18:01:31** | **3.145** | **−11.3 %**（洩漏 50 單位） |

兩次洩漏測試之間掉 11.3 %，和前面每一次 run 之間掉的 9.8–13.6 % 沒有分別。

**要斷定就必須知道 17:36–17:46 那五次 run 是什麼。**

- 若它們**沒有開洩漏閥**（或閥門設定固定），那條下降曲線是某個與洩漏無關的趨勢，
  兩次測試的 11 % 就落在其中，分不出來。
- 若它們**本身就是遞減設定的洩漏測試**，那條曲線就是洩漏響應，結論完全相反——
  這批資料反而證明工具對洩漏量有良好的單調響應。

**這條曲線的成因目前也未知。** 本文初版把它歸因於「17:34 拆板子時開過大氣、殘留空氣被抽走」，
該解釋已被現場資訊推翻（拆板子不破真空）。目前只知道：

- 只有空氣來源的物種在掉（N₂ −57 %、NO −69 %，27 分鐘內），製程氣體 Ar 750、O 777、
  Ar 811 只掉 2–6 %；
- 在單次 run 內，N₂ 337 峰高掉 23.6 %，而旁邊 441 nm 的連續背景只掉 9.9 %——
  **氮掉的速度是背景的 2.4 倍**，所以不是純光路衰減，氮本身確實在減少。

### 7.5 測試 2 開頭的 `Warning` 不代表測試 2 有事

那是測試 1 留下的鎖存未 Acknowledge。

### 7.6 單次 run 內的衰減依波長排序

`P_OES1_0819175518` 的 0 → 72 秒：309 nm −17.7 %、337 nm −16.2 %、357.7 nm −15.1 %、

洩漏指標長期鈍化。

## 8. 重測程序

**先修設定：**

1. **調低 `SaveStartThresholdIntensity`。** 先設 **200**（約暗態 77 的 2.5 倍），
   `StartConfirmSeconds` 設 **0 或 1**。
2. 起電漿、**不開洩漏閥**，跑一分鐘，記下 `P_OES1_*.csv` 第一列的 p99——
   **那就是無洩漏電漿的真實亮度**。把門檻設成該值的一半左右。
   判準：電漿穩定後，Monitor 分頁的 recorder strip 應該一直是 Saving，比值檔不該有空白列。
3. **確認 `AverageMode` / `AcquireMode`**，若非硬體平均就改過去，幀間隔應降到約 1.01 s
   （[§5](#5-幀率2-秒一幀而且改積分時間沒有用)）。

**再測洩漏：**

4. **先錄無洩漏基準**，同一電漿條件下錄滿至少一分鐘，並用它擷取 Golden Run。
5. **每個閥門設定維持數分鐘**，不要用 80 秒的 run。建議序列：
   無洩漏 3 min → 50 單位 3 min → 無洩漏 3 min → 100 單位 3 min → 無洩漏 3 min。
   這樣既看得到階梯，也有前後對照，還能分辨「響應」與「趨勢」。
6. **不要跨越 step 切換**（t ≈ 74 s 那一次），或把監測限制在 step 1。
7. 若要用 337 nm 判漏，**把萃取方式從 `RawMean` 改成 `PeakHeight`**（實測 SNR 6.7，可用），
   真訊號才不會被連續背景稀釋 4 倍。

## 附錄 B：分析方法

譜線強度是用 `LineIntensityExtractor` 的演算法在 Python 裡重做一遍算出來的
（`PeakHeight`：峰值搜尋 ±1 nm、訊號窗 ±0.5 nm、兩側背景窗 gap 1 nm / width 1 nm、
線性內插連續背景；`RawMean`：不減背景、不搜峰，±0.5 nm 分數像素加權平均）。

該重做過的萃取器**先對照本機 `settings.json` 裡已存的 Golden Run 基準驗證過**：
用同一段時間窗重算 `N2 337.1 / Ar 750.4` 與 `uN2 335.5 / Ar 750.4`，結果與 app 實際存進去的
`mean`、`σ`、`sampleCount` **一致到顯示精度（Δ 0.00 %）**。驗證時發現必須套用
`LeakMonitorSettings.WavelengthCorrections`，否則會差 24.9 %。

**注意**：該驗證用的是開發機的 `settings.json`。8/19 的現場機台是另一組比值設定
（`R_N2Ar`、`R_NOAr`、`R_N2357Abs` 與三條自建項目），其波長修正表未知，
所以本文的「峰高」是用**未修正的目錄波長**萃取的。這對 §6、§7 的相對比較沒有影響
（同一套萃取套用在所有檔案上），但絕對值可能與 app 內部的讀數有系統性偏差。

本文所有「峰高」都是減掉連續背景後的值，除非明確標示 `RawMean`。

## 附錄 C：修訂紀錄

初版（2026-08-21）有兩個結論是錯的，因為缺少現場條件。兩者都已在本版更正，
記錄於此是因為錯誤本身有參考價值——它們是「只看檔案、不知道機台怎麼跑」會犯的典型錯誤。

**錯誤 1：把空白列讀成「電漿沒亮」。**
初版據此判定 17:55:16 的跳升是點火，並以「Ar 750 同時跳升」為證。
實際上空白列代表 `PlasmaGate` 關著（觸發量測低於 `SaveStartThresholdIntensity`），
電漿是亮著的；而在 540 torr 下通入空氣會改變放電本身，Ar 跟著變亮不能證明是點火。
**更正後這成了本文最重要的發現**（[§1](#1-結論) 第 2 點）：門檻高於無洩漏電漿。

**錯誤 2：把「17:34 拆掉觀察窗壓克力板」讀成「腔體開過大氣」。**
初版據此把整個下午的衰減解釋成殘留空氣被抽走（32 分鐘時間常數）。
實際上壓克力板在窗**外側**，拆它不破真空。該解釋已刪除，那條衰減曲線的成因目前**未知**，
列為 [§9](#9-待確認事項) 第 2 項。這也讓初版 §3「100 vs 50 分不出來」的論證降級為
**開放問題**（[§6](#6-100-單位-vs-50-單位目前無法斷定)）——觀察本身（兩次測試的差距等於
run 間的既有趨勢）仍然成立，但能不能據此下結論，取決於那五次 run 是什麼。
