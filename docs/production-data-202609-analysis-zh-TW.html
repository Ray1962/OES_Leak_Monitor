C:\DualOES\202609\03、08、10 共 119 筆全譜錄檔,全部來自生產機台的日常批次。

這份分析原本要比照 leak-test-20260904-analysis-zh-TW.md 做,但那份的核心 —— 劑量曲線、k、φ_min —— 需要每筆錄檔的已知漏氣量(09-04 每筆都有 notes.txt 記 dosing valve index)。這三天沒有任何 漏氣紀錄,也沒有刻意引入漏氣(2026-09-17 確認),所以那一套做不了。

這三天資料能回答的是另一個更急的問題:09-08 與 09-10 的 Leak Monitor 整天 Alarm,到底有沒有漏?

一句話結論:沒有漏。 正常製程 C 的 N₂ 337 / CO 330 三天都在 0.0186–0.0188, 比 8 月的無漏參考還低 5 %,而規格大小的漏氣會讓它變成兩到三倍。 整天 Alarm 是 09-03 21:01 一次 10 秒的 Golden Run 重錄造成的 —— 它錄在一段沒有氬氣的製程 A 上, 丟掉了全部三條比值基準,只留下三條 σ 僅 1 % 的絕對強度基準,之後每一段 B、C 都是數百 σ。

4.2 為什麼這件事重要

C′ 比正常 C 高 +23.5 %,超過計畫 P3′ 的逐幀 Alarm 門檻(18.2 %)。 如果照計畫把 R_N2CO_C 設成逐幀 Alarm, 而分類器把 C′ 當成 C,每一批都會誤報。

跨批次層不受影響 —— 它只取每批第一個 C,而那一段永遠是正常的高氬 C(§2.2)。 這是「批次錨點取第一段」這個設計選擇的又一個理由。

4.3 找分類規則:兩次差點下錯的結論

第一次看,現有的三個比值都和 C 重疊,而 C′ 的 Ar 與 O 同時降到約 0.70 倍, 看起來就是「同一種氣體配比、只是放電較弱」—— 比值不會動。絕對強度又不能拿來分類 (結垢本身就會讓它變),所以改成全譜搜尋:取九月每個 C 段的中位光譜,找出 95 條峰, 兩兩相除,以「兩組之間的空隙 ÷ 正常 C 的散度」排序。

結果最好的比值也只分得開 0.89 σ。差一點就寫成「沒有穩健的判別方式」。

問題出在標註。C′ 是用「Ar 750 比前一段 C 掉超過 15 %」來標的,而 09-03 下午有兩段 C′ 連在一起 —— 第二段只比前一段低 4 %,被標成了正常 C。再加上 09-03 晚上那批不同配方(§1 第 2 點)混在 C 組裡。 改成「比這一批正常 C 的基準低 15 %」並排除那一批之後,全譜最佳的幾條變成:

計畫寫 DecideAfterFrames = 3「≈ 6 s」,那是 8 月 0.51 fps 的換算。 這個設定以幀計, 所以幀率一變,它代表的時間就悄悄變了 —— 在九月的 1.24 / 1.66 fps 下,3 幀只剩 1.6 / 1.2 秒,還在點火暫態裡。

5.3 現場沒有登錄波長修正

三份快照的 wavelengthCorrections 都是空的。8 月量到的 +0.30 nm 軸偏移從未登錄, 所以現場那幾條比值(中心寫的是型錄波長 337.1、750.4)的窗口都偏了 0.3 nm。 計畫 §4.2 的站點設定已經把偏移寫進 centerNm,換成那一套之後這件事自然消失。

6. 對現場的建議

類別名稱用 Cp(本文稱 C′):它會出現在比值 CSV、系統日誌與 SECS 的製程類別欄位, 識別字裡不要放撇號這類符號。

R_N2CO_C 維持 processClass: "C",只判正常 C。若要監看 C′,另建一條 processClass: "Cp" 的 R_N2CO_Cp,不要與 C 共用基準,而且在有 C′ 的受控漏氣資料之前先設成 TrendOnly(§7 第 3 點)。

⚠️ decideAfterFrames: 8 是依 1.24 / 1.66 fps 驗證的。幀率若再變(改積分時間、平均次數, 或 §5.2 那種原因不明的跳動),這個數字要重新換算,目標是閘門開啟後至少約 4 秒。

6.4 用 Baseline Builder 分製程重建基準

不要再用 10 秒的現場擷取。 照 baseline-builder-sop-zh-TW.md 附錄 A(多製程站台)做。 C′ 每批只有一到兩段,一定要跨檔合併(流程 B)。09-08 那 23 段正常 C 的日內散度只有 1.5 %, 是很好的建置素材。

6.5 把 goldenRunCaptureSeconds 改回 60

10 秒在 1.24 fps 下只有約 12 幀,而且這次兩個 10 秒視窗,一個落在錯的製程、一個落在空檔裡。

7. 這份資料不能回答的事

  1. 靈敏度。 沒有已知漏氣量,這三天只能說「沒漏」,不能說「漏了會看到多少」。那仍然只有 09-04 的外推。
  2. C′ 規則的長期穩定性。 9 段 C′、42 段正常 C、三天、單幀餘裕約 3 %。視窗清洗前後、 更換光學件之後會不會移動,要在累積兩到三週資料後重驗 §4.5 的表。
  3. C′ 對漏氣的響應。 它的放電較弱,N₂/CO 的斜率 k 可能和正常 C 不同。 在有 C′ 的受控漏氣資料之前,C′ 不宜單獨設 Alarm,建議先用 TrendOnly。
  4. 09-03 晚上那一批(A 108 s / C 78 s)是什麼配方。 只有一批,本文排除在外。
  5. §5.1 的 8 % 差距與 §5.2 的 200 ms 的原因。

8. 對程式的影響

沒有必須修的 bug。 這次發生的兩件事,程式都照設計運作:

  • 09-10 的 10 秒空擷取被正確拒絕存檔(GoldenRunEmpty),沒有把事情變得更糟。
  • 09-03 那次會丟掉三條基準的同名重錄,新版程式會先跳確認視窗(NeedsConfirmation)。 現場的舊版有沒有這道防護,從資料無法確認。

但有一個以幀計數的設定悄悄改變語意的問題值得記下來:DecideAfterFrames 的註解與計畫都寫 「≈ 6 s」,那個等號只在 0.5 fps 成立。目前的 A/B/C 規則強到不受影響,所以沒有出事; 一旦加入像 C′ 這樣兩類只差約兩成的規則,它就成了唯一決定對錯的參數。 若要處理,方向是以秒數表達判定時間,或至少在套用設定時,依實際幀率把換算出來的秒數寫進日誌。
