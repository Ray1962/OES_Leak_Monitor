OES Leak Monitor × EAP 製程事件介面規格（SECS，方案 2b）

對象： 廠內 EAP 平台廠商（開發與維運）。 目的： 定義 OES Leak Monitor 怎麼向 EAP 取得主機台 PM3 的製程事件：EAP 以 SECS equipment 身分提供製程視窗的狀態變數，並以 S6F11 轉發主機台事件；OES 以 host 身分連入讀取。 狀態： 2026-10-27。OES 端已依本規格實作。本規格取代 2026-10-26 的 TCP 文字行規格（eap-tool-event-tcp-spec-zh-TW），拿到舊版的請改依本規格。 一句話： OES 主動連到 EAP（預設 10.2.3.120:20347），上線後啟用兩個 CEID、讀 S1～S7，之後每 30 秒再讀一次；主機台每有一筆事件，EAP 就以一個固定的轉發 CEID 送 S6F11，報告內容固定為「主機台 CEID、EAP 收到的時間、序號」。

1. 背景

OES Leak Monitor 裝在主機台 PM3 上，用電漿光譜偵測腔體漏氣。PM3 會交替執行不同製程（Chamber Process／precoat、Chamber Clean 等），每種製程的光譜完全不同。OES 必須知道當下這一幀光譜屬於哪個製程，才能用正確的基準判定。

主機台的製程事件已經送到 EAP。OES 原有的 SECS 連線是給 FDC 用的，一條 HSMS-SS 連線只能有一個 host，所以 EAP 不能從那條連線送事件進來。因此 OES 另開一條 SECS 連線，以 host 身分連到 EAP。

這條連線只傳遞資訊：OES 只會讀狀態、啟用事件，不會對 EAP 或主機台下任何命令。

4. EAP 需要提供的識別碼與資料

下表的 S1～S7、兩個 CEID 共 9 個識別碼由 EAP 方指定，在 OES 的 EAP 分頁輸入（預設為 0，代表未設定）。其中 S4 與連線狀態 CEID 是選填：平台做不到時填 0，OES 照樣連線（見 Q5）。其餘 7 個都要填，而且 S1～S7 不可重複，OES 才會正式運作。7 個必填的全部是 0 時，OES 只做連線測試：連上、S1F17、S1F1，不送 S2F37、不讀 S1F3、不影響製程視窗，EAP 分頁顯示 EAP 回的型號與版本。這讓現場在 EAP 指定識別碼之前，就能先驗證位址、port、Device ID 與防火牆（見 §10 第 0 項）。只填了一部分則不會連線，並列出缺哪幾個。

6. EAP 端的行為要求

#要求原因
E1主機台事件發生後 1 秒內送出 S6F11OES 每一幀光譜（約每 0.6～2 秒一幀）都要依視窗判定製程，短的製程步驟只有約 60 秒
E2事件依發生順序送出Start 和 End 的順序錯了，視窗就是錯的
E3先更新 S1～S7，再送 S6F11報告的值在送出當下讀取；OES 也用之後的 S1F3 修正視窗，兩者必須一致
E4EAP 不知道 PM3 狀態時，S1 填 2：EAP 剛啟動、尚未收到任何 PM3 製程事件，或與主機台斷線、恢復後尚未收到新的製程事件時不知道時填 0，OES 會以為 PM3 閒置
E5與主機台斷線時，S4 改為 0、S1 改為 2，並立即送連線狀態 CEID讓 OES 立刻改用不依賴製程事件的判定方式
E6重送同一筆事件時使用相同的序號OES 用序號判斷重送，避免同一筆處理兩次
E7時間值填 EAP 收到主機台事件的時間主機台的報告不帶時間戳
E8不需要支援 S2F33／S2F35（報告由平台固定）OES 不會送
E9不需要 spooling：OES 斷線期間的事件可以丟棄OES 重連後會用 S1F3 重新同步
E10同時只接受一個 OES host 連線；同一台 OES 重連時，以新連線取代舊連線HSMS-SS 本來就只有一個 host；舊連線可能還沒釋放

可以這樣做： 主機台的事件可以不篩選、全部轉發（PM2 的也可以），OES 不認得的 CEID 只記錄、不處理。Start 之後又收到 Start，或收到沒有對應 Start 的 End，照實轉發即可，由 OES 處理並記錄警告。

7. OES 端的行為（供參考）

EAP 方不需要實作本節，但了解它有助於判讀雙方的日誌。

  • CEID 怎麼變成製程： OES 用自己的對照表把主機台 CEID 換算成製程類別（例如 3100439529 → 製程 A），Start 到 End 之間的光譜都依該製程的基準判定。
  • S1F3 讀到的視窗和 OES 自己記的不同時，以讀到的為準，並記一筆警告（這就是「EAP 漏送事件」的紀錄）。S1 = 1 時，S2 依 OES 對照表解讀：
S2 在 OES 對照表裡是OES 的視窗
有製程類別的 Start該製程的視窗
只記錄、不分類的 Start，或對照表沒有的 CEID不在任何視窗內
End 事件內容矛盾：記警告，視窗不變
  • 資料不可信時，OES 不會停止偵測： S1 = 2、S4 = 0、收到值為 0 的連線狀態事件，或 75 秒內沒有任何一次成功的 S1F3、也沒收到事件 時，OES 把製程視窗改為「不明」，改用光譜本身判斷，等狀態恢復再切回來。
  • 連線斷掉本身不改變視窗。OES 會自動重連，連上後依 5.1 重新讀取；只要 75 秒內恢復，視窗一直維持正確。
  • 序號： 同一序號只處理一次；跳號會記錄「有事件沒送到」；序號變小代表 EAP 重啟。OES 重啟後第一次讀到的 S7 不會讓接著重送的那筆被當成重複。
  • OES 不會因為這條連線斷掉而發出漏氣警報。 連線狀態顯示在 OES 的 EAP 分頁上，收發的每一則訊息記在 OES 的 eap_YYYYMMDD.log。

9. 自測工具

Test_SECS（OES 方提供的 SECS 測試程式，Windows，不需安裝 OES）內建兩個設定檔：

  • OES (2b host)：角色選 Host (active)，連到 EAP 平台後依序按「1. Establish and go online」「2. Enable the EAP events」「3. Read S1–S7」，就是 OES 上線時的同一套步驟。日誌的 [OES] 行寫出 S1～S7 的值與意思；收到的每筆 S6F11 依 4.2 的格式解讀，寫在 [EAP] 行，格式不符會寫 REJECTED 並說明原因。
  • EAP (PM3 event forwarder)：角色選 Equipment simulator (passive)，假扮 EAP，提供本規格的 S1～S7 與兩個 CEID，可以按鈕送各種事件。供 OES 方測試，也可以給 EAP 廠商當參考實作。

兩個設定檔的預設編號是 S1～S7 = 6001～6007、轉發 CEID = 6100、連線狀態 CEID = 6101、RPTID = 6200／6201。平台的編號不同時，在 Test_SECS.exe 旁放一份 eap-ids.json（欄位見 Test_SECS 的整合指南），沒寫的欄位維持預設。
