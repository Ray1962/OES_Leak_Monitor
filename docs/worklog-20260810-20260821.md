### 1.1 錄製回放（Replay）

| commit | 內容 |
|---|---|
| `a75882f` | `SpectrumReplaySource` / `ReplayViewModel` / `ReplayPanel` |
| `a96fb58` | 拒絕在真實硬體上回放 |
| `707ff21` | 回放結束時清掉留在監視器裡的狀態 |

回放走**錄檔自己的波長軸與自己的時間軸**（虛擬時鐘），而不是前一版重採樣到合成軸的做法：
EMA 的 `α = 1 − exp(−dt/τ)`、持續確認秒數、σ/min 斜率、洩漏率 EWMA 變異數全都跟 dt 綁在一起，
軸換掉就不是同一套判斷。這需要 `Aqst.OesApp.Wpf 0.1.12` 新增的 `DeviceViewModel.SpectrumMapper`
接縫才能整格換掉 frame，所以不是純 app 內的改動。

`a96fb58` 起因於一次真實 session：接著光譜儀按下 Play，分頁顯示 `PLAYING`、進度條停在 0，
而 `BeginReplayOutput` 已經把兩個記錄器切成 `SIM` 前綴——結果 450 KB 的**實際量測**被存成
`SIMP_*`。防護反了方向。現在有三道：按鈕層（`RealHardwareAttached`）、`Play()` 再檢查、
以及執行中第一個硬體 frame 觸發 `AbortReplayForHardware()`。

`707ff21` 起因於 2026-08-20 產生的 `P_Ratio_0820153410.csv`：一個生產檔名，第一列帶著錄檔的
σ-score 與 `OverallState=Alarm`，發生在錄檔結束後 45 秒，稽核日誌裡還有一筆沒有任何 chamber
造成的 `LeakMonitorState Idle → Alarm`。`EndReplayOutput` 現在先 `ResetRuntimeState(clearAlarms: true)`
再關檔、再還原前綴。

### 1.3 Baseline Builder（從既有錄檔匯集基線）

| commit | 內容 |
|---|---|
| `33fae7f` | `BaselineBuilder` + `RatioFrameSampling` |
| `4ecd43b` | Baseline Builder 分頁 |
| `8a912c7` | 修正分頁開啟前就拋例外 |
| `8730969` | `AcquisitionSidecar`：錄檔旁記錄當時的擷取條件 |
| `a56ae70` | 報告視窗內穩定度與 marginal baseline |
| `68a2531` | 報告錄檔**之間**的落差 |

存在理由是兩種現場製程形狀：一種先 ramp 才穩定（穩定段從圖上看得出來，碼錶看不出來），
一種整個 run 比擷取視窗還短（沒有單一 run 裝得下足夠 frame）。兩者都必須**事後**選段。

關鍵設計：每一格 frame 的判斷都經過 `RatioFrameSampling.Evaluate`，引擎自己的 live capture
也走同一支。第二份「這格算不算」的實作會讓兩份 Golden Run 不可比較而兩邊看起來都正常，
所以 `BaselineBuilderTests` 把真實錄檔同時餵給兩條路徑，要求吻合到小數第九位。

最低要求是 **frame 數而非秒數**（σ 的可靠度跟樣本數走，120 秒在 0.56 fps 是 68 格、在 5 fps 是 600 格）。

`a56ae70` / `68a2531` 各自來自一次結果幾乎沒用、而且自己只講了一半的實際建置：

- 前者：一次匯集三整段錄檔（連洩漏上升段一起），產出一條 10.2 σ 的基線，而它的穩定段值是 97。
  現在會報 per-recording 的 `σ/mean` 與 drift、在 `mean/σ < 20` 時標記 marginal、
  並在所有視窗都覆蓋整段錄檔時明說「沒有做 back-check」（空白的區段會被讀成通過）。
- 後者：兩段各自穩定到 ~1 % 的視窗，因為是不同 run 的不同電漿亮度，絕對強度差了 19 %；
  匯集後那個落差**變成**了 σ，`mean/σ` 從 ~125 掉到 10.7。ratio 模式會把它除掉（同一組線 2–5 %），
  **absolute-intensity 模式不會，所以它要的是單一錄檔的基線**。兩段就報，不像 outlier 檢查
  需要三段才指得出是誰——「這兩段彼此不合」本身就值得知道。

### 1.4 pedestal 判準（2026-08-20）

`3c83110`。原本 `ValueHasPedestal` 假設「除以參考線就把台階除掉了」，但
`(pedestal + line) / reference` 只是同一個仿射位移乘上 `1/reference`，fraction-of-baseline
被壓縮的程度完全一樣。之所以沒被發現，是因為外觀上沒有任何異狀：`Math.Max` 改走乘法分支，
而它在 `mean/σ > SigmaWarn/(WarnFactor−1)` 之後勝出——在原廠 1.05/1.12 下就是 60。

實測一台機器，`N₂ 337.1 RawMean / Ar 750.4` 在 `mean/σ ≈ 119` 時，設定 3/6 σ，
實際要 5.9 σ 才警告、14.2 σ 才警報。

把判準放寬會**重新判斷**這類 ratio 而不動它們既有的基線（監測量沒變，
`Mode`/`ReferenceLabel`/`ExtractionRevision` 才是基線比對的依據），但確實會放寬它們的門檻，
也會翻轉它們的洩漏率單位——所以既有的校正會被拒絕直到重新擬合。`RatioPedestalTests` 釘住兩個分支。

  `passwordHash` 的屬性拿掉，其餘照抄——手挑清單當初就會漏掉 logger 的觸發設定，
  而那正是缺的東西。
