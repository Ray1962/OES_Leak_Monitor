1.1 錄製回放（Replay）

commit內容
a75882fSpectrumReplaySource / ReplayViewModel / ReplayPanel
a96fb58拒絕在真實硬體上回放
707ff21回放結束時清掉留在監視器裡的狀態

回放走錄檔自己的波長軸與自己的時間軸（虛擬時鐘），而不是前一版重採樣到合成軸的做法： EMA 的 α = 1 − exp(−dt/τ)、持續確認秒數、σ/min 斜率、洩漏率 EWMA 變異數全都跟 dt 綁在一起， 軸換掉就不是同一套判斷。這需要 Aqst.OesApp.Wpf 0.1.12 新增的 DeviceViewModel.SpectrumMapper 接縫才能整格換掉 frame，所以不是純 app 內的改動。

a96fb58 起因於一次真實 session：接著光譜儀按下 Play，分頁顯示 PLAYING、進度條停在 0， 而 BeginReplayOutput 已經把兩個記錄器切成 SIM 前綴——結果 450 KB 的實際量測被存成 SIMP_*。防護反了方向。現在有三道：按鈕層（RealHardwareAttached）、Play() 再檢查、 以及執行中第一個硬體 frame 觸發 AbortReplayForHardware()。

707ff21 起因於 2026-08-20 產生的 P_Ratio_0820153410.csv：一個生產檔名，第一列帶著錄檔的 σ-score 與 OverallState=Alarm，發生在錄檔結束後 45 秒，稽核日誌裡還有一筆沒有任何 chamber 造成的 LeakMonitorState Idle → Alarm。EndReplayOutput 現在先 ResetRuntimeState(clearAlarms: true) 再關檔、再還原前綴。

d311661：舊行為是把空 capture 也存起來，於是一次「門檻設在電漿之上、整分鐘閘門全關」的 capture 就同時拿走所有 ratio 的基線、並解開綁在上面的校正。現在 FinalizeCapture 在儲存前就返回。

7b3b1cd：plasma floor 原本是整個 run 一個數字，只在所有 ratio 共用同一條參考線時成立。 混用 Ar 811.5 與 N₂ 662.4 時，匯集出的 20 % 會落在暗線的正常值之上，那條 ratio 於是每一格 都判「電漿關閉」而靜靜死掉，亮的那條則等於沒有閘門。現在以 LineRegion.MeasurementKey 為 key 存進 GoldenRun.PlasmaFloors；PlasmaPresentFloor 保留為舊 run 的回退值，不再寫入。

同一個 commit 也把原廠 ratio 組合換成實測選出來的那組（R_N2Ar 33.8 σ、R_NOAr 18.3 σ、 R_N2357Ar 16.2 σ，加上預設停用的 R_N2357Abs），取代原本四條裡有三條對同一次洩漏只動 0.1–0.7 σ 的教科書組合。

849cb0b 寫下引擎本身不編碼的前提：這個工具要偵測的東西，在腔體健康時本來就不存在， 所以無洩漏的 N/O 線讀在雜訊底，而定義成除數的基線對它不可能存在。文件把 ReportDroppedRatio 能吐出的每一句話對應到一個動作，以及一個「怎麼確認這動作有效」的方法； 並用同等篇幅寫相反的失敗：RawMean 讀值帶著連續譜台階，一路通過所有閘門，產生一份看起來 健康、實際上量的是背景的基線——這件事 app 完全不會警告。

1.3 Baseline Builder（從既有錄檔匯集基線）

commit內容
33fae7fBaselineBuilder + RatioFrameSampling
4ecd43bBaseline Builder 分頁
8a912c7修正分頁開啟前就拋例外
8730969AcquisitionSidecar：錄檔旁記錄當時的擷取條件
a56ae70報告視窗內穩定度與 marginal baseline
68a2531報告錄檔之間的落差

存在理由是兩種現場製程形狀：一種先 ramp 才穩定（穩定段從圖上看得出來，碼錶看不出來）， 一種整個 run 比擷取視窗還短（沒有單一 run 裝得下足夠 frame）。兩者都必須事後選段。

關鍵設計：每一格 frame 的判斷都經過 RatioFrameSampling.Evaluate，引擎自己的 live capture 也走同一支。第二份「這格算不算」的實作會讓兩份 Golden Run 不可比較而兩邊看起來都正常， 所以 BaselineBuilderTests 把真實錄檔同時餵給兩條路徑，要求吻合到小數第九位。

最低要求是 frame 數而非秒數（σ 的可靠度跟樣本數走，120 秒在 0.56 fps 是 68 格、在 5 fps 是 600 格）。

a56ae70 / 68a2531 各自來自一次結果幾乎沒用、而且自己只講了一半的實際建置：

  • 前者：一次匯集三整段錄檔（連洩漏上升段一起），產出一條 10.2 σ 的基線，而它的穩定段值是 97。 現在會報 per-recording 的 σ/mean 與 drift、在 mean/σ < 20 時標記 marginal、 並在所有視窗都覆蓋整段錄檔時明說「沒有做 back-check」（空白的區段會被讀成通過）。
  • 後者：兩段各自穩定到 ~1 % 的視窗，因為是不同 run 的不同電漿亮度，絕對強度差了 19 %； 匯集後那個落差變成了 σ，mean/σ 從 ~125 掉到 10.7。ratio 模式會把它除掉（同一組線 2–5 %）， absolute-intensity 模式不會，所以它要的是單一錄檔的基線。兩段就報，不像 outlier 檢查 需要三段才指得出是誰——「這兩段彼此不合」本身就值得知道。

1.4 pedestal 判準（2026-08-20）

3c83110。原本 ValueHasPedestal 假設「除以參考線就把台階除掉了」，但 (pedestal + line) / reference 只是同一個仿射位移乘上 1/reference，fraction-of-baseline 被壓縮的程度完全一樣。之所以沒被發現，是因為外觀上沒有任何異狀：Math.Max 改走乘法分支， 而它在 mean/σ > SigmaWarn/(WarnFactor−1) 之後勝出——在原廠 1.05/1.12 下就是 60。

實測一台機器，N₂ 337.1 RawMean / Ar 750.4 在 mean/σ ≈ 119 時，設定 3/6 σ， 實際要 5.9 σ 才警告、14.2 σ 才警報。

把判準放寬會重新判斷這類 ratio 而不動它們既有的基線（監測量沒變， Mode/ReferenceLabel/ExtractionRevision 才是基線比對的依據），但確實會放寬它們的門檻， 也會翻轉它們的洩漏率單位——所以既有的校正會被拒絕直到重新擬合。RatioPedestalTests 釘住兩個分支。

兩個原則值得記住：SecsBridge 只讀不算——每個 binding 都在請求端執行緒上被呼叫， 所以最後一份 LeakMonitorSnapshot 以單一 volatile 的不可變物件持有，binding 只讀欄位並轉型； 不在快照裡的數字就不屬於這個類別（VID 021–023 因此變成快照欄位而非現場推導）。 SecsChamberCoding 的蓋章會驗證：位數不對、ss ≠ 27、aa ≠ 00 一律拒絕啟動， 而 cc = 00 不是一個 chamber，所以未蓋章的 profile 不可能被誤認為已蓋章。
