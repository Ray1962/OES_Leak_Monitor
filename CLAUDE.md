## Build & run

- WPF, .NET 8, Windows-only, x64-only (no AnyCPU). Configurations: `Debug|x64`, `Release|x64`.
- Build: `dotnet build src/OES_Leak_Monitor/OES_Leak_Monitor.csproj -c Debug` (or open `OES_Leak_Monitor.sln` in Visual Studio 2022).
- Run: `dotnet run --project src/OES_Leak_Monitor/OES_Leak_Monitor.csproj`.
- Tests: `dotnet test tests/OES_Leak_Monitor.Tests/OES_Leak_Monitor.Tests.csproj -c Debug` (xUnit, `net8.0-windows`/x64 to match the app it references). They cover the SECS interface — chamber-code stamping, the profile/binding contract, and the wire behaviour against a real `GemHost` over loopback — plus the leak engine replayed against a recorded plasma run. **Three of them need a recording that is not in the repo** and report as *skipped* without it; see `RecordedRun` and the note below.
- Do not add the test project with `dotnet sln add` — it writes `Any CPU` and `x86` configurations into the solution, which this repo deliberately does not have. Edit `OES_Leak_Monitor.sln` by hand.
- **From the WSL shell there is no native `dotnet`** — this is a Windows/WPF build. Invoke the Windows SDK explicitly, e.g. `"/mnt/c/Program Files/dotnet/dotnet.exe" build src/OES_Leak_Monitor/OES_Leak_Monitor.csproj -c Debug` (same for `publish`). The bare `dotnet …` commands above assume a Windows terminal / Visual Studio.

### Manual verification (no hardware required)

The automated tests cover the SECS interface and the leak engine; **everything with a window on it is still verified by running the app.** With no spectrometer attached, Connect falls back to **test mode** (`ConnectStandaloneAsync`), which streams synthetic spectra — enough to exercise the full UI without hardware. A connect that silently lands in test mode when hardware *should* be present usually means the native DLLs didn't reach the output root (see the native-DLL note above). To smoke-test a change:

- Launch, then **Connect** → **Start** in the Monitor tab's `DevicePanel`; confirm spectra stream and the Leak Monitor / Wavelength-Trend charts update.
- The Leak Monitor tab shows a **"test mode"** note while synthetic; alarms are suppressed there by default (`LeakMonitorSettings.SuppressAlarmsInTestMode`), so to exercise alarm transitions either tick **Raise leak alarms during replay** on the Replay tab or feed real/abnormal data. The note names what the frames actually are and whether alarms are live (`LeakMonitorViewModel.SetTestModeContext`).
- To validate against a **recorded spectrum** instead of the synthetic sine wave, use the **Replay tab** (Engineer+): Choose CSV… → Connect → Start (test mode) → Play. The `DevicePanel` live plot, Wavelength-Trend chart, leak monitor, and the written CSVs all show that recording, on its own wavelength axis and at its own frame intervals. See `SpectrumReplaySource` below.
- The intensity logger only writes CSVs while the selected wavelength's intensity is **above the trigger threshold** — lower the threshold in the `LoggerPanel` if you need test-mode spectra to cross it and open a save session. The **Ratio CSV is independent**: it writes for as long as the OES is acquiring, whatever the threshold logger is doing, so it appears even in a test-mode run that never crosses the threshold.
- Recordings / Ratio Review tabs read back the CSVs written above; use them to confirm a logging change round-trips to disk and re-parses.

### The recorded-run tests

`RecordedRunTests` replays a real plasma recording through the leak engine and out to a SECS host. The default is `C:\DualOES\202608\14\P_OES1_0814220358.csv` — ten minutes of a chamber on 2026-08-14 during which the tool went Normal → Warning → Alarm; its ratio CSV (`P_Ratio_0814220355.csv`) is the contemporaneous record of that. Point `OES_TEST_RECORDING` at another full-spectrum CSV to use a different run.

**The recording is deliberately not committed.** It is 5.5 MB (2.5 MB zipped) against a repository whose whole history is ~5 MB and whose largest file is 128 KB. Synthetic spectra cannot replace it: what the engine does is decided by the continuum under each line, the noise on it, and the axis the spectrometer actually produced.

The tests replay it through the **factory** ratio set with a baseline captured from the recording's own first minute — not the configuration that produced the live transitions, which has since been retuned and cannot be recovered. It lands within a few seconds of them anyway (warning +2 s, alarm +5 s), which is what makes the ±90 s tolerance meaningful rather than generous: **if it starts drifting, either detection changed or the factory ratio set was retuned.** Widening the tolerance is not the fix.

### Standalone publish (no .NET install required on the target PC)

`Properties/PublishProfiles/SelfContained-win-x64.pubxml` produces a single self-contained `.exe` (the .NET 8 runtime is bundled in). Three ways to run it: double-click `publish.cmd` in the repo root; `dotnet publish src/OES_Leak_Monitor/OES_Leak_Monitor.csproj -p:PublishProfile=SelfContained-win-x64`; or in Visual Studio right-click the project → Publish → that profile. The `/publish` Claude slash command does the same. Output: `src/OES_Leak_Monitor/bin/Publish/win-x64/`.

The `.exe` bundles all managed code plus the .NET 8 runtime, but native DLLs are not embedded — the output folder also holds the WPF native DLLs (`wpfgfx_cor3.dll`, `PresentationNative_cor3.dll`, `D3DCompiler_47_cor3.dll`, `PenImc_cor3.dll`, `vcruntime140_cor3.dll`), the OES native DLLs (`UserApplication.dll`, `SiUSBXp.dll`, `libsodium.dll`) and the Visual C++ runtime (`vcruntime140.dll`, `vcruntime140_1.dll`, `msvcp140.dll` — see `CopyVcRuntime` below). Ship the whole folder together — those DLLs are loose next to the `.exe` on purpose (the `DllResolver` only searches the app base directory; see the native-DLL note below). Do not enable `IncludeNativeLibrariesForSelfExtract` — it would bundle the OES DLLs into the exe and break hardware connect.

The `CopyOperatorDocs` target also drops the operator-facing HTML docs — `docs/user-manual-zh-TW.html`, `docs/daily-inspection-plan-zh-TW.html`, `docs/secs-operation-sop-zh-TW.html`, `docs/secs-acceptance-sheet-zh-TW.html`, `docs/CONTEXT-zh-TW.html` and `docs/golden-run-baseline-troubleshooting-zh-TW.html` — into the publish folder (publish only, not build), so a delivery folder carries its own manual, inspection plan, SECS SOP, acceptance sheet, glossary and Golden Run troubleshooting guide. Both the `Warning` and the `Copy` batch over the `_OperatorDoc` item, so a missing file warns on its own and the rest still ship; regenerate it first (see [Documentation](#documentation)). Adding another shipped doc means adding one `_OperatorDoc` line here **and** one filename to `publish.cmd`'s completeness check.

Two guards exist because a publish can "succeed" and still produce an unshippable folder. Left alone, an incremental `dotnet publish` (nothing changed since the last one) keeps the `.exe` but strips every loose native DLL — a folder that launches fine and then falls back to test mode on the production PC, the hardest failure mode this app has:

- `EmptyPublishDirBeforePublish` (csproj) empties `$(PublishDir)` first, so every publish is a full copy. It hooks **`PrepareForPublish`, not `Publish`** — the pipeline copies its files inside targets that `Publish` depends on, so `BeforeTargets="Publish"` runs *after* the copy and would delete exactly what it was meant to protect. It only ever cleans a folder under the project's own `bin\`; a `-o` path outside it is warned about, not deleted.
- `publish.cmd` re-checks all 20 expected files afterwards and refuses with a non-zero exit if any are missing.

> ⚠️ **Never `set` an MSBuild property name as an environment variable in `publish.cmd`.** Environment variables become global MSBuild properties, so a helper called `OUTDIR` silently becomes `OutDir`, redirects the *build* output into the publish folder, and single-file bundling then dies with `Unable to access file during bundling` / a missing `runtimeconfig.json`. The folder-path helper is deliberately named `PUBFOLDER`. The same trap applies to `CONFIGURATION`, `PLATFORM`, `OUTPUTPATH`, `TARGETFRAMEWORK`.

`0.4.6` of the SDK is what supplies `OesAcquireMode` / `OesAverageMode`; it also stopped opting into `UAI_BackgroundRemove` implicitly, though `DeviceViewModel` still passes `EnableBackgroundRemove = true`, so this app's behaviour is unchanged.

`Core 0.1.4` fixes the intensity logger's silent data loss on a mid-session wavelength-axis change. `IntensityCsvWriter.WriteRow` now takes the frame's own axis (`WriteRow(timestamp, wavelengths, intensities)`) and returns a `RowWriteResult`; when the axis differs from the one the header was written from it closes the file and continues into the next rotation file (summary companion included) carrying the new axis. Previously such rows were dropped with no signal at all, so the session stayed in `Saving` with a CSV that never gained another row. `DualIntensityLogger` surfaces it as the new `FileRolled` event (`FileRollReason.SpectrumAxisChanged` / `RowLimit`), which `MainViewModel.OnIntensityFileRolled` logs — Warning for an axis change, since it means an acquisition parameter was reapplied mid-save and any Golden Run from the old exposure no longer applies. `Wpf 0.1.8` is only a re-pack against the new Core.

`Core 0.1.7` puts the **`Description` column into the system-log CSV**. Every entry had carried one from the beginning — it is the sentence saying what happened and what to do — and `SystemLogger.FormatEntry` simply never wrote it, so the file recorded that something called `Device_RuntimeError` had occurred and nothing at all about the error. It survived only in the in-memory ring the Logs tab renders from, i.e. until the app closed, which is backwards: the file is what gets read after something has already gone wrong. The column sits after `Condition`; `SystemLogger.ResolveLogFilePath` sends this run to `{stem}_1.csv` when the hour's file was written by a build with a different header, so no file ever mixes column counts. `Wpf 0.1.11` is only a re-pack against the new Core.

`Wpf 0.1.12` adds **`DeviceViewModel.SpectrumMapper`** — an optional `Func<SpectrumSample, SpectrumSample>` applied in `OnSpectrumAvailable` before *both* the `SpectrumAvailable` invoke and the `UpdatePlot` dispatch, so returning a different sample replaces the frame for every consumer including the device's own live plot. It exists because a frame's arrays are fixed-length and `init`-only: mutating the incoming frame (the previous trick) could substitute intensities but never the wavelength axis, which is what recorded-spectrum replay needs. Null by default, so a host that doesn't set it is unaffected; it runs on the SDK callback thread, and a mapper that throws is ignored in favour of the original frame.

`Wpf 0.1.13` makes a **test-mode fallback say so**. The SDK reports one as a *successful* connect (`SetupTestMode()` returns true), so `Device_Connect` was logged as `ok` at Information and the one string that says what happened — `OesDeviceInfo.LastConnectionResult`, e.g. `"No OES hardware devices found - test mode activated"` or `"UserApplication.dll load failed at …"` — never left the SDK: `DeviceViewModel` did not expose it and no `ILogger` was passed to `Spectrometer`, so the SDK's own warnings went nowhere either. Diagnosing the 2026-08-17 fab PC needed a separate script (`tools/check-oes-connect.ps1`) purely to recover that sentence. `ApplyConnectResult` now sets `LastConnectionResult` / `ResolvedDllPath` (both public, both raising `PropertyChanged`), puts the reason in `StatusMessage`, and logs one `Device_TestModeFallback` **Warning** carrying it plus `ForceTestMode` and `DllAvailable`. `DevicePanel`'s footer shows `Test Mode` in red with the reason on the tooltip. `LogDeviceConnection` is untouched, so Core stays at 0.1.7.

`Core 0.1.8` **back-fills the frames from before the save trigger confirmed**, and it is on without anyone setting anything: the buffer window is `max(StartConfirmSeconds, PreTriggerSeconds)` and the new `PreTriggerSeconds` defaults to 0, so the confirmation window alone is already back-filled. Recordings therefore start earlier than they did under 0.1.7 — at the default 2 s / 200 ms, about 11 extra frames at the head — and each file is named from its own first row rather than from the moment the trigger confirmed. Worth knowing here specifically, because baselines are built from these recordings: the added head is below the trigger threshold by definition, so `PlasmaGate` — which measures the same quantity against the same threshold — closes on it, and `RatioFrameSampling.Evaluate` holds it out of a baseline in **both** monitor modes (a ratio entry additionally needs its own reference line, but the gate comes first for it too). Two caveats, both about the offline path: `BaselineBuilderViewModel` builds that gate from the logger's *current* settings, not the ones the recording was made under — a threshold that has moved since is what the day folder's `_config_*.json` is for — and an unusable gate (`IsUsable` false: a non-positive threshold, or `AnyMonitoredWavelength` with an empty list) makes `IsPlasmaPresent` return null, which `Evaluate` reads as open. The head then lands in the baseline, dragging the mean down and the σ up on exactly the `RawMean` entries that can least afford it. So `PreTriggerSeconds` is a Recordings-review setting, not a measurement one: leave it at 0 unless someone wants the pre-discharge background on screen. `LoggerPanel` gains a `Pre-Trigger Time (s)` box and a live buffered-frame reading; `Wpf 0.1.14` is only a re-pack against the new Core.

`Core 0.1.9` puts **every timestamp the intensity logger hands out on one clock**. `DualIntensityLogger.Stop()` and a `Configure` that disables the logger stamped their `StateChanged` event with `DateTime.UtcNow`, while frames, CSV rows and file names all carry local time. Nothing computed across the two, so nothing broke and nothing was logged as wrong — it surfaced only when someone read the audit CSV and found a session ending eight hours before it started, because `MainViewModel.OnIntensityStateChanged` writes that stamp straight through as the entry's `Value` (`e.Timestamp.ToString("O")`). Both paths now go through a private `LocalNow()`; `SystemLogger` keeps `UtcNow` for its flush deadline, which is a duration rather than a wall-clock reading. `Wpf 0.1.15` is only a re-pack against the new Core.


### Native DLL flattening (do not remove)

`Aqst.OesSpectrometer` ships `UserApplication.dll`, `SiUSBXp.dll` and `libsodium.dll` under `runtimes\win-x64\native\`, but the package's `DllResolver` only searches the app base directory. The `FlattenOesNativeDlls` MSBuild target in `OES_Leak_Monitor.csproj` copies those three DLLs into `$(OutDir)` (and `$(PublishDir)`) after Build/Publish. If hardware connect silently falls back to test mode, check that those files reached the output root.

### The Visual C++ runtime ships app-local (do not remove)

`UserApplication.dll` statically imports `libsodium.dll`, which imports `VCRUNTIME140.dll`. On a PC that has never had the **Visual C++ 2015–2022 x64 redistributable** installed, `LoadLibrary` fails with Win32 126 (`ERROR_MOD_NOT_FOUND`) before a single device is enumerated — and `OesDevice.CheckHardwareDllAvailability` catches that into `SetupTestMode()`, so the app reports "Connected", streams synthetic spectra into the real data folder under the ordinary `P_` prefix, and writes **nothing at all** about why. It is indistinguishable in the audit log from a healthy connect except for `Serial=TEST_MODE_SIMULATOR`. Measured on a fab PC on 2026-08-17: complete delivery folder, correct bitness, working driver, vendor software connecting fine, and this was the difference.

The `CopyVcRuntime` target therefore copies `vcruntime140.dll`, `vcruntime140_1.dll` and `msvcp140.dll` into `$(OutDir)` and `$(PublishDir)`, which removes the prerequisite: Windows resolves a dependency from the executable's own folder before the system directories. Notes:

- `vcruntime140_cor3.dll` (already in the publish folder) is WPF's **renamed private copy** and does not satisfy an import of `VCRUNTIME140.dll`. It is not a substitute, and its presence is why the folder looks like it already carries the runtime.
- All three travel together — `msvcp140.dll` imports `VCRUNTIME140_1.dll`. Only `vcruntime140.dll` is strictly required by today's import graph; the other two guard against a dynamically loaded C++ component in a future SDK build.
- Source order: `-p:VcRuntimeSourceDir=<folder>` if the build sets one, then the VS C++ redist folder (`$(VCToolsRedistDir)`, only defined in a developer prompt), then `%SystemRoot%\System32` — the same binaries the redistributable installs. A build machine with no redistributable at all warns per file and `publish.cmd` then refuses the folder.
- `tools/check-oes-connect.ps1` (+ `.cmd` wrapper) is the field diagnostic for this whole class of failure: run it **in the app folder, as the operator's own user**, and it reproduces `DllResolver.Resolve` → `CheckHardwareDllAvailability` → USB enumeration and prints the Win32 error the app swallows, plus the device list and an open test. It is the only way to tell "DLL will not load" from "no device found", because the app logs neither.

## Architecture

This is a **single-OES** leak-monitoring fork of a previously dual-OES codebase. Most of the UI shell, device control, logging, access control, and plot/configuration panels live in the `Aqst.OesApp.*` NuGets — the project here is mostly composition + a custom Recordings tab.

### What comes from `Aqst.OesApp.Core` / `Aqst.OesApp.Wpf` (referenced, not defined here)

- `DeviceViewModel`, `LoggerViewModel`, `LogViewerViewModel`, `SystemLogger`, `DualIntensityLogger`, `IntensityCsvWriter`
- `AccessControlService`, `UserRole` (Guest < Operator < Engineer < Admin), `LoginDialog`, `UserManagementDialog`, `AccessControlConfig`
- `OesAppPaths` — resolves per-user AppData subfolders (`Config`, `Log`, `Data`) under the app folder name
- `RelayCommand`, `DeviceSettings`, `LoggerSettings`, `LogSeverity`
  - `DeviceSettings.AcquireMode` (`HardwareAverage` / `Oneshot` / `Standard`) and `DeviceSettings.AverageMode` (`Hardware` / `Software`) are exposed as combo boxes in the Configuration tab and hot-applied by Apply (`UpdateParametersAsync`). `Oneshot` is the fix for segmented / torn frames on Z5 / Ethernet modules; `Software` averaging trades N× wall-clock for avoiding the peak shift / broadening some hardware averagers introduce. Both round-trip through `settings.json` as strings (`SettingsService` registers `JsonStringEnumConverter`), so pre-existing files without the keys just keep the defaults.
- WPF user controls bound in `MainWindow.xaml`: `DevicePanel`, `ConfigurationPanel`, `LoggerPanel`, `LogViewerPanel`
- Global `using Aqst.OesApp.Core;` and `using Aqst.OesApp.Wpf;` are injected via the csproj, so these types appear unqualified throughout.

Treat that NuGet surface as the framework. When something looks "missing," it is almost certainly defined in those packages, not here.

### What is defined in this project

- `MainViewModel` — wires a single `DeviceViewModel` (the `DeviceProfiles` array has one entry tagged `"OES1"`), the `DualIntensityLogger`, the `RecordingsViewModel`, and the toolbar role badge. Per-device Connect/Disconnect/Start/Stop live in the embedded `DevicePanel` header (Monitor tab); the LoggerPanel exposes Start Save / Stop Save. The top toolbar holds only the title, status message, and the user/role controls — there is no longer a "Both" command that bundles device + logger.
  - **Constructor ordering (load-bearing).** `settings.json` is loaded and `Logger.LoadFrom` runs *before* `RecordingsViewModel` / `RatioReviewViewModel` are constructed, because both read the logger in their own constructors — they scan `EffectiveBaseDirectory` once, and Recordings also snapshots `Logger.TriggerWavelength` into `_wavelengthNm`. Built against an un-hydrated `LoggerViewModel` they silently take the factory defaults (the AppData fallback folder instead of the configured data directory — both tabs then show "0 files" until the user presses Refresh — and 337 nm instead of the configured trigger). Don't move the review tabs back above the settings load. The runtime counterpart is in `ApplyAll`: a changed base directory (tracked in `_lastDataDirectory`) re-`Refresh`es both tabs and logs `DataDirectoryChanged`, since neither watches the logger for path changes.
  - **Trigger modes (Core 0.1.6).** `LoggerSettings.TriggerMode` decides what the save threshold is compared against: `Wavelength` (unchanged default), `SpectrumPercentile` (the frame's `TriggerPercentile`-th percentile — tracks the discharge rather than the gas mix, for a recipe that admits the watched gas after ignition or only in some steps), or `AnyMonitoredWavelength` (brightest of `MonitoredWavelengths`). `MainViewModel.TrendThresholdFor` passes 0 for the Monitor trend's dashed threshold line in the whole-frame modes — that line marks the threshold against the trigger *wavelength's* trace, which stops being the trigger, and a line drawn at a meaningless height is worse than no line. The recorder strip's text names the active mode.
  - **Recorder strip (Monitor tab).** `RecorderStateText` / `RecorderBrush` / `RecorderDetailText` / `RecorderWarningText` / `RecorderTooltip` are a read-only projection of the logger, recomputed by `UpdateRecorderStatus()` from `Logger.PropertyChanged`. It exists because the `LoggerPanel` — the only place that shows whether anything is being recorded — lives in the Engineer-gated Configuration tab, so an Operator doing the daily check previously had no way to see it. Status only, by design: seeing the state is an Operator concern, arming stays an Engineer one. `RecorderWarningText` compares the live `Logger.Enabled` against `_persistedLoggerEnabled` (the value in `settings.json`, refreshed at load and in `SaveSettings`) and warns while they differ — Start Save without Save silently reverts to disarmed on the next launch, which is otherwise invisible until the data is missing. Documented for operators in the manual §6.1.2.
- `AppSettings` + `SettingsService` — `settings.json` in `OesAppPaths.ConfigDirectory`. Two framework `LoggerSettings` defaults are overridden for a fresh file: `DefaultTriggerWavelengthNm` (337.1, the N₂ band head, not the framework's 387) and **`DefaultLoggerEnabled` = true** — the framework ships a general-purpose recorder disarmed, but a leak monitor that isn't recording has nothing to show when someone asks what the tool was doing an hour ago, and the arming switch is on the Engineer-gated Configuration tab an Operator never opens. Only the *factory* value changes: a stored `"enabled": false` is a saved decision and is honoured. A third override, `DeviceSettings.ForceTestMode`, works the same way: **`DefaultForceTestMode` = false**, because the framework ships it *true* and a fresh settings.json therefore ran the whole leak monitor on the synthetic generator — nothing on screen says so but `Test Mode: True` in the `DevicePanel` footer, and the CSVs carry the ordinary prefix. `AppSettings.NewDevice()` is the one place that value is applied, so the default list and `OnDeserialized`'s padding cannot disagree; `AppSettingsDefaultsTests` pins all three plus the stored-decision half of the contract. `MainViewModel.LoadDefaultsAll` re-applies all three after `LoadDefaults()`, so the button and a fresh install land in the same place — left alone the framework's device defaults silently re-arm test mode and the next Save persists it. `AppSettings.OnDeserialized` migrates the legacy `device1`/`device2` keys into the `devices` list, and pads the list to at least 2 entries (legacy schema lock — do not shrink to 1).
- `Recording` / `RecordingGroup` — parse CSVs produced by `IntensityCsvWriter` under `{baseDir}\YYYYMM\DD\{prefix}_{tag}_{MMddHHmmss}[_N].csv`. The group key is `{prefix}|{sessionStart}|{rotation}` (dual-OES file layout preserved) but only the `"OES1"`-tagged file populates the group; any historical `"OES2"` siblings on disk are ignored at scan time. Year is recovered from the parent folder.
- `Recording.FromArchive` / `Recording.OpenText` — the review tabs read archived CSVs **straight out of `DD.zip`**, so compressing a day folder (see `DataRetentionService`) doesn't hide it from Recordings / Ratio Review. Scanning a month folder lists loose `*.csv` and then each `*.zip`'s central directory; an archived `Recording` carries `ArchivePath` + `EntryName`, and `OpenText()` returns a `StreamReader` over the entry whose `Dispose` also closes the owning `ZipArchive`. Parsing streams the decompression — a 30 MB full-spectrum entry parses in ~0.35 s with no temporary extraction, which matters because a single file can be several hundred MB. `RecordingCsvParser.ReadFull(TextReader, …)` (Core 0.1.5) and `RatioCsvReader.Read(TextReader, …)` are the overloads that make this possible; both are forward-only, so a non-seekable stream is fine. The lists show a `zip` marker column and Ratio Review's status names the source archive.
- `RecordingsViewModel` + `RecordingsPanel` — Recordings tab: scans the data folder, builds OxyPlot line / heatmap / frame-spectrum views, supports two-row compare mode (two sessions overlaid — orthogonal to device count), PNG export, clipboard copy, notes, search. **The line view plots up to `MaxTrendWavelengths` (6) wavelengths**, added from the emission-line catalog picker or typed free-hand (a stretch of continuum with no line on it is the control you need when judging whether a line responded, and the catalog cannot offer it). **Colour encodes the wavelength, dash pattern the session** — "which line moved" and "how does this run differ from that one" are separate questions, so they get separate channels instead of being made mutually exclusive; colours are positional and re-dealt on removal so the swatch list can't disagree with the legend. `NormalizeTrend` divides each trace by **its own mean over the whole recording** (not the first frame — a recording usually starts before the plasma is lit, and dividing by ~0 explodes the trace); it is *not* the Leak Monitor's % -of-baseline, whose divisor is a Golden Run, so the axis says `× own mean` and a trace whose mean is ≤ 0 is left in raw counts and labelled. `UsePeakWindow` (±0.5 nm max, matching the Monitor tab's live trend) is **off by default**: taking a window maximum biases a weak line upward and inflates its scatter, which is exactly the σ-based judgement §1.1 asks the operator to make here — drift belongs to the Wavelength Calibration overlay instead. The set persists to `AppSettings.RecordingsWavelengths` on every change (a review preference, not a measurement setting), written with the same read-modify-write idiom as the replay selection since whoever is comparing recordings never visits the Configuration tab's Save.
- `RatioReviewViewModel` + `RatioReviewPanel` + `RatioCsvReader` — Ratio Review tab: scans the data folder for the `{prefix}_Ratio_*.csv` files `RatioCsvLogger` writes, and plots the selected file's per-ratio trend in one of three modes — % of baseline (with the 100/120/150 % threshold lines), raw ratio, or **leak rate** (the calibrated `Q̂` in mbar·L/s with a translucent ±1σ band) — with the composite leak state drawn as translucent Warning/Alarm bands behind the series. The ratio CSV carries trailing `LeakRate,LeakRateSigma` columns (P3); `RatioCsvReader` locates columns by header name so pre-calibration files (without those columns) still parse, exposing `RatioTrendData.HasLeakRate`. The per-ratio percent column is named for what it holds — `_pctBaseline` or `_sigmaScore` (see `ValueHasPedestal` below) — and `RatioTrendData.PctIsSigmaScore` carries that through so the legend can mark a σ-score series; both share the 100/120/150 scale by construction, but they are not the same number and a file that doesn't say which is unreadable a year later. Reuses `Recording.TryParse` for the shared filename scheme, filtering on the `"Ratio"` tag. PNG export, clipboard copy, search.
- `RatioSetupViewModel` + `RatioEditViewModel` + `RatioSetupPanel` — Ratio Setup tab: a staged editor for the species-ratio configuration. Up to `RatioSetupViewModel.MaxRatios` (10) ratios; each picks a signal and a reference line (species + wavelength) from the species-grouped `SpectralLineCatalog`, plus per-ratio extraction mode (`PeakHeight` / `Integral` / `RawMean`) and alarm thresholds. Each entry also has a **monitoring method** (`RatioDefinition.MonitorMode`): `Ratio` (signal ÷ reference — the actinometric default) or `AbsoluteIntensity`, where the monitored quantity is the signal line's absolute baseline-subtracted intensity and **the reference line is not used at all** (see `PlasmaGate` below; the picker is hidden in that mode). Absolute mode is for weak/near-noise lines where the ratio of two small numbers swings wildly — dropping the reference division removes one noise source — at the cost of no longer cancelling plasma-condition drift (so it needs a stable operating point and more frequent re-baselining). The mode branches the monitored value in `RatioMonitor.Update` and the Golden-Run / calibration-point accumulation in `LeakMonitorEngine`; everything else (Golden Run baseline, σ thresholds + live-σ widening, SNR gate, state machine) is shared across both modes. **Pedestal handling — keyed on `RatioDefinition.ValueHasPedestal` (a `RawMean` numerator, in *either* monitor mode), not on the monitor mode.** A value carrying the continuum pedestal compresses everything defined as *(value ÷ baseline)* into a fraction of a percent, so those quantities switch to σ units: (a) the **% -of-baseline trend** plots a σ-normalized score `100 + (20/SigmaWarn)·(ema − baseMean)/EffectiveSigma` (`RatioMonitor.PercentOfBaselineDisplay` — baseline stays at 100, one warn-σ above lands at 120, so the shared 100/120/150 guide lines still hold) and the per-row slope reads in σ/min; (b) the **leak-rate calibration** fits and inverts the *absolute* rise `Δ = value − baseMean` (σ straight from the EWMA scatter, no division), stamped by `RatioSensitivity.Absolute` and supplied by `LeakMonitorEngine.CurrentValueUnits()`; (c) the Warn/Alarm **factors** are ignored. Everything else — a baseline-subtracted line in either mode, whose mean *is* the signal — keeps the honest `ema/baseMean·100` and the fractional rise, which is also immune to a pure re-scaling. **Dividing by a reference line does not remove the pedestal**, which is what the predicate used to assume: `(pedestal + line) / reference` is the same affine offset scaled by `1/reference`, so the fraction-of-baseline is compressed exactly as in absolute mode. It went unnoticed because nothing looks wrong — `Math.Max` just takes the multiplicative branch instead, and it wins once `mean/σ > SigmaWarn/(WarnFactor−1)`, i.e. past 60 at the factory 1.05/1.12. Measured on one machine, `N₂ 337.1 RawMean / Ar 750.4` at mean/σ ≈ 119 was warning at 5.9 σ and alarming at 14.2 σ against a configured 3/6. Widening the predicate re-judges such ratios without touching their stored baselines (the monitored value is unchanged, and `Mode`/`ReferenceLabel`/`ExtractionRevision` are what a baseline is matched on) — but it does loosen their thresholds, and it flips their leak-rate unit, so a calibration fitted against the fractional rise is refused until re-fitted. `RatioPedestalTests` pins both branches. A fit is rejected if that unit changed since calibration (`LeakRateEstimator.Estimate`, same spirit as the reference-label gate), which is what invalidates every pre-existing absolute-mode calibration on upgrade. Save persists into `LeakMonitorSettings.Ratios` in `settings.json` (same file as the Configuration tab), gated to Engineer+. Edits are **staged** — they take effect only when OES acquisition restarts: `MainViewModel` watches `DeviceViewModel.IsAcquiring` and, on a Stop→Start transition, calls `LeakMonitorEngine.ReloadRatios()`, which rebuilds the monitors and raises `RatiosReloaded` (the Leak Monitor tab rebuilds its rows in response). **Latched alarms survive that rebuild**: `ReloadRatios` snapshots which keys were latched, then re-arms each one whose definition still `MeasuresSameAs` the old (same mode, same monitored line, same reference in ratio mode — thresholds and smoothing deliberately excluded, since retuning a threshold doesn't change what is measured) and logs `LeakMonitorAlarmLatchDropped` for the rest. Without it, restarting acquisition cleared every confirmed leak without an Acknowledge, which is exactly what happened twice in a real run; `_overall` is recomputed rather than forced to `Idle` so a carried-over latch still reads Alarm immediately. `RatioEditViewModel` reuses an untouched line's original `LineRegion` so editing one ratio never re-labels another. Each line-picker entry is a `SpectralLineOption` (catalog line + its current wavelength offset), so a line carrying a correction shows `+0.20 nm → 777.4 nm` beside its species and wavelength — in the dropdown and in the closed combo. The offsets are display-only; `RatioSetupViewModel.RefreshCorrections` re-reads them in place (leaving unsaved ratio edits alone) when `WavelengthCorrectionViewModel` raises `CorrectionsSaved`. Because several species share a wavelength (Ar and N2 both list 750.4 nm), a saved region is matched back to its catalog line by the species in its `Label` first, falling back to the globally nearest wavelength. The Leak Monitor tab is therefore display-only for ratio config (no live reference/enable controls).
- `LinePickerViewModel` — the **emission-line picker on the Configuration tab**, filling the logger's `TriggerWavelength` and `MonitoredWavelengthsText` from the catalog instead of from memory. `LoggerPanel` is a framework (`Aqst.OesApp.Wpf`) control that knows nothing about emission lines, and `SpectralLineCatalog` is defined here, so the picker sits beside the panel and writes into the same properties a hand-typed value would — **an input aid that owns no state**, which is why there is no second copy of the setting to drift out of step (a checkbox-list design would have had to answer "what does a hand-typed 250.3 look like when it matches no line"). It writes the **catalog** wavelength, never the corrected one: a recorder holding `777.4` would match neither the catalog nor the correction table after someone retuned the offset, so the correction is named in the hint text instead. Setting a trigger while `TriggerMode` is a whole-frame mode writes the value and *says* triggering won't use it rather than switching the mode — percentile mode is chosen deliberately. Adding a monitored line skips duplicates (±0.05 nm) and notes when the list passes `WavelengthTrendViewModel.MaxMonitoredWavelengths`, since the CSV takes every entry as a column while the trend chart draws the first five — capping the list would make wanting eight columns cost the chart. `SpectralLineOption.Display` exists for this picker; the Ratio Setup combos template the parts themselves.
- `UserSpectralLine` + `SpectralLineTableViewModel` — the **emission-line table** at the top of the Wavelength Calibration tab. `SpectralLineCatalog.BuiltIn` is fixed and read-only (it is the shared reference; editing it would make two tools' configurations incomparable); `SetUserLines` layers the site's own lines over it, and `All` / `Species` are recomputed from both. A user species always carries the `u` prefix (`SpectralLineCatalog.UserPrefix`), **applied by the editor rather than typed** — the operator enters `N2`, the row stores `uN2` — so a user line can never collide with or shadow a built-in one, and a ratio label, Golden Run `ReferenceLabel` or CSV column header that came from one says so on its face. Reusing a built-in species name is allowed and expected (`uN2` beside `N2` is the "the built-in N₂ lines don't include mine" case). Stored in `LeakMonitorSettings.UserSpectralLines` — in `settings.json`, not a file of its own, because a ratio can reference a user line and the manual promises that one file is a machine's whole configuration. **Removing or moving a line a ratio or correction references is refused**: nothing visible would break today (a `RatioDefinition` holds its own region copy), but the next Ratio Setup open would fail to match the missing species, fall back to the nearest wavelength and silently re-point that ratio — with no signal at the deletion and none later. CSV import is **merge-only** (skips what is already there, never removes), which is what makes it exempt from that same check; export writes the user lines alone. Saving takes effect **immediately** — a catalog line is not something the running engine computes with — so it has its own Save button separate from the staged correction table below it, and `MainViewModel` pushes it into the Ratio Setup pickers via `RatioSetupViewModel.RefreshLineCatalog()` rather than making the operator restart acquisition to find out.
- `WavelengthCorrection` + `WavelengthCalibration` + `WavelengthCorrectionViewModel` + `WavelengthCorrectionPanel` — Wavelength Calibration tab: a staged editor for a **catalog-level wavelength-drift correction overlay**. Each row corrects one catalog `(species, wavelength)` emission line by an additive offset (nm), stored sparsely in `LeakMonitorSettings.WavelengthCorrections` (only corrected lines are persisted; everything else uses offset 0). Because the key is the catalog `(species, wavelength)`, a single correction re-aligns **every** ratio (signal *or* reference) that uses that line — unlike the earlier per-ratio-line approach (reverted `e03f47a`) that stored the offset on each `LineRegion` separately. `WavelengthCalibration` (pure, no engine/UI deps) builds a `(species, wavelength) → offset` lookup and applies it at monitor-build time: in the `LeakMonitorEngine` constructor and `ReloadRatios`, each `RatioDefinition` is replaced in `_defs` (and its `RatioMonitor`) by a **corrected clone** whose region `CenterNm` is shifted, while `_settings.Ratios` keeps the raw catalog wavelength — so the correction reaches extraction (and thus Golden Run capture, calibration, SNR, CSV logging, all of which read `_defs`) but never leaks back into `settings.json`. Region→catalog matching keys on the region `Label`'s leading species token + `CenterNm`, with a small alias map folding the reference-preset labels (`"N₂"→"N2"`, `"Hα"→"H"`) back to catalog species. Save is gated to Engineer+, validates the offset range (±`MaxOffsetNm` = 5 nm) and rejects duplicate `(species, wavelength)` rows, and — like every Ratio Setup edit — is **staged**: it takes effect only on the next OES acquisition restart (`ReloadRatios`). Note this correction is deliberately distinct from `LineRegion.PeakSearchHalfWidthNm`, which already re-centers ±1 nm on the local peak each frame; the overlay is for larger axis drift or when the wrong peak sits inside that search window.
- `ConfigSnapshot` + `SystemLogMirror` — **what makes a day folder readable on its own.** The data lives wherever the operator pointed the logger (a fab machine's `C:\DualOES`); everything needed to interpret it lives under `%AppData%` — the save threshold and trigger mode that decide which frames are evaluated at all, the ratio definitions, the wavelength corrections, the active Golden Run, and the system log saying what the tool actually did. Copying a day folder off the machine takes the first and leaves the second, which is not a mistake anyone makes once: it is what the folder layout invites. On 2026-08-19 it cost a day's leak testing — the save threshold had to be bounded by arithmetic on the frame that opened the plasma gate, and the acquisition mode inferred from the frame interval, both of them sitting in a file nobody thought to copy (`docs/leak-test-20260819-analysis.md` §9). `ConfigSnapshot` writes `_config_{HHmmss}.json` beside the recordings when one opens, **skipping when the newest one there is identical** — so a settings change mid-session (that day: integration 200 → 100) leaves a second file whose name says when. It is `settings.json` **with holes cut in it, not a list of fields to remember**: the whole `accessControl` section goes, and any property named `passwordHash` anywhere in the tree, and everything else is copied wholesale — a hand-picked list would have omitted the logger trigger settings, which are exactly what was missing. `SystemLogMirror` copies the day's `yyMMddHH.csv` log files in as `_log_*.csv`, re-copying whichever has grown (the live hour is still being appended to, so every copy but the last is partial; the last is taken in `MainViewModel.Dispose`) and opening with `FileShare.ReadWrite` because `SystemLogger` holds its own handle. Both are best-effort and log their own failure; both are named with a leading underscore and are rejected by `Recording.TryParse`, so the review tabs walk past them. `MainViewModel.CurrentSettings()` is the single definition of "the settings right now", shared by Save and the snapshot — the snapshot exists to be trusted months later, so it has to be the same object the Save button would write.
- `DiagnosticBundle` + `DiagnosticManifest` + `OesLoadProbe` + `DiagnosticsViewModel` + `DiagnosticsPanel` — **the one-click diagnostic bundle**, on the Logs tab and **deliberately ungated**: the person who can press it is the Operator on the phone, and a diagnostic an Operator cannot produce does not exist. Same split as the SECS tab and the recorder strip — it reads and copies, it changes nothing. It serves exactly two questions, the two that cannot be settled over a phone call: *it silently stopped measuring* and *the host says it never got that alarm*. Both are answered from four places nobody copies together — the data folder the operator chose, the logs and configuration under `%AppData%`, the SECS profile and traffic log, and one fact that lives nowhere at all until something probes for it. `ConfigSnapshot` / `SystemLogMirror` fixed the narrow version of this for a day folder; this is the same argument for a whole machine. Contents: 7 days of system + SECS log (the whole `Logs\` tree is ~800 KB for three months, so the window is free, and a test-mode session is routinely noticed the next day), today's ratio CSVs and `_config_*.json`, the SECS profiles, a redacted `settings.json` **and its `.bak-*` files** — which is why `ConfigSnapshot.RedactJsonText` exists: a backup written by an older build need not deserialise into `AppSettings` any more, and a redactor that throws on the file it was aimed at fails open. `OesLoadProbe` is `tools/check-oes-connect.ps1`'s sections 1–4 run **in-process** (files, VC++ runtime, PE bitness, `LoadLibraryEx` + the Win32 error `CheckHardwareDllAvailability` swallows) — the button's process is already in the app folder, under the operator's account, at the right bitness, which are that script's three preconditions. It deliberately skips the script's section 5: re-entering the native SDK to enumerate USB while the tool may be acquiring makes a diagnostic nobody dares press, so the device's live state answers that half instead. **The `.ps1` stays** — when the app will not start, it is the only one of the two that can run. **Two omissions are the whole design.** A recording over the cap is dropped *whole*, never shortened: the EMA, the EWMA variance and the σ/min slope are dt-bound, so a trimmed full-spectrum CSV re-baselines happily and answers wrongly with nothing in the file to say so. And the newest recording is usually the one the logger holds open — copied anyway (`FileShare.ReadWrite`, as `SystemLogMirror` does, because it is the file covering the problem) but marked `Truncated` via the same exclusive-open probe `DataRetentionService` uses. Both land in the manifest's **"NOT in this bundle"** section, which is why the manifest exists at all: one listing only what is present reads as complete whatever is missing. `README.txt` and `manifest.json` are rendered from one object, never assembled twice. The filename leads with the **machine name, not the serial** — a serial reads `TEST_MODE_SIMULATOR` in precisely the failure this is for, so it is evidence inside and never a label outside; the chamber code is appended only when set, so its absence says "no MES here". Runs on a worker thread with no cancel (a half-written bundle is rubbish; the question during the wait is "is it done", which progress answers), keeps the newest 5 bundles, and logs the path as `DiagnosticBundleCreated` because the Explorer window gets closed and "where is it" is always the next sentence. `DiagnosticBundleTests` pins the three negative facts plus the button itself; operator-facing docs are manual §6.11.1 and the rewritten postmortem §5.
- `DataRetentionSettings` + `DataRetentionService` — data-folder housekeeping, in this project (no NuGet change). **It compresses, it never deletes**: a day folder that ages past `ArchiveAfterDays` (30) becomes a sibling `{baseDir}\YYYYMM\DD.zip`, so every row stays recoverable with any unzip tool and the actual retention decision stays with whoever owns the data. Two rules, in order: age first (what an audit asks about), then `MaxTotalSizeGB` (20) as a safety net that keeps compressing into newer folders, oldest first, until the tree fits. Neither ever touches the newest `MinKeepDays` (2) days or a folder holding a file the logger has open (`MainViewModel.IsFileInUseByLogger`, plus an exclusive-open probe that also catches a CSV someone left open in Excel). **The removal order is the safety property**: probe locks → write `.zip.tmp` → verify the archive's entry list equals the folder's file list → rename into place → only then delete the originals; any failure leaves the folder exactly as it was. `MainViewModel` runs a pass 20 s after start-up and every 6 h on a worker thread (`_retentionRunning` suppresses overlap), logs every action, and exposes the Configuration-tab row (enable, days, cap, Compress now, status). `MainWindow.ShowDataFolderWarning` shows free-space / over-cap warnings when the app opens and closes — and only then, since a dialog that appears every time stops being read.
  - **`Enabled` defaults to false, deliberately.** It shipped as true for exactly one development session, and launching the app once compressed three months of real data on the dev machine — an upgrade would do the same on a production tool, with months of days vanishing from the Recordings / Ratio Review lists (into archives, but still) that nobody asked to create. Warnings are issued whatever the switch says; only the compressing is opt-in. Restoring is `Expand-Archive` back into `DD\`, but don't rely on that being anyone's expectation.
- `WavelengthTrendViewModel` + `WavelengthTrendPanel` — the live intensity time-trend chart below the `DevicePanel` on the Monitor tab. It does **not** subscribe to the device itself; `MainViewModel.FanOutSpectrum` feeds it each frame via `OnSpectrum(...)` (see the single fan-out note below), and it plots one line per tracked wavelength: the trigger ("threshold") wavelength configured in the `LoggerPanel` (the "selected" wavelength — not a separate setting), plus the first `MaxMonitoredWavelengths` (5) entries of that panel's monitored-wavelength list (the wavelengths logged into the intensity CSV). Each line is the peak intensity within ±0.5 nm of its wavelength (a peak *locator* that absorbs wavelength drift — **not** noise filtering; by default the chart plots the raw per-frame counts, deliberately unfiltered, so it reads like a live scope). A dashed reference line marks the save-start threshold intensity. `MainViewModel` seeds it from `LoggerViewModel.ToSettings()` and re-points it (`Configure`) on every `ApplyAll`; any change to the tracked-wavelength set rebuilds and clears the trends. Two display toggles, both re-projecting from each `Track`'s retained raw points so the toggle also transforms the history already on screen: a **Smooth** checkbox (default off) applies the same `α = 1 − exp(−dt/τ)` EMA the Leak Monitor uses (τ = `SmoothTauSeconds`, 3 s) to damp per-frame noise — the running EMA is advanced every frame in `UpdateEma` and replayed across raw on toggle; a **Normalize** checkbox divides every line by its value at the moment the box is ticked (baseline captured in the *display* domain, so a smoothed line also snaps to 1.0), the threshold line hidden while normalized. Follow-while-zoomed, Zoom All — same chart conventions as the Leak Monitor trend. Retention is `AppSettings.TrendRetentionMinutes` (default 30, clamped 1–480), a **single setting shared with the Leak Monitor trend** — they are read together, and every point is held in memory, so the ceiling is a real limit. Applied via `SetRetention` at construction and on every `ApplyAll`; shortening it trims the plotted points immediately, measured against the newest point rather than the wall clock (the chart's clock is the spectrum stream — with acquisition stopped, "now" would empty it).
- `SpectrumReplaySource` + `ReplayViewModel` + `ReplayPanel` — **Replay tab: recorded-spectrum playback for algorithm validation.** In test mode the spectrum normally comes from the SDK's synthetic generator (`OesDevice.InitializeTestData`: `1000 + 500·sin(i·0.01) + noise`, a fixed 1000-point axis). This plays a recorded full-spectrum CSV instead — the wide format `IntensityCsvWriter` writes (`WaveLength,<wl…>` header, then `HH:mm:ss.fff,<intensity…>` rows), parsed with `RecordingCsvParser.ReadFull`, which also gives per-frame `ElapsedSec`. Engineer-gated tab with Choose CSV… / Play / Pause / Restart / Stop, a 1× / 5× / 20× speed, progress + frame counters, and a preview of the frame being delivered. The path persists as `AppSettings.SimulationCsvPath` (key name kept) and the rate as `AppSettings.ReplaySpeed`; a missing/unparseable file leaves test mode synthetic.
  - **Real axis, not the synthetic one.** Frames are delivered on the *recording's* wavelength axis. Its predecessor (`SpectrumSimulationSource`, removed) resampled onto the ≈200–800 nm / 1000-point test-mode axis because all it could do was overwrite the incoming frame's fixed-length intensity array — Ar 811.5 nm was dropped outright and everything finer than the device pixel spacing was interpolated away, so ratios, σ, SNR and leak rates all differed from what the same data gives on hardware. Replacing the frame outright needs the `DeviceViewModel.SpectrumMapper` seam (`Wpf 0.1.12`), which is why this is not a within-app-only change.
  - **Virtual clock.** Playback starts when Play is pressed and advances by the recording's own `ElapsedSec`, so frame timestamps are `playStart + elapsed`: the produced CSVs land in today's folder while the engine sees exactly the intervals the plasma was measured at — the EMA `α = 1 − exp(−dt/τ)`, the sustained-confirmation seconds, the σ/min slope and the leak-rate EWMA variance are all dt-bound. Speed scales the *wall* time only, so 20× is behaviourally identical, just faster. Pausing freezes both clocks and leaves no gap in the timestamps. `MaxFramesPerTick` (400) bounds one tick's catch-up burst and re-anchors the clock to what was actually delivered; the shortfall surfaces as `ReplayStatus.AchievedSpeed` and a warning line rather than silently running fast.
  - **Plays once.** The recording is played through exactly once and then holds on its last frame (`ReplayState.Finished`) — deliberately not looping, which stitched the file's end to its beginning and every baseline and alarm downstream read that as a real step change. Finishing keeps the stream (`Handled = true`, no frames) so the synthetic spectrum cannot resume into the recorders behind the operator's back. **The finish is reported on `ReplayTick.Finished`, not as an event raised inside `Advance`** — an event fired before the caller had fanned that tick's frames out, so the UI-thread teardown closed the replay's recorder session first and the run's last frames opened a session of their own, under the ordinary prefix once the teardown had restored it. The first real test run produced exactly that: three stray one-row files, two of them `P_Ratio_*` holding a replayed frame. `EndReplayOutput` also closes the recorders again after reconfiguring them, so a frame landing between the two calls cannot leave a session open.
  - **Test mode is a precondition, now enforced.** `SpectrumReplaySource.Advance` refuses a non-test frame (`!raw.IsTestMode → default`), so with a spectrometer attached Play delivered nothing — while the tab said `PLAYING`, the progress bar sat at 0, and `BeginReplayOutput` had already switched both recorders to the `SIM` prefix. A real session did exactly this and filed 450 KB of measured spectra as `SIMP_*`: the safeguard inverted, measurement labelled as replay. Three guards now: `ReplayViewModel.RealHardwareAttached` (fed by `MainViewModel.UpdateReplayAvailability` from `DeviceViewModel.IsConnected`/`IsTestMode`) disables Play and shows why; `Play()` re-checks before raising `ReplayStarting`, since starting is what moves the recorders; and `MapDeviceFrame` calls `AbortReplayForHardware()` on the first hardware frame that arrives while `_replayOutputActive`, which stops the replay, restores the prefix and logs `ReplayAbortedByHardware` — the connect can happen mid-run, after the button check has passed.
  - **Fan-out.** `MainViewModel` installs `MapDeviceFrame` as the device's `SpectrumMapper`; it calls `_replay.Advance(raw)`, fans every due frame out itself (`FanOutSpectrum` → intensity logger, leak engine, `WavelengthTrend`) since a fast-forwarding tick owes them several frames while the device wants one to draw, and returns the newest for the plot. `OnDeviceSpectrum` (the `SpectrumAvailable` handler, still the whole path when no replay runs) skips the frame when `_replayHandledFrame[slot]` says the mapper already dealt with it. Real-hardware frames (`IsTestMode == false`) are never replaced.
  - **Replayed output is marked.** While a replay runs both recorders are reconfigured with the `SIM` prefix (`MainViewModel.ConfigureRecorderOutput`, `ReplayPrefixMarker`), so files are `SIMP_OES1_…` / `SIMP_Ratio_…` — still `{prefix}_{tag}_{MMddHHmmss}`, so `Recording.TryParse` and both review tabs list them as usual, but replayed data is never mistaken for measurement. Both recorders are force-closed on start and on end, since a writer captures the prefix when its session opens. `ApplyAll` re-imposes the marker, because `Logger.ApplyCommand` pushes the unmarked prefix straight into the intensity logger.
  - **Ending a replay resets the monitors.** `EndReplayOutput` calls `LeakMonitorEngine.ResetRuntimeState(clearAlarms: true, reason)` **before** it closes the recorders and restores the prefix. The replay's last frames otherwise leave an EMA, a confirmation timer and a latched alarm behind, and the first synthetic frame after teardown opens a session under the ordinary prefix and writes them into it — measured on 2026-08-20 as `P_Ratio_0820153410.csv`, a production filename whose first row carries the recording's own σ-scores and `OverallState=Alarm` three quarters of a minute after the recording ended, plus a `LeakMonitorState Idle → Alarm` in the audit log that no chamber caused. Clearing the latch is deliberate: an alarm confirmed against a recording is not a fact about the chamber, and carrying it live would ask an operator to acknowledge something that never happened. `ReplayEndResetTests` covers both that and the Monitor-tab Reset, which still leaves a confirmed alarm latched.
  - **Alarms.** `LeakMonitorSettings.SuppressAlarmsInTestMode` (still true by default) is exposed as a checkbox here, because replaying a real recording is precisely the case where the alarm transitions are the thing being checked. **The switch is not scoped to the replay** — it governs every test-mode frame, so synthetic frames arriving after a replay ends are judged too (which is how the 2026-08-20 alarm above reached the log at all). `LeakMonitorViewModel.SetTestModeContext` keeps the tab's banner honest about both halves — which spectra, and whether alarms are live.
  - **Expect an acquisition mismatch.** The CSV does not carry the exposure it was recorded at, so replayed frames carry the *device's* current acquisition metadata and a Golden Run captured live will report `LeakMonitorAcquisitionMismatch`. Capture a baseline from the replay itself.
- `BaselineBuilder` + `RatioFrameSampling` + `BaselineBuilderViewModel` + `BaselineBuilderPanel` + `AcquisitionSidecar` — **Baseline Builder tab: a Golden Run pooled from recordings already on disk.** It exists for the two process shapes a live capture cannot serve: one that ramps before it settles (the steady segment starts where the plot says, not where a stopwatch does) and one whose whole run is shorter than a capture window (no single run holds enough frames, so several are pooled). Both need the segment chosen *afterwards*, with the trace visible. `BaselineBuilder` is pure computation — `Scan` re-extracts a parsed recording through the current wavelength-corrected ratio set, `Suggest` offers the flattest windows (deliberately dumb: it can see that a stretch is steady, never that it is leak-free), `Build` pools one window per recording into a `GoldenRun`. **Every per-frame decision goes through `RatioFrameSampling.Evaluate`, which the engine's own capture loop also uses** — a baseline built here lands in the same field and is judged by the same thresholds, so a second implementation of "does this frame count" would make two Golden Runs incomparable while both looked fine; `BaselineBuilderTests` pins that by replaying the recorded run through both paths and requiring agreement to nine decimal places. The minimum is a **frame count, not seconds** (σ's reliability follows the sample count; 120 s is 68 frames at 0.56 fps and 600 at 5 fps — the live capture counts seconds only because someone is waiting). A recording whose level disagrees with its peers is **excluded by default** and named, because pooling one run that was actually leaking makes the leak the baseline, after which nothing can detect it; overruling it is possible and usually futile, since the pooled σ then inflates past `MinBaselineMeanToSigma`. **One window per recording** — two windows out of one run are either one window with a gap or two operating points averaged together, which is the error the whole tab exists to avoid (see `docs/adr/0001`). Recordings on different wavelength axes are refused outright. **Three things the result reports beyond the baselines themselves**, all added after a real build came back nearly useless and half-said so: per-recording **in-window steadiness** (`σ/mean` and drift for the worst ratio — a steady plateau reads ~1 %, and drift separates a ramp from noise), a **marginal-baseline mark** when `mean/σ < MarginalMeanToSigma` (20) since 10.2 σ and 97 σ are indistinguishable on the Leak Monitor tab while the first has thresholds ten times wider, and an explicit **"no back-check"** line when every window covers its whole recording — the back-check is what would otherwise notice a window containing an excursion, and an empty section reads as a pass. The build that prompted this pooled three whole recordings, leak rise included, and produced one baseline at 10.2 σ where its steady-window value is 97. A fourth, **between-recording spread** per ratio, was added after the next build: two well-chosen windows, each steady to ~1 %, whose absolute-intensity levels sat 19 % apart because they were different runs at different plasma brightness — pooled, that gap *became* the σ and `mean/σ` fell from ~125 to 10.7. Ratio-mode entries divide the gap out (2–5 % on the same pair); absolute-intensity ones cannot, so **they want a baseline from one recording rather than several**. It is reported from two recordings upward, unlike the outlier check, which needs three to name one: "these two disagree" is worth knowing without knowing who is wrong. Saving goes through `LeakMonitorEngine.ImportGoldenRun`, which reuses the capture's own result type and confirmation dialog rather than growing a second one. `GoldenRun.Source` records what it was built from (`LiveCapture` / `OfflineBuild`, the files and windows, and the recordings the consistency check set aside) — live captures stamp it too, so a missing `Source` now means only "stored before this existed". `AcquisitionSidecar` writes `{recording}.acq.json` beside each recording as it opens (`MainViewModel.OnIntensityFilesChanged`), because a CSV says nothing about the exposure it was taken at and the alternative — a header field — means changing `IntensityCsvWriter` *and* `RecordingCsvParser` in the Core package; older recordings have none, so their fingerprint carries only the axis the CSV itself proves. `Recording.EnumerateSpectra` holds the data-folder walk that Recordings used to have inline; both tabs share it.
- `LeakRateEstimator` + `LeakCalibrationViewModel` + `LeakCalibrationPanel` + `CalibrationPointDialog` — Leak Calibration tab: a staged wizard that turns the qualitative ratio rise into a **quantitative leak rate** (mbar·L/s). The operator picks a baseline (Golden Run), then captures one calibration point per calibrated-leak element: `LeakMonitorEngine.BeginCalibrationPointCapture(leakRate, label, seconds)` averages each ratio's fractional rise `x = rawRatio/baselineMean − 1` over a window (reusing the Golden Run capture machinery) and raises `CalibrationPointCaptured`. Save calls `LeakRateEstimator.FitAll` — a through-origin weighted least-squares sensitivity `x ≈ s·Q` per ratio — and persists a `LeakCalibration` (points + per-ratio `RatioSensitivity`, bound to the baseline and reference labels) into `LeakMonitorSettings.Calibrations` in `settings.json`, gated to Engineer+. At runtime (P2) the engine holds a `LeakRateEstimator` built from the active calibration and computes a fused estimate every frame into `LeakMonitorSnapshot.LeakRate`: each ratio's `xᵢ` comes from its % -of-baseline and `σ_xᵢ` from a per-ratio EWMA variance (`RatioMonitor._emaVar`); `Estimate` inverts each to `Qᵢ = xᵢ/sᵢ` and fuses them by inverse variance into `Q̂ ± σ_Q` with a cross-ratio consistency confidence and an out-of-calibrated-range flag. The Leak Monitor panel shows it as a readout under the status banner ("Leak rate ≈ Q̂ ± σ · NN% confidence", or `extrapolated` / `not calibrated`). Saving a calibration calls `engine.ReloadCalibration()` so it activates immediately (no acquisition restart, unlike a ratio-set change). Pure math core (`LeakRateEstimator`) has no engine/UI deps. **The calibrated leak must be air** (or match the leak being detected) — an inert leak won't raise O/OH/NO. The estimate is also logged to the Ratio CSV (`LeakRate,LeakRateSigma` columns) and replayable in Ratio Review's "Leak rate" mode (P3). A calibration only applies while the active Golden Run matches the baseline it was captured against (`LeakMonitorSnapshot.CalibrationStatus`: `NotCalibrated` / `Active` / `BaselineMismatch`); switching baselines suspends estimation rather than silently mis-scaling it, and status transitions are logged (`LeakCalibrationActive` / `LeakCalibrationSuspended` / `LeakCalibrationCleared`). Every baseline change routes through `ApplyGoldenRun` → `BuildEstimator` to re-evaluate validity (P4). Switching (or capturing) the active Golden Run also **auto-selects the calibration bound to it** (`AutoPairCalibration` — the most recent `LeakCalibration` whose `GoldenRunName` matches, or none), so the active calibration follows the recipe and a recipe change doesn't leave a stale `BaselineMismatch`; the pairing is persisted (`SelectGoldenRun` raises `ConfigurationChanged`, capture persists on `GoldenRunCaptured`). Full design + math: `docs/leak-rate-calibration.md` (P0–P4 complete: model, estimator, wizard, runtime display, CSV logging/review, validity gating).
- **Leak Monitor** — an actinometry-based air-leak detector on its own tab. `LineIntensityExtractor` + `LineRegion` pull line intensities out of each `SpectrumSample` in one of three `LineExtractMode`s (`LineRegion.PeakSearchHalfWidthNm` re-centers the window on the actual peak each frame, so wavelength-calibration drift or a shifted band head doesn't corrupt the reading). `PeakHeight` and `Integral` subtract a linear continuum interpolated between two side windows; `Integral` is in **counts·nm** with fractional-pixel window edges, so it neither steps by a whole pixel when the peak search shifts the window nor depends on how finely the axis samples. **`RawMean` subtracts nothing and searches for nothing** — for a wavelength with no peak, where the two subtracting modes measure mostly their own baseline error: a convex continuum puts the interpolated line above the middle (systematically negative — measured −11.7 with 63 % of frames negative at 440.7 nm where the raw value is a stable 3745 ± 19), and the peak search on a monotonic slope pins the window to the edge of its search range every frame. `RatioDefinition.ValueHasPedestal` (a `RawMean` numerator, in either monitor mode — dividing by a reference scales the pedestal, it does not remove it) is the single predicate for everything that consequently changes: the Warn/Alarm **factors** are dropped in favour of the σ terms (1.2 × a pedestal is tens of σ — an alarm that looks armed and can never fire), the % -of-baseline display becomes a σ-score, the trend slope reads in σ/min, the leak-rate calibration fits the absolute rise Δ instead of the fractional one, and the ratio CSV names that column `_sigmaScore` rather than `_pctBaseline`. Raw readings carry no noise estimate at all (SNR **unknown**, not high — dividing a pedestal by the continuum σ reports 200 for a wavelength with no line on it), so the SNR gate stands down for them; in ratio mode it still gates the reference line, which does have one. `LeakMonitorEngine` divides signal lines by a reference line into ratios — the reference defaults to Ar 750.4 nm but is switchable per ratio from `ReferenceLineCatalog` (N₂ 337.1, N₂ 662.4, Hα 656.3, Ar 750.4, Ar 811.5). **The factory ratio set is what one machine's known-leak measurement selected, not the textbook assumption**: `R_N2Ar` (N₂ 337.1 `RawMean` / Ar 750.4, 33.8 σ), `R_NOAr` (NO 237, 18.3 σ — a second species, so an independent opinion), `R_N2357Ar` (N₂ 357.7 `PeakHeight`, 16.2 σ, so one ratio dropping to LowSignal can't make `RequireTwoForAlarm` unreachable), and `R_N2357Abs` — the same 357.7 line undivided, **shipped disabled**, whose only job is to be read beside `R_N2357Ar` to separate a chemistry change from the whole spectrum brightening. Absolute intensity doesn't return to baseline once a leak is closed (+7.6 % measured, with the Ar-normalized ratio back at +1 %), so armed by default it would park an untuned tool in Warning after every event. It replaced `R_O`/`R_OH`/`R_NO`/`R_Ar` (all over N₂ 337.1), where three of the four numerators measured 0.1–0.7 σ against the same leak that moved the *denominator* 33.8 σ. Factory Warn/Alarm factors are 1.05/1.12 (that machine's 2 % scatter); `RatioDefinition`'s class defaults stay 1.2/1.5 for hand-added ratios. Existing installs are not migrated — `CreateDefault()` only runs for a fresh `settings.json`; a Golden Run baseline only applies while everything that defines the monitored quantity still matches: the reference line it was divided by (`GoldenRunRatioBaseline.ReferenceLabel`, ratio mode only — an absolute baseline stores `""` so swapping an unused line can't invalidate it), the monitor mode (`.Mode`; a ratio and a line intensity are not the same quantity), and the extraction revision (`.ExtractionRevision`, checked only for ratios whose reading involves an `Integral`, whose unit changed to counts·nm — peak-height and raw baselines survive the upgrade). Each mismatch logs its own `LeakMonitorBaselineMismatch` reason. A capture is also rejected outright unless its mean clears `MinBaselineMeanToSigma` (10) σ and zero (`GoldenRunRatioUnstableBaseline`): thresholds, the % display and the leak-rate fit all divide by that mean, and a `−25 ± 95` baseline turns every one of them into the sign of the noise. `GoldenRun.Acquisition` records the integration time / averaging / correction switches / axis the capture ran under (`AcquisitionFingerprint`, fed in by `MainViewModel` via `ConfigureAcquisition` at start-up and on every Apply); a live mismatch surfaces on `LeakMonitorSnapshot.AcquisitionWarning`, in the Leak Monitor banner, and once in the log (`LeakMonitorAcquisitionMismatch`) — absolute-intensity readings scale with those settings, so changing the exposure silently re-scales every ratio against a baseline that no longer applies. The engine runs a per-ratio `RatioMonitor` (EMA + two-level threshold state machine + sustained-confirmation + latched alarm), and computes a composite `LeakAlarmLevel`. **`Acknowledge(user)` logs `LeakMonitorAcknowledged`** (who, which latched ratios were cleared, composite before → after) — without that entry the audit CSV showed an alarm ending by itself, which is what a real run produced: an `Alarm → Normal` at 21:10:37 with nothing to attribute it to. The one other place a latch clears is `ResetRuntimeState(clearAlarms: true, reason)`, which logs `LeakMonitorAlarmLatchCleared` naming the reason and the ratios; the invariant is not "only Acknowledge clears a latch" but "nothing clears one without an entry of its own". A call that finds nothing latched logs nothing, so the entry always means a human ended a confirmed alarm. `LeakMonitorViewModel.SetRole` carries the username for it. **Signal-quality gate:** `LineIntensityExtractor.Extract` returns a `LineMeasurement` (value + a local continuum-noise σ estimated from the baseline windows → SNR); when the signal or reference line falls below `RatioDefinition.MinSnr` (default 5) the ratio enters `RatioState.LowSignal` and is held out of the composite alarm (absolute mode judges **only** the monitored line — the reference takes no part in the reading, so letting its SNR veto would leave a strong line reading "low signal" for ever) — at low plasma intensity the ratio of two near-noise lines is meaningless however well it is smoothed. The Warn/Alarm thresholds also widen by the *larger* of the Golden-Run σ and the live EWMA σ, so a noisier-than-baseline ratio doesn't trip on its own jitter. The Leak Monitor panel shows each ratio's SNR and a "LOW SIGNAL" banner when any enabled ratio is below its floor. The **same SNR floor gates Golden Run capture**: a frame only feeds a ratio's baseline if its lines clear `MinSnr` (mirrors the runtime gate), and `FinalizeCapture` *rejects* a ratio's baseline outright when fewer than `MinBaselineAcceptFraction` (0.5) of its SNR-evaluable frames cleared the floor — so a near-noise line can't seed a baseline from a biased sliver of upward noise excursions (logged `GoldenRunRatioLowSnr` / explained in `ReportDroppedRatio`). **A capture that clears none of those gates is discarded outright** — `FinalizeCapture` returns before it stores the run, so an empty capture neither becomes the active baseline nor replaces a same-named run that is already working. Storing it (the old behaviour) took every ratio's baseline away at once and unpaired the bound calibration with it, on the strength of a window that measured nothing — usually just a trigger threshold set above the plasma, with the gate shut for the whole minute. The engine reports every capture on `GoldenRunCaptureFinished` (a `GoldenRunCaptureResult`: the run, `Accepted`, and the per-ratio rejection reasons — the same sentences the log carries); `GoldenRunCaptured` now fires **only for an accepted capture**, since a discarded one leaves nothing for `MainViewModel` to persist. `LeakMonitorViewModel` turns the result into a modal: Error for a discarded capture (naming the baseline left untouched), Warning listing the ratios that got no baseline when some did — a capture is a deliberate action the operator waited a minute for, and a silently partial one leaves ratios out of the composite alarm with no sign on screen. **A capture that would destroy baselines a same-named stored run still has is held unstored** (`NeedsConfirmation` + `Lost`): the VM merges that into one Yes/No dialog (what this capture missed *and* what replacing would cost — two halves of one sentence, and a second window saying it again is one that gets clicked away), then `ConfirmCapturedRun(run, keep)` either stores it or logs `GoldenRunCaptureDiscarded`. Only same-name overwrites are compared, because only they are irreversible; capturing under a new name leaves the old run selectable. A capture that loses nothing — the weekly re-baseline — is stored without asking, since a confirmation seen every time is one nobody reads. The dialog also names the run it would replace *before* the minute is spent, since it offers the current name by default. **Alarms don't escalate or latch during a capture** (`RatioMonitor.SuppressLatch`, `wasCapturing`): the window is judged against the baseline being replaced, so after a recipe change a deviation is certain and means nothing — an acknowledge-me alarm from a routine re-baseline is how operators learn to acknowledge without reading. `GoldenRunCaptureDeviation` logs where each ratio actually sat relative to that outgoing baseline (σ for pedestal values, % otherwise) — stated, not judged, because the same number is noise after a recipe change and the whole story when re-capturing the same recipe. A "Golden Run" captures the leak-free baseline (mean/σ per ratio) and is persisted to `settings.json` the moment it completes. `LeakMonitorViewModel` / `LeakMonitorPanel` show the per-ratio rows, the % -of-baseline trend chart, and the capture / acknowledge commands. `SpectralLineCatalog` is the static reference line table. Engine alarm transitions and Golden Run captures bridge into `SystemLogger`. `RatioCsvLogger` writes the ratio trend (raw ratio + % of baseline / σ-score per ratio) — each column headed `{DisplayName} [{key}]`, since the key is a random GUID stub (`RatioEditViewModel.GenerateKey`) that deliberately never changes so baselines and calibrations survive a rename, which also makes it meaningless to anyone opening the CSV without the `settings.json` that produced it; `RatioCsvReader.SplitColumn` recovers both, bare-key files (everything written before this) still parse and just have no label — to `{prefix}_Ratio_{MMddHHmmss}[_N].csv` under the same `DataDirectory\YYYYMM\DD` folder — **its own recorder, deliberately independent of the threshold logger** (see below). All of this lives in this project, not the NuGets.
- `PlasmaGate` — the plasma-present gate for **absolute-intensity** ratios, mirroring `DualIntensityLogger.SampleTriggerMetric` exactly (nearest bin within `WavelengthToleranceNm` / frame percentile / brightest monitored wavelength, per `TriggerMode`) against `SaveStartThresholdIntensity`, so the gate and the recorder judge brightness by one measurement — a third way to measure it would guarantee the two eventually disagree. **They share the metric and the threshold, not the state machine**: the gate is a bare per-frame `metric > Threshold`, while the recorder confirms for `StartConfirmSeconds`, holds through `StopConfirmSeconds`, and (Core 0.1.8) back-fills. So a recording carries gate-closed rows at both ends — the `PreTriggerSeconds` head and the stop-confirm tail — and "the gate is open" is not the same claim as "this row is in a file". `MainViewModel` feeds it in via `LeakMonitorEngine.ConfigureTrigger(LoggerSettings)` at construction and on every `ApplyAll` — **hot-applied**, unlike a Ratio Setup edit, because it is a logger setting and a staged one would leave the two disagreeing for the rest of the run. **Both modes gate on it.** Ratio-mode entries additionally require their own reference line (`den > 0 && den > floor`) because they divide by it — **the floor is per reference line**, keyed by `LineRegion.MeasurementKey` (the string form of the `MeasuresSameAs` fingerprint) and stored in `GoldenRun.PlasmaFloors`. It was one pooled number per run, which only holds while every ratio shares a reference: mix an Ar 811.5 reference with an N₂ 662.4 one and the pooled 20 % lands *above* the faint line's normal level, so that ratio reads "plasma off" every frame and goes silently dark while the bright one is left effectively ungated. Keying on the full fingerprint rather than the label is deliberate — two ratios can read `Ar 750.4` as `PeakHeight` counts and as an `Integral` in counts·nm, and pooling those is the same mixing one scale down; too-fine a key merely stops the pooling, too-coarse is a wrong number. `GoldenRun.PlasmaPresentFloor` survives as the fallback for runs captured before this and is no longer written, so an upgrade changes nothing until the next capture. `_floorByRatio` is resolved in `ApplyGoldenRun` (the only place either `_defs` or the active run changes), not per frame — but that check is not a plasma test: a frame the spectrometer returns *blank* still carries ~75 counts at the reference wavelength, clearing `> 0` and clearing a floor derived from a capture those same blank frames contaminated. A real run produced 20 such frames in 13 minutes; **one** of them inside a Golden Run capture pushed that ratio's baseline to `0.02512 ± 0.05914` (σ 2.4× the mean) so `MinBaselineMeanToSigma` rejected it — with the gate the same window gives `0.02064 ± 0.00073`. `TrackGateDropouts` counts brief closures sandwiched between good frames and logs `SpectrumFrameDropout` (first immediately, then a running total at most every 5 min): the gate discards them silently, and an instrument fault you can't measure is one you can't fix — this is the number that says whether `AcquireMode = Oneshot` helped. A closure longer than `MaxDropoutSeconds` (1 s) is the plasma genuinely going off, not a dropout, and isn't counted. Absolute mode never had the reference to fall back on: it doesn't divide by it, so the reference needn't exist — and a line that isn't there extracts to continuum noise about zero, making `den > 0` a coin flip that decided whether the frame was evaluated (32 % of rows blank in a real run), while a reference on a *convex* continuum extracts systematically negative (a linear baseline drawn between the two side windows lies above it) and the ratio never evaluated a single frame. An unusable / unmeasurable gate leaves absolute ratios **ungated** and logs `LeakMonitorPlasmaGateUnavailable` once — "we can't tell" is not "plasma off", and a silently dead ratio is the failure this replaced.
- `RatioCsvLogger` — **independent of the intensity logger.** It used to open/close in lockstep with the threshold logger's save sessions, which tied the leak record to the raw-spectrum recorder; disarming that recorder — or simply running below its trigger threshold — silently threw away the leak history and left Ratio Review with nothing to replay. The two are not the same kind of data: a full-spectrum intensity row is ~22 KB (~400 MB/hour at 5 Hz), a ratio row ~200 B (~4 MB/hour), so the ratio CSV is cheap enough to always write. It now subscribes only to `LeakMonitorEngine.SampleProcessed`, opens lazily on the first frame after idle, and closes on `Stop()` — called from `MainViewModel` when acquisition stops and on Reset Run. A session crossing local midnight rolls into a new file so each day's rows land in that day's folder (which also bounds a continuously-acquiring file to one day). `Configure(LoggerSettings)` mirrors the intensity logger's base directory + file prefix (startup and every `ApplyAll`) so both recorders share one folder tree; that is now their only coupling. `UniquePath` appends `_N` if a same-second file exists, since the writer opens with `append:false` and two sessions can share a start second (a quick double Reset Run). A failed open sets `_openFailed` so a broken path is not retried once per frame. **Consequence:** the ratio file no longer shares a session timestamp with an intensity CSV, so `RecordingsViewModel` skips every non-`"OES1"` file at scan time — without that, each ratio file would create an empty `RecordingGroup` of its own in the Recordings list.

- **SECS/GEM equipment interface** — lets a fab host (MES) connect over HSMS and read the leak monitor's state, receive leak alarms, and be told when acquisition starts or an operator acknowledges an alarm. Design + field tables: `docs/secs-integration.md`; wire semantics: `docs/Satellite_SECS_Specification_v2.md` (`ss=27`). The protocol itself is the `Aqusen.Secs` NuGet; this project supplies the values and the policy.
  - `SecsBridge` — owns the `EquipmentSimulator`, registers the `SvBindings`, and pushes alarms/events. **It reads, it does not compute.** Every binding is invoked by the library on the requesting thread — once per S1F3, once per trace sample, several at a time — so the last `LeakMonitorSnapshot` is held as one volatile reference to an immutable object and the bindings do nothing but read a field and convert it. If a number is not already in the snapshot it does not belong in this class; that is why VID 021–023 became snapshot fields (`PlasmaPresent`, `PlasmaGateAvailable`, `DropoutCount`) instead of being re-derived. Sends are chained through `Enqueue` so an alarm's set and clear cannot arrive out of order — a host that receives them reversed is left holding an alarm that ended.
  - `SecsChamberCoding` + `SecsProfileTemplate` — the profile is a site-editable JSON in `{ConfigDirectory}\profiles\`, written from the built-in template on first run and carrying `cc = 00`. At start-up the configured chamber code is stamped into every `svid`/`alid`/`ceid` and the result is written to `profiles\.effective\` and loaded from there. Stamping **validates**: wrong digit count, `ss ≠ 27` or `aa ≠ 00` refuses to start rather than serving ids belonging to another sensor type. `cc = 00` is not a chamber, so an unstamped profile can never be mistaken for a stamped one. The two paths are printed into the traffic log because field staff have to find them without a developer.
  - `SecsSettings` (in `settings.json` under `secs`, **`Enabled` false by default** — an upgrade opens no port until asked) + `SecsViewModel` / `SecsPanel`. Three reporting switches: alarms, events, and *report test/replay data too* (off by default — synthetic and replayed frames are not measurements, and an alarm arriving at the host carries no marking that says so; VID 016 reports the truth either way). Switching reporting off never hides anything from a status query.
  - **Alarms** are ALID `1{cc}27nnn`: 001/002 leak warning/alarm from the composite level, plus 012–014 (connection lost / acquisition error / data write failure) added to the specification's reserved range. The fault three are **not** suppressed in test mode — a spectrometer off the bus is a fact about the tool whatever the frames contain — and 012 is a *transition*, not a state, so launching disconnected is not a fault. **Events** are CEID 502/508/509, wired to `LeakMonitorEngine.Acknowledged` (added for this; it fires on exactly the condition that writes the `LeakMonitorAcknowledged` audit entry) and the `IsAcquiring` transition `MainViewModel` already watches.
  - `SecsLogFile` — every message in and out, to `Log\secs_YYYYMMDD.log`, day-rolled and pruned. Deliberately not the audit CSV: thousands of lines an hour would bury it, and acceptance asks for this trace.
  - **ALID goes out as ASCII** (`<A[8] "10227002">`), which the Satellite specification uses throughout. `Aqusen.Secs 0.5.0` only sent U4, so 0.6.0 added `GemOptions.AlarmIdFormat` (default still U4) and made `SecsItems` parse an inbound ASCII id — a host disabling an alarm by the id it was announced has to reach the same alarm.

### Conventions worth knowing

- The single device keeps the tag `"OES1"` (not `"OES"`) so the existing recording file-pairing infrastructure, filename scan, and `RecordingGroup` logic keep working unchanged. Don't rename it.
- The **SECS tab is deliberately not gated** — whether the tool is talking to the MES is a question an Operator gets asked, and the answer must not need a sign-in. Its settings carry the gate instead (`SecsViewModel.CanEdit`, bound to the settings `Border`'s `IsEnabled`). Same split as the Monitor tab's recorder strip: seeing the state is an Operator concern, changing it is not.
- The Configuration and Replay tabs are gated to Engineer+ (`MainWindow.IsEngineerGated`); window close is blocked for Guest. Both gates are enforced in `MainWindow.xaml.cs` (`MainTabControl_SelectionChanged`, `MainWindow_Closing`). The gate identifies its tabs by `x:Name` (`ConfigurationTab`, `ReplayTab`, `MonitorTab`) and compares by reference — **never reintroduce a hard-coded tab index here**. It was written that way twice and silently broke both times a tab was inserted ahead of Configuration (most recently `6734da1`, which left Configuration ungated for anyone including Guest while the gate guarded Leak Calibration instead).
- Sample flow: each `DeviceViewModel.SpectrumAvailable` event is forwarded to `DualIntensityLogger.ProcessSample(slot, sample)`. The logger's threshold state machine decides when to open/close CSV writers; lifecycle events (`StateChanged`, `ErrorOccurred`, `FilesChanged`) are bridged into `SystemLogger` for the audit log.
- `MainViewModel.ConnectBothAsync` calls `OesDiscovery.OpenAllDevices()` once, then hands one handle to each slot via `AttachAsync`; slots with `ForceTestMode=true` or that run out of handles fall back to `ConnectStandaloneAsync`. Unused handles are explicitly closed.
- Settings are saved atomically (temp file + `File.Move(..., overwrite:true)`). The `AccessControl` user list is re-read from disk on each persist so user-management edits don't clobber unsaved Configuration-tab edits, and vice versa.
